0.3 用语与优先级

MUST必须满足，例外只经 ADR；SHOULD默认做法，偏离在 PR 或任务说明中写一行理由；MAY允许。规则编号（如 ERR-04）供评审引用；未标等级的规则对所有等级有效。

冲突时依次服从：安全不变量与已发布的对外契约 > 维护者采纳的 ADR > 本规范的 MUST、SHOULD > 外部基线（各章引用的标准）> 文件既有风格（只在修改旧文件时沿用）。

0.4 例外与 ADR

  • MUSTG-04对 MUST 的例外，以及改变结构、对外契约、安全边界、发布门禁、外部基线或第三方组件的决定，写 ADR（20.2）；写明范围和到期条件。难回退的决定有记录，避免反复争论和返工。
  • SHOULDG-05ADR 由维护者采纳；AI 代理只能写“提议”状态的 ADR。
  • MUST NOTG-06未经维护者批准删除、跳过、放宽任何检查、测试、断言或阈值。认为检查有误时保持原样并附证据报告。防止用放宽检查让结果变绿，掩盖真实缺陷。

0.5 规范本身的维护

  • SHOULDG-07本规范有版本号和日期（当前 1.1，2026-11-02）：删除或放宽 MUST 升主版本，新增规则升次版本，措辞修正升修订号；每次变更记入文末的规范变更记录。
  • SHOULDG-09每个项目在里程碑或发布后的回顾中复查一次：把教训写成规则，把成本高于收益的规则删除或降级。

★ 最小必做清单

每个项目从第一天起遵守这 20 条，与等级和领域无关。其余规则按等级和配置采用。

  1. 结构清楚：分层只向下依赖，外部系统（厂商 API、设备、网络、文件）只在适配层出现（ARC-01）。
  2. 一个功能一个实现：重复的逻辑合并，版本差异放在适配器（Q-03）。
  3. 只在边界校验：外部输入在进入时校验一次并转为类型化对象，内部调用不重复检查（P-21、P-22）。
  4. 不过度设计：没有单实现的推测性接口、没有只重抛的 try/catch、没有没人要的配置项（1.4）。
  5. 错误明确：失败有错误码和可执行的消息，不吞异常，不靠异常文本猜结果（ERR-01、ERR-04）。
  6. 结果未知不重放：写入发出后结果不明，就停下交给人（ERR-07–ERR-10）。
  7. 写入先确认：改变目标、设备或用户数据前，预览并由人确认（P-04）。
  8. 不放宽检查：检查、测试和阈值只收紧，放宽要维护者批准（G-06）。
  9. 主要行为有测试：每个功能的主要路径和规定的失败路径有测试；修缺陷先写修改前失败的测试（TST-01、BUG-02）。
  10. 测试快且稳：测试不等真实时间超过 1 秒，不依赖网络和真实设备（TST-05）。
  11. 分析器干净：新代码零新增警告，格式由工具统一（Q-15）。
  12. 合并经过评审：每次合并前有人或主导代理评审，并通过合并门（REV-01）。
  13. 不提交密钥和客户数据：仓库、日志、夹具中没有凭据和真实项目（SEC-22、DAT-07）。
  14. 日志去敏：日志、诊断包中不出现凭据，项目内容默认不记录（ARC-17）。
  15. 可诊断：每个操作有请求号，失败有诊断编号（P-14）。
  16. 一个构建入口：一条命令构建、测试、打包，依赖版本锁定（BLD-01、DEP-03）。
  17. 不改系统设置：产品和代理都不改 PATH、全局环境、安全设置（CFG-06、AI-12）。
  18. 只结束自己的进程：按核对过路径的 PID，不按名称（WIN-14）。
  19. Git 卫生：显式 git add 路径，英文提交，不加 AI 署名，不做破坏性 Git 操作（GIT-03、GIT-04、AI-13）。
  20. 决定写下来：难以回退的决定写 ADR，用户可见的变化写 CHANGELOG（G-04、DOC-06）。

★ 任务手册

要点日常工作按手册走，不必先读章节。每一步链接到规则，遇到问题再查。

新建项目

  1. 定等级（S/M/L）和领域，写进 README（T.1）。
  2. 按黄金路径建骨架、构建入口、锁文件、分析器和格式化配置（★ 黄金路径）。
  3. 建合并门命令和 CI，让第一条测试在两分钟内跑完（★ 快速交付）。
  4. 写代理说明（T.8），复制术语表（附录）。
  5. M+ 写 ADR 0001“采用本规范”、SECURITY.md、THIRD-PARTY-NOTICES。
  6. 用“新增功能”手册做第一个功能。

新增功能

  1. 写需求与验收标准（18.2）。
  2. L2 且 M+：一页设计说明，维护者批准（T.3）。
  3. 拆成可独立合并的任务，每个写任务说明（T.4）。
  4. 先把验收标准写成测试，再实现；只在边界校验（P-21）。
  5. 内循环：构建 + 相关测试，两分钟内反馈。
  6. 提交 PR（T.5）；评审（18.5）；合并门。
  7. CHANGELOG、文档、实机核对清单同步（第 23 节）。

修复缺陷

  1. 登记（T.6），按 S1–S3 分级；S1 先用配置停用相关功能（13.1）。
  2. 归类：真实缺陷、不稳定测试、环境、本分支回归（BUG-03）。
  3. 复现并定位根因；不试错（BUG-04）。
  4. 写一个修复前失败的测试（BUG-02）。
  5. 最小修复，内循环通过，评审与合并门。
  6. M+ S1 写复盘（BUG-06）。

重构

  1. 写明“行为不变”的范围和目的（可读性、去重复、为某个功能铺路）。
  2. 先补对等测试，锁住现有行为（Q-17）。
  3. 单独成批，不混入行为变化；新旧路径并存（Q-18）。
  4. 小步合并，每步过合并门；对等测试通过后删除旧路径。

增加依赖

  1. 先确认标准库或已有依赖做不到。
  2. 核对许可证（DEP-02）、维护状况、体积与传递依赖。
  3. 精确锁定版本并入锁文件（DEP-03）；离线还原可用（DEP-04）。
  4. 更新 THIRD-PARTY-NOTICES 与 SBOM（DEP-06、DEP-11）。
  5. M+ 运行时依赖经维护者批准，写一行理由或 ADR。

发布

  1. 维护者确认版本号和范围；发布期间不改代码（BLD-07）。
  2. 核对发布证据：M+ 最近一次夜间检查通过且之后无失败。
  3. 生成发布说明和“未验证”清单（T.7），核对支持矩阵。
  4. 由发布命令改版本号、打包、算 SHA-256、生成 SBOM。
  5. 预发布标为预发布、不设为最新；附测试清单与反馈模板（PKG-08）。
  6. 上传后更新交接文档与发布记录。

热修复

  1. S1 先用配置停用受影响的功能，告知用户。
  2. 在主干上按“修复缺陷”手册修复，带回归测试。
  3. 合并门加受影响的实机核对；发布修订版本（X.Y.Z+1）。
  4. 发布说明写清影响范围和升级要求；复盘。

新成员或新代理入门

  1. 读最小必做清单、黄金路径和本手册（约 15 分钟）。
  2. 读项目的代理说明、交接文档和术语表。
  3. 本机跑一次构建和合并门，确认环境可用。
  4. 代理：只接收按 T.4 写的任务说明，遵守 19.4 的开发机规则。
  5. 第一个任务选 L1（小修复或补测试），走完整的评审与合并。

1 工程原则

要点正确与安全排在简单前面，简单排在其他一切前面。只在边界校验一次；推测性抽象和防御层让每次改动都更慢。

1.1 正确与安全

  • MUSTP-01依赖的每条目标行为都有出处（厂商文档、SDK 元数据、设备手册或实机验证记录的条目编号），不按名称、相邻版本或“应该也行”推断能力。没有出处就先验证。凭记忆或推断写的厂商行为是最常见的实机缺陷。
  • MUSTP-03未经实机验证的行为在台账和发布说明中标为 NOT RUN。防止发布说明声称没有验证过的能力。
  • MUSTP-04改变目标、设备或用户数据的操作先预览，再经人确认执行。未经确认的写入可能损坏用户数据或设备状态。
  • MUSTP-05失败不留下不一致的数据：能回滚就回滚，不能就先备份并如实报告。半途失败会留下无法使用的数据。
  • MUST NOTP-06用软件代替安全功能（安全 PLC、硬接线联锁，见领域 B）。软件故障不能危及人员与设备。

1.2 简单与一致

  • SHOULDP-08同一概念全项目一个名称、一种形式（参数、错误码、单位、目录、日志字段）。
  • MUSTP-09同一能力一个实现，共享逻辑不复制。两份实现迟早不一致，修一处漏一处。
  • SHOULDP-10扩展点只开在已经发生过或路线图写明的变化方向（新工具、目标新版本、新设备协议），形式是“声明式登记 + 一处实现”（2.5）；其他方向不预留，除非有 ADR。
  • SHOULD NOTP-11为跨项目复用建共享库；需要时复制并注明来源。

1.3 只在系统边界校验一次

边界有四类：外部输入（API 调用、操作员输入、命令行、配置）、进程与通道（子进程、插件、设备通信）、文件与操作系统、厂商 API。

  • MUSTP-21输入在跨过的边界上校验一次（类型、必填、枚举、范围、单位、路径），结果是类型化对象。未校验的输入在深处才失败，难以定位。
  • MUST NOTP-22在内部调用中重复同样的检查；内部前提被破坏是缺陷，用断言暴露。重复检查彼此不一致，改动时容易漏改。
  • SHOULDP-23厂商 API 或设备的返回值（空对象、未设置、部分成功、质量位）在适配层检查一次，再转为本项目的类型。

推荐：边界一次，内部信任

var request = ExportRequest.Bind(arguments); // 失败 -> INVALID_ARGUMENT
return exporter.Export(request);             // 内部不再检查

避免：层层重复、吞掉原因

if (string.IsNullOrWhiteSpace(path)) return Fail("path");
try { return adapter.Export(path ?? "", dir ?? ""); }
catch (Exception) { return Fail("unknown"); }

1.4 不过度设计、不过度防御

  • MUST NOTP-12只有一个实现的接口或抽象类，除非它是真实边界（厂商 API、设备、文件系统、时钟、进程、网络）或测试需要的接缝。多余的抽象增加每次阅读和修改的成本。
  • MUST NOTP-13只重抛、或记录后继续的 try/catch；“以防万一”的回退路径；每层都判空。吞掉或绕开的错误让故障无法诊断。
  • SHOULD NOTP-15没人要求的配置项和开关。
  • SHOULD NOTP-16测试不可能出现的状态（类型系统或边界校验已排除的情况）。
  • SHOULD NOTP-18与当前问题无关的实验：计时探针、几十次压力重跑、额外的“加固轮”。只查阻塞合并或发布的问题，修好就停。

理由防御层和推测性抽象让每次改动都变慢；保护数据和设备的检查属于安全，不在此列。

1.5 事实只有一个来源

  • MUSTP-25对外契约（API、工具、文件格式、PLC 接口数据块）只按版本政策改变（第 17 节）。契约悄悄变化会让客户端失效。
  • SHOULDP-26目录、矩阵、数量、示例和迁移表由生成器从同一来源产出，生成文档开头注明生成命令且不含时间戳；手写文档只链接。
  • MUSTP-14每个操作有请求号，从入口传到子进程、插件和通信层；对外报告的失败带能定位日志的诊断编号。没有请求号就无法从报错追到原因。

2 架构

要点外部系统只在适配层出现，绝大部分代码因此能离线测试；不稳定的厂商组件放进隔离进程，故障不带倒主进程。

2.1 分层与依赖方向

入口传输、界面、命令行：只做绑定与呈现
↓
应用层边界校验、确认、审计、排队、错误映射
↓
领域逻辑规则、计划、换算；以纯函数为主，不引用外部库
↓ 经接口
适配层厂商 API、设备协议、文件、进程、时钟、网络
契约（横向）DTO、错误码、协议消息；不引用任何层
  • MUSTARC-01依赖只向下；外部系统只在适配层出现，适配器由组合根注入。外部系统散落各处，代码就无法离线测试和替换。
  • SHOULDARC-02M+依赖方向由工程引用和架构测试强制，不靠约定。
  • MUSTARC-03外部对象（厂商对象、设备连接、界面对象）不跨层或进程边界；跨边界只传 DTO 和标识。外部对象跨边界会引发线程和生命周期故障。

2.2 隔离不稳定的外部组件

  • MUSTARC-04可能挂起、崩溃或有线程亲和性的组件（厂商 API、驱动、原生库）放在隔离单元：独立进程，或专用线程加有超时的调度器；它故障不能带倒主进程。厂商组件崩溃会带倒整个服务。
  • SHOULDARC-05进程间协议有版本号和握手（协议版本、对方身份、一次性 nonce），不匹配就拒绝。
  • SHOULDARC-06对同一目标实例的调用串行化；不访问目标的操作不排在它后面。
  • MUSTARC-07隔离单元超时、退出或回复损坏时，这一代标为故障，显式恢复前拒绝后续调用，不自动重放。故障后的状态不可信，继续调用会扩大损坏。

2.3 错误模型

  • SHOULDARC-08组件内部用语言惯用的方式报错（异常或错误值）；边界（API 入口、界面命令、命令行）把它们映射为对外错误，映射表只此一处。
  • SHOULDARC-09错误码是闭集，集中定义在契约中，UPPER_SNAKE 拼写。

2.4 日志与诊断

  • SHOULDARC-11结构化日志（消息模板），每条带请求号；日志级别有约定（Information 记开始、结束、耗时；Debug 记参数摘要）。
  • MUSTARC-12以 stdio 提供协议的进程，stdout 只输出协议；日志写 stderr 或文件。stdout 混入日志会破坏协议通信。
  • SHOULDARC-14M+对目标的写入在发出前落盘一条“开始”记录，结果确定后补记；重启后先处理只有“开始”的记录。
  • SHOULDARC-15M+审计（谁、何时、做了什么、结果）与运行日志分开；审计只追加、按哈希链防篡改，不自动删除。
  • MUSTARC-17日志、审计、诊断包写出前去敏：凭据替换为占位符，用户名与用户目录换成占位符，用户项目内容只在 Trace 级别记录（默认关闭）。日志和诊断包会泄露凭据和客户数据。

2.5 扩展点

  • SHOULDARC-18每个扩展点是一张登记表（名称、分类、适用版本、权限等级）加一处实现；注册、发现、文档和测试都读这张表。

3 代码规范

要点语言无关的写法规则；具体工具见语言附录。格式交给工具，评审不争论格式。

本节对任何语言有效；各语言的具体做法见语言附录 L1、L2、L3。

  • SHOULDCODE-01遵循语言的官方命名与风格约定；格式由格式化工具统一，不在评审中争论格式。
  • SHOULDCODE-02一个文件一个公开类型或模块，文件名等于类型名；目录与命名空间或包一致。
  • MUSTCODE-04新代码启用最严格的类型检查（C# 可空引用类型、TypeScript strict、mypy/pyright strict）。空引用和类型错误是最常见的运行时缺陷。
  • MUSTCODE-05异步：界面线程和请求线程上不同步阻塞等待；取消信号一路传下去；不发出无人处理错误的“即发即弃”任务。阻塞等待会造成死锁和界面冻结。
  • MUSTCODE-06机器数据的解析与格式化与区域无关；字符串比较显式指定语义（序数或区域）；读写文本显式指定编码。区域设置不同会让同一数据解析出不同结果。
  • MUSTCODE-07解析外部数据用安全默认值：XML 禁止 DTD 和外部实体；不对外部数据使用不安全的反序列化（BinaryFormatter、pickle）；schema 不加载远程引用。防止 XXE 和不安全反序列化漏洞。
  • SHOULDCODE-08错误用具体类型，保留原因（内层异常、raise from、cause）；不抛出通用基类或字符串。
  • MUST NOTCODE-10可变的全局或静态状态；进程级设置只在启动时设置一次。全局可变状态让测试互相干扰并引发并发错误。
  • SHOULDCODE-14构建、生成与发布自动化用项目主语言写在 build-tools/，一个入口；不新增零散的 shell、PowerShell、batch 脚本。

4 代码质量

要点小函数、单一职责、一个功能一个实现。数值是评审触发线，不是硬门禁；注释解释原因。

4.1 规模与复杂度

数值是评审触发线：超过时拆分，或在 PR 中写一行理由（例如“厂商要求的固定调用序列”）。

度量建议上限超过时
方法或函数约 40–60 行提取命名清楚的函数
文件约 400–600 行，一个类型按职责拆类型，不靠 partial 变小
圈复杂度约 10–15表驱动、提前返回
嵌套深度3提前返回、提取函数
参数约 5 个参数对象
  • SHOULDQ-01新代码和改动的代码遵守上表；分析器的复杂度规则作提示，不机械拆分。

4.2 重复、死代码、杂物类型

  • MUSTQ-03同一判断、转换或业务规则（约 5 行以上）出现第二次时合并为一个共享组件。目标版本间的 API 差异不算重复。重复逻辑改一处漏一处。
  • SHOULD NOTQ-04死代码、注释掉的代码。
  • SHOULD NOTQ-05上帝类和杂物类型（Helpers、Utils、Manager、Common）；静态类只放无状态算法，名称说明用途。

4.3 设计

  • SHOULDQ-08逻辑写成不可变数据加纯函数；副作用集中在应用层和适配层。
  • SHOULDQ-09依赖经构造函数注入；不用服务定位器和静态单例。
  • SHOULDQ-10名称说明“是什么”，不说明“怎么做”（PendingApprovals，不是 DictionaryWrapperList）；布尔用肯定式。

4.4 注释规范

  • SHOULDCMT-01代码中的注释用英文；给用户看的文字走资源文件，不写在注释或字面量里。只有项目在自己的代理说明中明确决定时，才允许中文注释。
  • SHOULDCMT-02注释写代码说不出来的“为什么”：不显而易见的决定；厂商 API 的怪癖和版本差异（附文档或记录出处）；不变量；单位和范围；线程或单元要求；某个检查为什么存在（安全原因）；绕过办法（附 Issue 或 ADR 链接）。
  • SHOULD NOTCMT-03复述代码；保留注释掉的代码；在注释中记修改历史（那属于 Git）；装饰性横幅；作者或日期文件头（只在许可证要求时加许可证头）。
  • MUSTCMT-04与代码不符的注释是缺陷，在同一个改动中修正或删除。过期注释误导后来的修改者。
  • SHOULDCMT-05M+公开类型和成员有文档注释（C# XML 文档注释、TS 的 TSDoc、Python docstring）：摘要、参数、返回值、异常、线程安全性。由代码生成的对外描述（OpenAPI、工具描述、schema）取自同一来源。
  • SHOULDCMT-06TODO/FIXME 必须带负责人或 Issue 编号和原因，如 // TODO(#123): remove after v2 migration；发布涉及的代码路径中不留未关闭的 TODO，由检查列出。
  • SHOULDCMT-07密度与周围代码一致；优先用清楚的名称和小函数代替注释。测试的行为写在测试名里，只为不显而易见的夹具原因加注释。

推荐：说明原因与出处

// The vendor API returns success but drops the value when the
// object is locked by another user (vendor doc 4.2, issue #212),
// so verify by reading it back before committing.
var actual = adapter.ReadValue(path);

避免：复述、历史、无主 TODO

# read the value
value = adapter.read_value(path)  # changed by Li 2026-03-01
# TODO fix later

执行C# 开启 GenerateDocumentationFile 并把 CS1591 设为公开表面上的错误；TS 用 ESLint 的 jsdoc 规则，Python 用 Ruff 的 D 规则；仓库检查列出不带编号的 TODO；过期注释靠评审。

4.5 静态分析

  • MUSTQ-15启用语言的标准分析器和格式化工具，配置入库；新代码零新增警告：新项目警告即错误，老项目的存量记在只减不增的基线中。警告一旦堆积就没人再看，新问题被淹没。

4.6 测试质量

  • SHOULDQ-13测试名说明行为（WriteSetpoint_OutOfRange_IsRejectedBeforeSend）；一个测试一个失败理由；测试中不写分支和循环。

4.7 重构

  • SHOULDQ-16童子军规则只在本次改动触及的范围内执行。
  • MUSTQ-17重构单独成批、单独提交，不与行为变化混合；行为不变由对等测试证明。混在一起的重构与行为变化无法评审，也难以回退。
  • SHOULD NOTQ-18一次性重写；新旧路径并存，对等测试通过后再删旧路径。

5 错误处理与健壮性

要点错误按证据分类、消息可执行。写入后结果不明就停下交给人，绝不自动重放，这样才不会重复写入。

5.1 错误分类

每个对外报告的失败落在下表的一类中。分类决定能否重试、要不要锁定、给用户什么提示。

类别含义目标状态调用方可否重试
输入无效类型、范围、格式、未知字段未改变改正输入后可以
前提不满足未连接、未绑定、对象被锁、需要离线未改变满足前提后可以
不存在、不唯一对象找不到或有多个候选未改变按候选改正后可以
不支持当前目标版本或设备不提供该能力未改变不可以
确认被拒绝或超时人拒绝、超时、确认渠道不可用未改变只能由人重新发起
目标报告失败厂商 API 或设备明确返回失败已回滚或确认未变按提示
部分完成有确定的成功项和失败项部分改变，已逐项说明只处理失败项
结果未知写入已发出，结果无法确认未知不可以（5.3）
内部错误本项目的缺陷按发生阶段说明不可以；附诊断编号
  • MUSTERR-01结果按证据分类，不按异常文本猜测。写入调用发出后的未分类失败一律归为“结果未知”，不报告为干净失败。按异常文本猜结果会把未知的写入报成失败，引发重试。
  • SHOULDERR-02错误消息说明发生了什么、已知原因和下一步怎么做；不含堆栈、本机路径、内部类型名和凭据。
  • SHOULDERR-03先检查权限，再检查对象是否存在，避免错误信息泄露不该看到的对象。

5.2 不吞异常

  • MUSTERR-04只捕获能处理的具体异常。catch (Exception) 只允许在边界：工具或命令入口、进程入口、界面命令、调度回调、清理与收尾。宽泛捕获会掩盖缺陷。
  • SHOULDERR-05每个吞掉异常的 catch 在 catch 行或块首标注 /* swallow(<类别>): <原因> */，类别取自闭集（cleanup、teardown、logging-failure、probe-optional、parse-fallback、ui、privacy 等），并由仓库检查计数，计数只减不增。
  • MUSTERR-06后台线程、调度到外部主线程的委托、插件生命周期方法内部捕获全部异常，把失败作为结果交回。未处理的异常会结束宿主进程（包括目标软件的进程）。未处理的异常会结束宿主进程，包括目标软件。

5.3 结果未知

  • MUSTERR-07写入、传输或通道在写入发出后中断时，先尝试取回结果（同一请求号查询，目标侧按请求号去重）；取不回时报告“结果未知”。先取回结果，避免把已经成功的写入当作失败。
  • MUSTERR-08结果未知后锁定受影响的范围（会话、项目或设备），锁定持久化；只有人检查目标的实际状态后经确认渠道解除，没有自动化接口能解锁。锁定防止在状态不明时继续写入。
  • MUST NOTERR-10宿主、客户端、批处理或重试策略自动重放结果未知的写入。重新预览也不等于获准再次写入。重放会造成重复写入或设备重复动作。

5.4 资源清理

  • SHOULDERR-12临时文件和目录每次运行新建（随机后缀），只删除本次运行创建的内容；删除前核对路径仍在预期根目录下且不是重解析点。
  • SHOULDERR-13断开或退出时不隐式改变外部系统的状态（保存、关闭、复位、停机）；需要时作为显式操作提供。

5.5 超时与等待

  • MUSTERR-14每个跨边界调用有超时：按操作类别设预算（例如普通调用、首次连接、编译或导入这类长操作），预算集中定义、可经配置覆盖，并写在用户文档中。没有超时的调用会让会话永久挂起。
  • SHOULDERR-16派发前的取消返回“已取消”；派发后不能中止外部调用时，等待真实结果，不假装已取消。

5.6 进程生命周期

  • MUSTERR-18启动时校验配置和必需文件，有错就以明确的退出码和消息退出（fail fast），不在半配置状态下运行。半配置运行会产生错误结果。
  • SHOULDERR-20M+需要独占某个目标实例时用租约文件（所有者 PID、启动时间、状态），租约状态为忙碌或不确定时拒绝竞争者；不靠删除租约文件绕过。
  • MUSTERR-21状态文件原子写入（写临时文件后替换，9.2）；审计写不进去时拒绝写入目标，读取照常。半写的状态文件会让程序无法启动；没有审计的写入无法追查。

6 安全

要点威胁集中在审批绕过、路径穿越、XXE、命令注入、本机认证、密钥泄露和提示注入。安全流程按等级取舍。

6.1 范围与信任边界

  • SHOULDSEC-01M+威胁模型文档：资产、信任边界、STRIDE 威胁、措施及其测试、已知缺口，并写明前提与范围外的情况（例如“同一 Windows 用户”是信任边界）。

6.2 确认与审批不可绕过

  • MUSTSEC-03需要人确认的操作，确认只来自人独立操作的界面（工作台窗口、目标软件内的对话框、操作员终端）；调用方的参数、元数据、批处理或客户端自己显示的表单都不能代替。客户端能自己批准写入就等于没有审批。
  • MUSTSEC-04确认请求号由服务端生成；决定绑定请求号、计划指纹和去敏后的参数摘要，只能使用一次；迟到、重复、不匹配或格式错误的决定一律按拒绝处理。防止伪造、重放或张冠李戴的审批决定。
  • MUSTSEC-05确认开关、可写范围等安全配置只能由人在配置文件或“仅人可改”的设置页修改；没有接口或工具能修改它们，也不能写这些文件（包括经短文件名、链接或文件 ID 的写法）。防止自动化或 AI 关掉自己的保护。
  • SHOULDSEC-06确认关闭时，每个执行结果带“确认已关闭”的警告，界面持续显示该状态，开关变化写入审计。

6.3 路径穿越与压缩包

  • MUSTSEC-07外部给出的路径只接受固定根目录之下的相对路径：拒绝绝对路径、UNC、驱动器号、.、..、空段、控制字符、Windows 保留字符和保留设备名（CON、NUL…）；按规范化后的完整路径判断。防止写到预期目录之外。
  • SHOULDSEC-08根目录之下的每一级都不能是符号链接、联接点或其他重解析点；写出后再列出目录，确认文件都在根目录内。
  • SHOULDSEC-09导出和输出写入每次新建的空目录，从不覆盖已有文件，除非调用显式允许覆盖且经确认。
  • MUSTSEC-10压缩包在内存或新建的临时目录中读取：条目名按 SEC-07 校验，名称忽略大小写后唯一，拒绝链接条目；文件数、单文件大小、总大小、压缩比都有上限；不执行包内任何代码。防止压缩炸弹和经压缩包的路径穿越。

6.4 XXE 与解析器

6.5 命令注入

  • MUSTSEC-12启动子进程只用 ProcessStartInfo.ArgumentList 或 stdin 传参，UseShellExecute=false，可执行文件用绝对路径，工作目录为绝对路径；限制超时和输出大小。防止命令注入。
  • SHOULDSEC-13需要执行外部命令、脚本或宏时，只执行随产品发布的白名单条目；参数逐个校验类型、枚举、范围、长度和字符集，拒绝引号和控制字符；没有工具、配置或数据文件能增改白名单。

6.6 本机管道与 HTTP

  • MUSTSEC-14命名管道：名称由当前用户 SID 和安装路径派生；受保护的 DACL 只授予当前用户；拒绝远程客户端；双方核对对方 SID，需要时核对对方映像路径；帧有大小上限，未知字段和重复字段拒绝。防止同机其他用户或进程冒充对端。
  • SHOULDSEC-15HTTP 默认只监听 127.0.0.1；局域网访问只绑定人选择的具体 IP，防火墙只放行指定来源；明文 HTTP 只在私有网络中使用，作为剩余风险写入威胁模型。
  • MUSTSEC-16HTTP 认证：每个请求带 Authorization: Bearer，密钥至少 24 字节随机数，定长比较；失败只回 401，同一来源连续失败后限流；健康检查端点只返回版本等非敏感信息。防止未认证的网络访问。
  • MUSTSEC-17校验 Origin 头（不在允许列表中回 403，允许列表默认空）和 Host 头，防 DNS 重绑定。防止 DNS 重绑定攻击本机服务。

6.7 密钥与凭据

  • MUSTSEC-19密钥和凭据只存在受保护的用户存储中（DPAPI CurrentUser 或 Windows 凭据管理器），不写入明文配置、命令行参数（会进入进程列表）或日志。明文密钥会经配置、进程列表或日志泄露。
  • MUSTSEC-20去敏规则统一一处实现：键名含 password、passwd、secret、token、credential、authorization，或以 key 结尾（明确的白名单除外）的值替换为固定占位符；自由文本中的 Bearer/Basic 令牌、name=value 形式的密钥、URL 用户信息、PEM 私钥清除。审批摘要、哈希、审计和日志都在去敏后计算。防止凭据进入日志、摘要和响应。
  • SHOULDSEC-21新增带凭据的参数时，命名符合 SEC-20 的规则，并加测试证明值不进入确认摘要、审计、日志和响应。
  • MUST NOTSEC-22在仓库、文档、夹具、截图、Issue 中出现真实凭据、机器地址、客户项目或许可证信息。提交过的密钥只能轮换，无法真正撤回。

6.8 经项目数据的提示注入

  • MUSTSEC-23来自用户项目或设备的自由文本（注释、属性值、标签名、导入文件内容）只作为数据返回，放在数据字段中，不拼进给模型的说明或摘要。防止项目数据中的文字被模型当成指令执行。
  • SHOULDSEC-24这类文本剥除控制字符（保留换行和制表符）和双向文本控制符（U+202A–202E、U+2066–2069），超长时截断并注明原始长度。

6.9 最小权限

  • SHOULDSEC-26产品以普通用户权限运行和安装；只有确实需要的步骤（防火墙规则、URL ACL、加入厂商要求的用户组）单独提权，并向人说明原因。
  • SHOULDSEC-27CI 工作流令牌默认只读（contents: read），需要写权限的作业单独授予。

6.10 安全开发流程（SDL-lite）

  • SHOULDSEC-28M+威胁建模（只对跨越信任边界的功能）：新功能或新接口（新端点、新管道、新文件入口、新设备写入路径）在设计说明（18.3）中附一段简短威胁模型：画出信任边界，对每个边界按 STRIDE 列出威胁和措施；更新项目的威胁模型文档。
  • SHOULDSEC-29安全静态分析：启用 .NET 安全相关规则（CA2100、CA2300–CA2330、CA3001–CA3012、CA3075、CA3077、CA5350–CA5403 等）为警告；新增违规阻止合并。
  • SHOULDSEC-30M+依赖漏洞扫描：每次合并和每周运行 dotnet list package --vulnerable --include-transitive（或等效工具）；高危漏洞阻止发布。更新政策：高危 7 天内升级或给出缓解，中危下一个次版本处理，其余随常规更新。
  • SHOULDSEC-31密钥扫描：仓库启用密钥扫描（托管平台的 secret scanning 或提交前钩子）；发现泄露立即轮换，再从历史中清除。
  • SHOULDSEC-32M+发布前安全复核：对照威胁模型核对本版新增的边界和措施、去敏测试、依赖扫描结果；结论写入发布记录。
  • SHOULDSEC-33L或网络暴露：网络暴露模式（HTTP 等）在首次发布和每次改动认证、绑定或路由时做滥用测试：无密钥、错误密钥、暴力尝试、错误 Origin/Host、超大请求、畸形帧、跨会话访问句柄。
  • SHOULDSEC-34M+漏洞受理：仓库有 SECURITY.md（报告渠道、受理范围、响应时限）；收到报告 3 个工作日内确认并分级，高危 30 天内修复或发布缓解，修复后发布安全公告并在 CHANGELOG 中注明；事件处理按 13.1 的 S1 流程。

7 用户数据与隐私

要点未经确认不改用户数据；覆盖前备份；没有同意，数据不离开这台电脑。
  • MUSTDAT-02覆盖或删除用户数据前备份：复制到新建的带时间戳的目录，核对副本（大小、哈希或对象数），备份失败就不执行；备份路径写入结果和审计；备份不自动删除。覆盖或删除后无法恢复用户数据。
  • MUSTDAT-03修改用户的配置文件（例如 AI 客户端配置）前，先展示将写入的内容和备份位置，备份原文件后再写入。防止用户的配置被覆盖丢失。
  • SHOULDDAT-05每类本地数据有保留规则并写在用户文档中：运行日志按份数或天数轮转；导出句柄、临时文件有过期时间；审计和备份不自动删除，由人清理。
  • MUSTDAT-06没有人的明确同意，任何数据都不离开这台电脑：不自动上传日志、崩溃转储或使用统计（第 22 节）。检查更新只发送版本请求，不发送用户数据。未经同意外传数据违反用户信任和法规。
  • MUST NOTDAT-07把真实客户项目、个人数据、许可证文件或未脱敏的现场日志放进仓库、测试夹具、Issue 或发布物。防止客户资料经仓库或附件泄露。

8 配置与环境

要点命令行 > 环境变量 > 用户配置 > 默认值；默认值安全；产品和代理都不改系统设置。
  • SHOULDCFG-01优先级从高到低：命令行参数 > 环境变量 > 用户配置文件 > 内置默认值。每个设置的生效来源可在自检命令中查看。
  • MUSTCFG-03默认值安全并写在文档中：确认默认开启，网络监听默认只在本机，可写范围默认最小，危险功能默认关闭。设置缺失或无效时按安全的一侧处理（例如审批设置文件损坏时视为开启）。默认开放的危险功能会在用户不知情时生效。
  • SHOULDCFG-04数据目录按用户：优先显式指定的目录，其次安装目录下可写的 data，否则 %LOCALAPPDATA%\<Product>；显式指定的目录无效时立即报错，不静默回退。
  • MUST NOTCFG-06产品或 AI 代理修改机器级或系统设置：PATH 与全局环境变量、其他软件的注册表键、系统服务、安全策略、杀毒排除项。确需变更时给出命令和理由，由人执行。改系统设置会破坏用户机器，例如过长的 PATH 会让登录时环境变量加载失败。

9 Windows 平台

要点长路径、文件锁、杀毒软件、编码和进程管理是 Windows 上最常见的故障来源；照做可以省掉大部分排查时间。

只对在 Windows 上运行或构建的项目。规则来自真实项目中反复出现的故障。

9.1 长路径与路径规范化

  • SHOULDWIN-01假设 LongPathsEnabled=0：安装根、数据根、构建输出和临时目录的深度保持很小；产品内部固定子路径预留余量。路径超过 260 字符时立即以明确的错误失败，不产生半截文件。

9.2 文件锁与原子替换

  • SHOULDWIN-06遇到共享冲突（被其他进程打开）时有界重试并报告占用者能识别的信息；升级时不强制结束正在写入的进程。

9.3 杀毒软件干扰

  • SHOULDWIN-07假设杀毒软件会短暂锁定刚写入的可执行文件和压缩包：替换、删除、加载新文件时有界重试；构建与测试不依赖“写完立刻能执行”。

9.4 编码与区域

  • SHOULDWIN-10读写文件和管道显式指定编码；不依赖控制台代码页。子进程的输出按约定的 UTF-8 读取；必须读取旧程序输出时，按其实际代码页（例如 cp936、cp1252）显式解码。

9.5 换行策略

  • SHOULDWIN-12仓库设置 core.autocrlf=false，换行由 .gitattributes（* text=auto eol=lf）决定；需要 BOM 或 CRLF 的文件逐项声明。

9.6 进程树与作业对象

  • MUSTWIN-13产品启动的子进程放进作业对象，设置 JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE；需要比宿主活得久的进程（例如用户的目标软件实例）显式脱离作业。孤儿子进程会占住目标实例和文件。
  • MUST NOTWIN-14按进程名、窗口标题或模式匹配结束进程。只结束自己启动的进程：记录 PID 和启动时间，结束前核对可执行文件路径。按名称结束进程会关掉用户的其他程序。
  • MUSTWIN-15测试夹具和辅助进程关闭 Windows 错误报告对话框：SetErrorMode(SEM_FAILCRITICALERRORS | SEM_NOGPFAULTERRORBOX)，并注册未处理异常处理程序，把异常写入 stderr 后以约定的非零退出码退出，不弹出 WER 对话框阻塞无人值守运行。WER 对话框会让无人值守的运行一直挂起。

10 国际化与本地化

要点文字进资源，时间存 UTC，机器数据与区域无关，一个概念一个术语。
  • SHOULDI18N-01界面文字全部放在资源文件中（.resx 或等效），代码和 XAML 中不写给人看的字面文字。默认提供 zh-CN 与 en-US，跟随系统语言，可在设置中切换并即时生效。
  • SHOULDI18N-02项目维护一份术语表（从附录术语表开始扩展），界面、文档和资源共用。例如：面向用户时统一写“服务”而不是“引擎”，目标软件中的工程统一写“项目”而不是“工程”。
  • MUSTI18N-03持久化、线上和日志中的时间戳为 UTC，格式 ISO 8601 / RFC 3339（例如 2026-11-02T08:30:00.0000000Z）；给人看时转为本地时间并按界面语言格式化。混用本地时间会在时区和夏令时切换时出错。
  • SHOULDI18N-05布局不为某种语言写死尺寸：承载文字的容器不用固定高度和宽度，允许换行和增高；按英文比中文长约 30–50% 预留空间，在两种语言下检查。
  • SHOULDI18N-06技术标识（工具名、错误码、路径、哈希、请求号、块名、标签名）原样显示，不翻译，用等宽字体。
  • SHOULDI18N-07多语言的项目数据返回时注明语言代码（如 zh_CN），不静默只取一种语言；未设置与空字符串区分。

11 性能

要点只在关键路径上优化并给出前后计时；批量调用，源头分页。
  • SHOULDPERF-01只优化关键路径（对目标软件或设备的调用、周期采集、界面线程、请求热路径），并在 PR 中给出同一台机器上改动前后的计时。
  • SHOULDPERF-02对目标和设备的调用成批进行：API 允许时一批一次调用，避免跨进程的 N+1 调用。
  • SHOULDPERF-03大列表在源头分页和过滤；结果有大小预算，超出时分页或给出句柄。
  • SHOULDPERF-04缓存只存不可变或限定快照的数据，键包含版本或绑定标识，写入时失效；不跨请求缓存厂商对象。

12.3 规则

  • MUSTTST-01每个功能有主要行为的测试和 12.2 列出的相关失败路径测试；不写证明不了主要功能的防御性测试。没有主要行为测试，回归会直接到用户手里。

  • MUSTTST-06默认测试不连接网络、真实目标或设备；可以在 127.0.0.1 上启动自己的夹具和模拟器。依赖网络和设备的测试不稳定。
  • SHOULDTST-07夹具使用真实格式的脱敏数据。
  • MUSTTST-08快照和 golden 文件只由正式工具重新生成，差异逐项说明；从不自动接受。自动接受快照会把回归写进基线。
  • SHOULDTST-09M+每个测试套件登记最少通过数和最多跳过数，防止“过滤写错、一个没跑也算通过”；下限只升不降。
  • SHOULDTST-10测试互相独立，不依赖执行顺序和共享状态。
  • SHOULDTST-11M+实机验证记入台账：目标版本、日期、项、结果；没跑写 NOT RUN。

13 缺陷处理

要点先归类、再定位、再修；每个修复带一个修复前失败的测试，同一缺陷不会回来。

13.1 分级

级别定义响应
S1损坏用户数据、未经确认写入目标或设备、可能影响人员或设备安全立即用配置停用相关功能，修复，M+ 写不追责的复盘
S2结果错误但没有写入下一个修订版本
S3体验、文字、性能问题常规排期
  • SHOULDBUG-01缺陷当天登记：复现步骤、版本、环境（目标版本、操作系统）、证据。
  • MUSTBUG-02每个修复带一个修复前失败、修复后通过的回归测试；做不到时写明原因（例如只能实机复现）并加入实机核对清单。没有回归测试，同一缺陷会再次出现。
  • SHOULDBUG-03失败先归类再行动：真实缺陷、不稳定测试、环境问题、本分支引入的回归。
  • MUSTBUG-04先定位根因再修；不靠反复重跑和试错。试错修复会引入新缺陷并浪费轮次。
  • MUSTBUG-05不稳定的测试：保留证据，找原因修好；隔离（quarantine）只经维护者批准，带 Issue 和期限；不“重跑到通过”。重跑到通过会掩盖真实的竞态缺陷。
  • SHOULDBUG-06M+S1 复盘写入 docs/postmortems/：时间线、影响、根因、为什么防线没拦住、行动项（落到 Issue）。

14 依赖与许可

要点每个依赖都是长期成本：许可证合规、版本精确锁定、可离线还原，不分发厂商运行库。
  • SHOULDDEP-01新增依赖写明用途、许可证、维护状况和更轻的替代；M+ 运行时依赖由维护者批准。
  • MUSTDEP-02允许的许可证：MIT、Apache-2.0、BSD-2/3-Clause、ISC；MPL-2.0 等弱著佐权需评审；GPL/AGPL 和带使用限制或收费条款的许可证（例如某些断言库、快照库的新版本）不进入发布物，除非有 ADR。许可证冲突会让产品无法合法发布。
  • MUSTDEP-03版本精确锁定：中央版本管理 + 锁文件，CI 以锁定模式还原；传递依赖同样锁定。未锁定的版本让构建不可重现，问题难以复现。
  • SHOULDDEP-04M+构建可以离线还原：本地包源或缓存配置入库，构建过程不临时下载。
  • SHOULDDEP-05原样引入的第三方源码放在 third_party/<name>/，记录上游地址、标签或提交、许可证文件；本地修改逐项列出。
  • MUSTDEP-06发布物带 THIRD-PARTY-NOTICES，列出每个随包组件的许可证文本；保留原始版权声明。派生自他人项目时保留原许可声明，再加自己的。缺少声明违反许可证义务。
  • MUSTDEP-07厂商 SDK 和运行库不提交、不分发，除非许可证明确允许；构建引用本机安装（不复制到输出），运行时从本机安装加载。分发厂商运行库违反许可并造成版本冲突。
  • SHOULDDEP-08提到第三方产品时写全称，需要处注明商标归属，并声明本项目与厂商无隶属关系；不使用厂商标志。

14.1 交付物完整性

要点一个入口命令；检查分层运行，合并门只跑受影响的部分；发布只核对证据和打包。

15.1 验证分层

  • SHOULDBLD-02检查只在各档之间移动或按身份复用，不删除。复用只针对同一机器上输入完全相同的干净通过；计时敏感的检查总是重跑。

15.2 版本与发布

  • SHOULDBLD-06SemVer；预发布写作 X.Y.Z-beta.N 或 X.Y.Z-rc.N，在托管平台标为预发布且不设为最新版。

  • SHOULDBLD-10M+每次合并后做一次发布演练（不上传），让发布本身只剩上传。

16 打包与安装

要点按用户安装、不要管理员；卸载保留数据；包内容由清单决定。
  • SHOULDPKG-01默认按用户安装，不需要管理员：程序在 %LOCALAPPDATA%\Programs\<Product>（或用户选择的目录），数据在 %LOCALAPPDATA%\<Product>；运行时不写程序目录之外的系统位置。
  • MUSTPKG-04卸载撤销注册、删除程序，保留用户数据并说明位置；删除数据是单独的、需要确认的操作。卸载时删除用户数据无法挽回。
  • MUSTPKG-07包内容由一份清单决定，由检查核对；不含开发源码、密钥、厂商 SDK 和测试数据。防止把密钥、开发文件或厂商 SDK 发出去。
  • SHOULDPKG-08M+预发布交给测试者时附：测试清单（按“未验证”清单编号）、反馈模板（Issue 模板，填写清单编号、版本、环境）；反馈先记入反馈台账，复核后再写入真机台账。

17 兼容、升级与迁移

要点同一主版本内只做增量；格式带版本并自动迁移；更新器可回滚。
  • MUSTMIG-01同一主版本内对外契约只做增量（新功能、新可选参数、新字段、新错误码）；消费方容忍未知字段和未知错误码。破坏性变化会让现有客户端失效。
  • MUSTMIG-02破坏性变化（改名、删除、改必填、改含义、改安全属性）升主版本，并在发布说明中附生成的新旧对照表。没有对照表，用户无法迁移。
  • SHOULDMIG-03弃用：在目录和说明中标注替代项与计划移除的版本，调用时给出弃用警告；至少保留一个次版本再移除（公开 API M+ 保留一个主版本）。
  • MUSTMIG-04配置和数据格式带版本号；启动时把旧版本迁移到当前版本，迁移前备份原文件；遇到更新的格式拒绝并提示升级，不静默丢弃未知设置。升级后配置丢失或程序无法启动。
  • MUSTMIG-05M+更新器：核对哈希和版本号，暂存后原子替换，保留上一版本用于回滚；失败自动回滚；不动用户数据；正式安装不收预发布，除非用户选择。坏的更新无法回退会让用户停工。
  • SHOULDMIG-06M+维护目标版本支持矩阵：已验证、已构建未验证、不支持；写入发布说明。
  • SHOULDMIG-07实验性或隐藏开关登记在一张表中：用途、默认值（关）、负责人、移除期限；到期删除。

18.4 Git

  • SHOULDGIT-01只有一条长期分支（主干）。任务分支短命，评审并通过合并门后变基到主干，快进或压缩合并，合并后删除。

目的：在合并前发现缺陷，让下一个读代码的人（或下一个代理会话）能读懂，并让团队了解改动。评审不是风格之争，格式交给工具。

  • 改动只做一件事，规模在 GIT-06 以内；重构与行为变化分开。
  • 本机构建通过，零新增警告，受影响的测试和合并门已运行。

20 文档

21 界面设计

要点人始终掌控，风险越高摩擦越大。只用 token；每对前景与背景满足 WCAG 2.2 AA；写入审批等权重、回车不批准。

本章对所有带界面的项目有效。桌面工具的参考 token 集是已采纳的 EplanMcp Workbench 设计规范（Apple HIG 风格，Windows 优先）；Web 与移动另按领域 E、F 的平台规范；工业操作画面另加领域 B 的 HMI 规则。下面的尺寸和交互是默认值；项目的取舍（行高、确认方式、页面数等）记在自己的 ADR 中。

21.1 原则

  1. 人始终掌控：自动化和 AI 只能请求，执行由人决定；超时按拒绝处理。
  2. 清晰优先：一屏回答一个问题；颜色只表达状态和风险，不做装饰。
  3. 克制：界面退后，数据（对象名、路径、变更）走到前面；用留白和分组建层级，少用线和阴影。
  4. 风险越高，摩擦越大：只读不打扰；写入一次点击但回车不批准；破坏性先确认，默认是取消。
  5. 永远说清状态：连接、暂停、超时、结果在发生的位置即时可见，不靠弹窗。

21.10 本地化、文案与动效

  • SHOULDUI-29文案：短句、主动语态、动词开头；标题说清要发生什么（“在项目 Demo 中放置 2 个设备”）；错误说发生了什么、原因、怎么办，不责备用户，不用感叹号；技术标识原样用等宽。
  • SHOULDUI-31动效克制，只表达状态变化；系统开启“减少动态效果”时滑入改为淡入；不闪烁，状态快速多次变化时合并显示。

21.11 AI 或自动化驱动界面（适用时）

  • MUSTUI-32AI 只能打开白名单中的页面，从不包括审批页和设置页；审批或设置为当前页、有模态界面、最近 1.5 秒内有人的输入、或页面正在执行命令时拒绝 AI 的显示和预填。防止 AI 把人引到审批或设置上。
  • SHOULDUI-34预填的字段旁有可见标记“AI 预填，待确认”和可用键盘的“清除预填”，状态也暴露给读屏；AI 操作界面后显示“AI 操作了界面 · 工具 · 客户端 · n 秒前”。

21.12 界面测试

  • SHOULDUI-36M+渲染测试覆盖 1024 × 640 与 1366 × 860、中英文、浅色/深色/高对比；自动化树测试检查名称和焦点顺序。
  • SHOULDUI-37设计值断言（尺寸、字号、token 值）随批准的设计变更更新；行为、键盘、无障碍、审批类断言不放宽（G-06）。

21.13 界面评审清单

  • 只用 token；没有字面颜色和字号；新 token 已加入设计系统。
  • 页面类型（列表 + 详情、表格、分组列表）符合 21.3；每类功能一个入口。
  • 七种状态齐全；加载、空、错误三种状态分开。
  • 每个决策区最多一个默认按钮；写入审批等权重、回车不批准；破坏性走确认面板。
  • 键盘可完成全部操作；焦点可见；访问键无冲突；自动化名称完整。
  • 对比度矩阵通过；高对比下有描边、无阴影、状态靠形状和文字。
  • 中英文、1024 × 640、200% 缩放下不截断。
  • 文案用动词、说清后果；错误说明怎么办。

22 诊断与支持

要点离线现场没有遥测：靠用户导出的去敏诊断包和诊断编号做支持。

产品常在离线的现场运行，所以默认没有自动数据收集，支持靠用户导出的诊断信息。

  • MUSTDIAG-01不做自动遥测。确需遥测时只能选择加入（opt-in），附公开的数据清单和关闭开关。未经同意收集数据违反用户信任和法规。
  • SHOULDDIAG-02M+提供用户导出的诊断包：日志、版本、生效配置及其来源、环境检查结果、最近错误；导出前去敏（ARC-17），用户可以先预览内容；只保存在本机。
  • SHOULDDIAG-03M+界面提供“复制诊断信息”：产品版本、操作系统、目标版本、最近一次错误的诊断编号。
  • MUSTDIAG-04未处理异常写日志并给出诊断编号；崩溃转储只在用户启用后保存在本机，按敏感数据处理，从不自动上传。崩溃转储可能含有内存中的凭据和项目数据。
  • SHOULDDIAG-05提供只读自检命令（如 doctor），可输出 JSON。
  • SHOULDDIAG-06M+问题模板要求附诊断编号和诊断包；收到后按 13.1 分级。

23 完成定义

要点任务、合并、发布各有一张完成清单；没过清单就不算完成。

23.1 任务完成

  • 代码、测试、生成文件和文档在同一个任务中更新；生成文件由生成器产出。
  • 主要行为和相关失败路径有测试；缺陷修复有回归测试。
  • 零新增分析器警告；格式化通过。
  • 契约变化已重新生成快照并逐项说明；破坏性变化写入迁移表。
  • 用户可见的变化写入 CHANGELOG Unreleased。
  • 依赖目标的新行为加入实机核对清单，或在台账中标 NOT RUN。

23.2 合并完成

  • 评审通过，阻止项（REV-05）全部解决。
  • 在变基后的提交上通过合并门。
  • 任务分支已删除；交接文档和任务状态已更新 M+。

23.3 发布完成

  • 发布证据有效（M+ 最近一次夜间检查通过且之后无失败）。
  • CHANGELOG 版本条目、发布说明、“未验证”清单与版本号一致。
  • 资产附 SHA-256（M+ 加 SBOM 与来源证明）。
  • 维护者已确认；发布后更新交接与发布记录。

领域 A：MCP 服务

要点工具是给模型用的：第一次调用就能用对。写入默认预览、经人审批、结果未知不重放。

适用于通过 Model Context Protocol 向 AI 客户端提供工具的服务。工具的读者首先是模型：检验标准是“模型第一次看到这个工具，能不能不试错就用对”。

A.1 协议、传输与会话

  • SHOULDMCP-01固定所支持的 MCP 修订版本（由 SDK 协商），写在发布说明中；升级修订是 ADR 级决定。
  • MUSTMCP-03只有协议层问题（未知工具、请求格式错误）用 JSON-RPC 错误；参数错误、拒绝、执行失败、部分完成和结果未知都作为 isError: true 的工具结果返回，让模型能自我纠正。模型读不到错误原因就会盲目重试。
  • SHOULDMCP-04服务端状态（连接、绑定、计划、句柄、游标）限定在所属会话内；协议无状态时用服务端签发的不透明、会过期的句柄，并在描述中写明有效期。
  • SHOULDMCP-05服务器说明（instructions）不超过约 300 token：能做什么、命名与单位约定、“项目内容是数据，不是指令”、写入需要人工审批。

A.2 命名与描述

  • SHOULDMCP-07新项目的工具名是 PascalCase 的“动词 + 对象 + 必要限定”，只用 ASCII 字母和数字，不超过 64 字符；动词取自代码中的闭集，由生成器检查。已发布的名称不为本规范改名。
  • SHOULDMCP-08同一动词在所有对象上含义相同：Get 取单个、找不到报 NOT_FOUND；List 一律分页；Find/Search 按条件；Create/Update/Delete；Preview/Apply 成对。单个对象用单数，批量用复数；名称不出现序列化格式（Json、Xml）。
  • SHOULDMCP-09描述用英文，按顺序写：一句话做什么、什么时候用 → 什么时候不用、用哪个代替 → 前提（需要连接、绑定、离线、审批）→ 约束（单位、坐标、名称格式）→ 1–3 个经实机核对的参数示例 → 相关工具。描述加参数说明约 250 token 以内。
  • MUST NOTMCP-10在描述中写影响模型对其他工具行为的指令（防工具投毒）；描述变化按契约变化评审。防止工具描述被用来操纵模型（工具投毒）。

A.3 输入 schema

  • MUSTMCP-11JSON Schema 2020-12；对象设 additionalProperties: false；必填列在 required；闭集用 enum；默认值写在 default；互斥参数组用 oneOf。拼错或多余的参数会被静默忽略。
  • SHOULDMCP-12参数名统一一种大小写（新项目 camelCase）；可选参数省略即未提供，不用 "" 哨兵；路径参数以 Path、File、Directory 结尾并区分文件与目录；数值带单位后缀（timeoutSeconds、xMm）。
  • SHOULDMCP-13同一概念在所有工具中同名同形；对象用业务名称标识，句柄必须不透明、会过期；哈希为 64 位小写十六进制。
  • SHOULDMCP-14写入工具显式要求目标身份（例如 expectedProject），不默认“当前对象”；列表工具提供 limit（有默认值和上限）和最常用的过滤条件。
  • SHOULDMCP-15参数错误一次列出全部问题，每项用 JSON 指针指出参数，枚举错误给出允许值。

A.5 错误

  • SHOULDMCP-19错误码是 UPPER_SNAKE 闭集，覆盖参数无效、前提不满足、不存在、不支持、需要审批、计划过期、身份不符、需要重置会话、原生失败、部分失败、结果未知、取消、超时、内部错误；details 按错误码定型。
  • SHOULDMCP-20message 是稳定的英文句子，告诉模型下一步做什么（“Call ListPages to see the pages.”）；不含堆栈、本机路径、内部类型名。
  • SHOULDMCP-21厂商调用失败时返回去敏后的原生消息首行、原生异常类型或错误码（放在 innererror），以及关联服务器日志的 diagnosticId；堆栈只进日志。

A.6 写入：分类、预览、审批、执行

  • MUSTMCP-22每个工具显式登记分类（只读、写入、破坏性、在线写入等）和四个注解 readOnlyHint、destructiveHint、idempotentHint、openWorldHint，按最有副作用的动作与参数组合取值；带 dryRun 的工具 readOnlyHint 为 false；只操作本机目标时 openWorldHint 为 false。注解只是提示，安全不依赖它。注解缺省时客户端会把写入工具当作只读。
  • MUSTMCP-23写入工具默认预览（dryRun: true）；预览不写目标、文件或设备，不等待审批，返回变更清单和计划哈希。预览路径写入会绕过审批。
  • SHOULDMCP-24执行前先用相同参数在只读范围内跑一次预览：预览拒绝就直接返回；预览显示无变化就返回预览结果，不请求审批。
  • MUSTMCP-25审批在人独立操作的界面中进行（SEC-03、SEC-04），不用 MCP elicitation（表单由客户端自己显示、自己回答，证明不了有人确认）；拒绝、超时、审批界面不可用都返回 CONFIRMATION_REQUIRED。客户端自己显示、自己回答的表单证明不了有人确认。
  • MUSTMCP-26批准后在串行通道内复核：会话锁、参数摘要、目标身份、计划哈希（expectedPlanHash）；不一致返回 PLAN_STALE 或 IDENTITY_MISMATCH。计划只执行一次。批准之后目标或参数可能已变化。

A.7 大结果

  • SHOULDMCP-29结果有大小预算（两个内容块都计入，硬上限低于主流客户端的工具输出上限，例如约 20k token）；超出时分页、截断并给出提示，或返回导出句柄。
  • SHOULDMCP-30分页信息放在 meta.paging；客户端用返回的 nextOffset/nextCursor 继续，不自行计算；游标不透明，限定在会话、绑定、查询和快照内。
  • SHOULDMCP-31导出句柄带 id、mediaType、byteLength、sha256、expiresUtc，只在签发它的会话中可读，存储有数量和总量上限；错误结果从不寄存。

A.8 目录、档位与批处理

  • MUSTMCP-33只在厂商 API 支持的版本上注册工具：至少一个动作在该版本有 API 证据才注册；不支持的动作在调用目标前返回 UNSUPPORTED_CAPABILITY。各版本的工具数量由生成目录给出（领域 C）。模型会调用该版本上不存在的能力。
  • SHOULDMCP-34先考虑给现有工具加可选参数或动作，再考虑新工具；M+ 提供不超过约 25 个工具的精简档（core/lite），完整目录经 FindTools/CallTool 一类的桥接访问。
  • SHOULDMCP-35批处理准入由每个工具的显式标志决定（只读批、预览批），不按分类推断；一批最多约 50 项，按顺序执行，遇失败停止，其余标为未执行；预览批签发一次性、限时的令牌，应用时复核全部预览；不承诺回滚。
  • SHOULDMCP-36收到进度令牌时，在排队、等待审批和长操作期间按固定间隔发送单调递增的进度；客户端支持时，长任务改用 tasks 扩展。

A.9 契约、示例与评测

  • SHOULDMCP-37工具契约 = 名称、描述、输入输出 schema、注解、服务器说明；全部进入快照测试，差异逐项评审；破坏性变化按第 17 节。
  • SHOULDMCP-38示例、参数来源、结果解释只在一处源数据中维护，生成到用法元工具（例如 GetToolUsage）和文档；每个工具和动作至少一条示例，参数经实机核对；示例写明验证范围（例如“离线预览，原生执行 NOT RUN”）。
  • SHOULDMCP-39测试检查：示例符合输入 schema；描述和示例只提到已注册的工具；面向模型的文本不含中日韩字符（项目数据除外）。
  • SHOULDMCP-41M+维护 Agent 评测任务集（程序化验证，不看模型自述；分开发集与保留集）；发布前和描述改动后运行，成功率不得下降。

领域 B：上位机（工业监控与操作软件）

要点软件不做安全功能；通信隔离在适配器后；数据带质量和时间戳；报警与画面按 ISA-18.2、ISA-101。

适用于与 PLC、仪表、驱动通信，供操作员监视、操作、记录的软件。等级标记照常适用；7×24 运行的产线系统通常是 L。

B.1 安全功能边界

  • MUSTIND-01软件不执行任何安全功能。人员与设备安全由按 IEC 61508、IEC 62061 或 ISO 13849 设计的安全 PLC 和硬接线联锁承担。软件故障不能危及人员与设备。
  • MUST NOTIND-02软件能绕过、屏蔽或改写安全联锁：不写安全程序区和安全数据块，不强制（force）安全相关信号，不提供“旁路”按钮。绕过联锁可能造成人身伤害和设备损坏。
  • MUSTIND-03每条写入路径定义通信中断时的安全状态（保持、回到安全值、由 PLC 接管），由工艺负责人确认并写入文档；PLC 通过心跳检测上位机掉线，掉线后的动作由 PLC 程序决定。掉线时输出状态不明会让设备处于危险状态。

B.2 设备通信

  • SHOULDIND-04每种协议（OPC UA、S7、Modbus TCP 等）一个适配器，藏在统一接口后面；业务逻辑不引用通信库。
  • MUSTIND-05每次读写有超时；断线后按指数退避加随机抖动重连，有上限，不做紧密重连循环。无超时或紧密重连会拖垮网络和设备。
  • SHOULDIND-06每台设备的连接状态（已连接、降级、断开）和最后一次成功通信时间持续显示给操作员。
  • SHOULDIND-08LOPC UA 生产环境用 Sign 或 SignAndEncrypt，证书信任列表受管理；没有安全机制的协议（如 Modbus TCP）只在隔离的网段中使用。

B.3 数据与采集

  • MUSTIND-09每个值带质量（好、不确定、坏）和时间戳（源时间与服务器时间，UTC）；坏值或过期值按其状态显示，从不静默显示上一个好值。把坏值当好值显示会误导操作员。
  • SHOULDIND-10工程单位、原始量程、换算和记录死区只在变量配置中定义一次，代码不重复换算。
  • SHOULDIND-12设备支持时用订阅（如 OPC UA 监视项）代替轮询；轮询按扫描等级（例如 100 ms、1 s、10 s）分组批量读取，并限制每台设备的请求速率。

B.4 写入设备

  • MUSTIND-14操作员写入设定值或命令前确认：显示目标设备、变量、旧值、新值和单位。误操作的设定值会直接作用到设备上。
  • MUSTIND-15发送前在边界检查量程、变化率和允许条件（由变量配置定义）；检查不通过就不发送。越限或不满足条件的写入会损坏设备或产品。
  • SHOULDIND-16写入后读回；不一致时标出并记入审计。
  • MUST NOTIND-17自动重发结果未知的写入或命令；会使设备运动的命令每次都需要操作员的明确动作，不批量、不自动重复。重复发送命令会让设备重复动作。

B.5 报警管理（ISA-18.2 原则）

  • SHOULDIND-18报警有明确的状态：正常、未确认、已确认、恢复未确认、搁置、设计抑制、停用；状态变化记入历史。
  • SHOULDIND-19M+每条报警经合理化：优先级（3–4 级）、原因、后果、操作员动作、允许的响应时间；不满足的不是报警，改为事件或提示。
  • SHOULDIND-20确认按条进行，由登录用户完成并记录；搁置有时限和原因，并审计。
  • SHOULDIND-21M+提供报警洪流抑制与首出报警；统计每位操作员的报警率，与 ISA-18.2 / EEMUA 191 的目标比较（稳态约每 10 分钟 1 条以内）。

B.6 操作画面（ISA-101 高性能 HMI）

  • SHOULDIND-22灰度基调：正常状态不用彩色；颜色只表示异常和报警，报警色保留给报警，不作他用。
  • SHOULDIND-23画面分层：总览 → 单元 → 设备细节 → 诊断；从总览到任一设备不超过 3 次操作。
  • SHOULDIND-24符号库统一：状态用形状加文字表达，同一符号全系统同义；数值总带单位，关键量配带正常范围的趋势。
  • SHOULDIND-25操作值刷新不慢于 1 秒；通信慢或中断不阻塞画面。界面的其他规则按第 21 节。

B.7 用户、权限与记录

  • MUSTIND-26角色（查看、操作、工程、管理）按最小权限；L 每人独立账号，不共用登录。越权操作会改变设备状态。
  • MUSTIND-27操作员动作的审计记录：谁、做了什么、何时（UTC）、在哪个站点、旧值、新值，需要时附原因；防篡改。事故后无法追查谁改了什么。
  • MUSTIND-28L受监管场合（如 21 CFR Part 11、EU GMP Annex 11）：电子签名注明含义并重新验证身份；审计记录不能关闭或编辑；保留期按法规。受监管场合缺少电子记录会导致合规失败。

B.8 历史数据与时间

  • SHOULDIND-29按变量类别定义历史保留期，并据此估算存储。
  • SHOULDIND-30数据缺口明确记录，不跨通信中断插值；网络中断时本地缓存后补传。
  • SHOULDIND-31用 NTP 与厂区时钟源同步并监视漂移；存储一律 UTC。

B.9 7×24 稳定性

  • MUSTIND-32M+浸泡测试：M 至少 72 小时、L 至少 7 天，内存、句柄、线程数趋势平稳。泄漏会在连续运行数周后导致宕机。
  • SHOULDIND-33M+服务受看门狗监督，崩溃后带退避自动重启；重启计数并报警。
  • SHOULDIND-34日志轮转并有磁盘空间保护；磁盘将满时报警，不停止采集。

B.10 网络安全（IEC 62443 基础）

  • SHOULDIND-35L按区域与管道划分：上位机在自己的区域，只开放必需的端口，连接关系写入文档。
  • MUSTIND-36L所有用户和服务都经标识与认证；没有默认口令；服务账号最小权限。默认口令和匿名访问是最常见的入侵途径。
  • SHOULDIND-37L默认安全：不用的服务关闭，加密协议默认开启；安全事件（登录、失败、配置变更）记录并可导出到厂区的日志系统。
  • SHOULDIND-38L有书面的补丁流程（操作系统、运行库、产品）和兼容性测试；随产品提供已安装系统的加固指南（系统设置、防火墙、移动存储策略）。

B.11 离线现场部署与仿真

  • SHOULDIND-39安装、运行、更新都不依赖互联网：离线安装包和更新包附校验和。
  • SHOULDIND-40配置可导出备份（带版本）并可恢复；恢复流程经过测试。
  • SHOULDIND-41提供仿真模式：每种支持的协议有设备模拟器（OPC UA 模拟服务器、Modbus 从站模拟、PLC 仿真）；仿真状态在界面上醒目标出。
  • MUSTIND-42PLC 接口数据块带版本字：上位机连接时核对版本，不匹配就拒绝写入并提示；优先用符号访问；接口布局变化按对外契约管理（第 17 节）。接口布局不一致会把值写到错误的地址。

B.12 硬件在环测试清单 M+

  • 真实 PLC 或仿真 PLC 加实际网络拓扑；记录固件版本与接口数据块版本。
  • 拔网线、PLC 停机、重启上位机：状态显示、安全状态、重连、数据缺口记录都正确。
  • 每个写入路径：确认、量程与允许条件拒绝、读回、审计记录。
  • 报警：触发、确认、搁置、恢复、洪流抑制；报警率统计正确。
  • 负载：最大变量数和最短扫描周期下的周期时间与 CPU、内存。
  • 时间同步漂移、时区与夏令时切换下的历史数据和报警时间戳。
  • 角色权限：每个角色只能做允许的操作；审计记录完整。

领域 C：工程软件自动化（厂商 API）

要点厂商 API 关在适配层或独立进程；按精确 SDK 编译；功能按版本登记，不推断。

适用于经厂商 API（COM 或 .NET，例如 PLC 编程软件、电气 CAD 的开放接口）驱动另一款工程软件的工具。常与领域 A 一起使用。

C.1 隔离与线程

  • MUSTVND-01厂商 API 只在适配层出现，最好在独立的 worker 进程中；厂商对象不跨请求持有、不跨进程传递，按名称或规范路径寻址。跨请求持有厂商对象会导致崩溃或误操作。
  • MUSTVND-02按厂商文档使用指定的线程与单元（STA 或 MTA）；调用前核对，不符时在调用前拒绝；适配器不用 Task.Run、ConfigureAwait 或调度器把原生调用挪到其他线程。在错误的线程上调用会让目标软件崩溃或挂起。
  • MUSTVND-03插件运行在目标软件进程内时：经统一的调度器在主线程上执行，调度带超时（不用没有超时的同步调度）；调度的委托内部捕获全部异常；有模态对话框打开时拒绝并报“忙”；主线程上不 await、不阻塞等待其他线程。未捕获的异常会结束目标软件进程。

C.2 版本与注册

  • MUSTVND-06每个支持的目标版本按其精确 SDK 编译适配器；构建核对引用的版本，不符就失败，不静默回退到本机的其他版本；厂商程序集不复制、不分发（DEP-07）。静默回退到其他版本会产生难以复现的缺陷。
  • SHOULDVND-07“功能 × 目标版本”的支持关系只在一张登记表中声明，注册、发现、文档、示例和测试共用；编译期差异只用一份特性符号表表达。
  • SHOULDVND-08各版本的功能数量随 API 支持而定，不为一致而拉平，由生成目录给出。

C.3 写入与厂商行为

  • MUSTVND-09厂商提供事务或撤销时，每次写入放在一个事务内并合并为一个可撤销步骤（标注来源，如 “AI: <tool>”）；读回校验通过才提交，其余路径回滚。半途失败会留下损坏的项目。
  • SHOULDVND-10操作前后收集目标软件的系统消息差异，把相关消息随结果返回；很多失败只出现在这里。
  • MUSTVND-11用禁用 API 列表拦住“看似读取、实际写入”、占用许可或已知会使目标软件崩溃的成员；确需使用时就地抑制并写明原因。看似读取的成员可能写入项目或占用许可。
  • SHOULDVND-12自动化代码不弹出界面（除审批外），在目标软件的静默模式下执行；检查许可时不占用许可。
  • SHOULDVND-13每条依赖的厂商行为记在 API 笔记中（编号、版本、验证日期），代码注释引用编号（P-01、CMT-02）。

C.4 新增目标版本清单

  • 取得该版本的 SDK 与文档，放在本机，不入库。
  • 在版本登记表中加一行，并在特性符号表中声明差异。
  • 按精确 SDK 编译适配器；构建核对版本。
  • 逐个功能核对 API 证据，生成目录和数量；不支持的动作返回“不支持”。
  • 示例按该版本 schema 生成；离线检查通过。
  • 实机核对清单加入该版本；台账先标 NOT RUN，验证后更新；支持矩阵与发布说明同步。

领域 D：桌面应用

要点MVVM、界面线程不做 IO、按用户的数据位置、可回滚的更新；界面规则见第 21 节。

适用于 Windows WPF、WinUI，以及适用时的 Electron、.NET MAUI。第 21 节全部适用。

  • SHOULDDSK-01MVVM：视图只做绑定和呈现；视图模型不引用控件类型；业务逻辑在视图模型之外，可以不启动界面测试。
  • MUSTDSK-02界面线程只更新界面对象，跨线程经调度器；界面线程不做 IO、不阻塞等待；长操作显示进度并可取消。界面线程上的 IO 会冻结界面。
  • SHOULDDSK-05需要单实例时用当前用户范围的命名互斥量；第二个实例把参数转交给已运行的实例后退出。
  • SHOULDDSK-07M+安装程序与自动更新符合 PKG 与 MIG-05：按用户安装、校验哈希、保留上一版本用于回滚；更新时不强制结束正在写入的进程。
  • SHOULDDSK-08M+可执行文件和安装包用代码签名证书签名（带时间戳）；未签名时在发布说明中说明，并提供 SHA-256。
  • MUSTDSK-09Electron：渲染进程开启 contextIsolation 与 sandbox，关闭 nodeIntegration，经 preload 暴露最小 API，设置 CSP，不加载远程内容执行代码。渲染进程被注入后会获得系统权限。

D.1 桌面发布清单

  • 1024 × 640、200% 缩放、中英文、浅色/深色/高对比渲染检查通过。
  • 标准用户在干净机器上安装、首次运行、升级、回滚、卸载各一遍。
  • 单实例、崩溃处理、诊断包导出可用。
  • 签名与哈希齐全；SmartScreen 提示已在发布说明中说明（未签名时）。

领域 E：Web 开发

要点TypeScript strict、OpenAPI 为契约、OWASP 为安全基线；性能预算和可观测性按等级。

E.1 前端

  • SHOULDWEB-01组件小而单一：展示组件只接收数据和回调，数据获取放在页面或容器层；状态放在用到它的最近位置，服务端数据交给查询缓存库，全局存储只放真正全局的状态。
  • SHOULDWEB-02TypeScript strict；外部数据（API 响应、URL 参数、本地存储）进入时按 schema 校验（L2 附录）。
  • SHOULDWEB-03WCAG 2.2 AA：语义化元素优先于 ARIA；全部键盘可用；焦点可见；对比度按 UI-10；表单错误与字段关联。
  • SHOULDWEB-04M+性能预算按第 75 百分位：LCP ≤ 2.5 s、INP ≤ 200 ms、CLS ≤ 0.1；每个路由的首屏 JS 体积有上限，由 CI 检查。
  • SHOULDWEB-05响应式：从 320 px 宽度起没有横向滚动；颜色、字号、间距用 CSS 变量形式的设计 token；支持浅色与深色。
  • SHOULDWEB-06写明浏览器支持政策（例如主流常青浏览器的最近两个版本），按政策测试。
  • SHOULDWEB-07每个路由有错误边界，显示可恢复的错误界面并上报诊断编号；文字走 i18n 资源（第 10 节）。
  • MUST NOTWEB-08在前端代码、构建产物或环境变量中放密钥：发到浏览器的一切都是公开的。发到浏览器的密钥对所有人可见。

E.2 后端与 API

  • SHOULDWEB-09REST 按 Microsoft REST API Guidelines；选用 GraphQL 或 gRPC 时写 ADR。OpenAPI 是契约：入库、由代码生成或校验，差异按契约变化评审。
  • SHOULDWEB-10API 有版本（api-version 参数或路径主版本）；列表分页（游标或 nextLink）且有上限；创建或扣费类 POST 接受 Idempotency-Key。
  • SHOULDWEB-11错误用 RFC 9457 problem details（type、title、status、detail、instance，加稳定的错误码和请求号）；不返回堆栈。
  • SHOULDWEB-12限流返回 429 和 Retry-After；对外调用都有超时和有上限的重试（只对幂等请求）。
  • MUSTWEB-13认证用 OAuth 2.0 / OpenID Connect（浏览器用授权码 + PKCE）；访问令牌短期有效；授权在服务端按资源检查。只在客户端检查权限会被绕过。
  • MUSTWEB-14会话 Cookie 设 Secure、HttpOnly、SameSite=Lax 或 Strict；基于 Cookie 的状态变更请求有 CSRF 防护；CORS 使用显式白名单，带凭据时不用 *。防止会话劫持、CSRF 和跨域滥用。

E.3 Web 安全

  • SHOULDWEB-16按 OWASP Top 10 建威胁清单；M+ 选定 OWASP ASVS 等级（M 用 Level 1，L 用 Level 2）并逐项核对。
  • MUSTWEB-17SQL 只用参数化查询或 ORM，不拼接字符串；动态排序与列名走白名单。防止 SQL 注入。
  • MUSTWEB-18XSS：依赖框架的自动转义；插入 HTML 前用净化库；设置 CSP（nonce 或 hash，不用 unsafe-inline）。防止 XSS。
  • MUSTWEB-19SSRF：服务端发起的请求只访问白名单目标，拒绝内网地址段和云元数据地址，跟随重定向时重新校验。防止 SSRF 访问内网和云元数据。
  • MUSTWEB-20文件上传：大小上限；按内容判断类型；随机文件名；存放在 Web 根目录之外；下载用 Content-Disposition: attachment。防止上传的文件被执行或覆盖。
  • SHOULDWEB-21安全响应头：Strict-Transport-Security、Content-Security-Policy（含 frame-ancestors）、X-Content-Type-Options: nosniff、Referrer-Policy。

E.4 数据

  • SHOULDWEB-23数据库结构变更用入库的版本化迁移，由工具执行；每个迁移可回退，或写明只前进的计划；M+ 零停机变更用“先扩展、后收缩”两步。
  • SHOULDWEB-24跨多行的不变量放在事务中；索引按查询模式建立，并用执行计划核对慢查询。
  • MUSTWEB-25备份自动执行，并定期做恢复演练（L 至少每季度一次），记录恢复所需时间。没有恢复演练的备份往往恢复不了。
  • MUSTWEB-26个人信息有清单：最少收集、传输与存储加密、保留期与删除；遵守 GDPR 与《个人信息保护法》的基本要求（合法依据或同意、访问与删除请求、跨境传输规则、泄露通知流程）。违法收集或泄露个人信息。

E.5 运维

  • SHOULDWEB-27配置按十二要素经环境注入；同一个构建产物在 dev、staging、prod 之间晋升，不为环境重新构建。
  • SHOULDWEB-28M+容器用最小基础镜像、非 root 用户、按摘要固定版本；基础设施用代码（IaC）入库并经评审。
  • SHOULDWEB-30M+可观测性：结构化日志、指标、链路追踪（OpenTelemetry），全部带请求号；提供存活与就绪探针。
  • SHOULDWEB-31L为关键用户路径定义 SLO 和错误预算；按症状告警，每个告警链接到处置手册（runbook）。
  • SHOULDWEB-32M+零停机部署（滚动或蓝绿），一步回滚到上一个版本；数据库迁移与回滚兼容。

E.6 Web 发布清单

  • OpenAPI 差异已评审；破坏性变化升版本。
  • Core Web Vitals 与体积预算通过；无障碍自动检查与键盘走查通过。
  • 安全头、CSP、Cookie 属性、CORS 白名单已核对；依赖扫描无高危。
  • 迁移在 staging 演练；回滚步骤可用；备份最近一次恢复演练成功。
  • 仪表盘与告警覆盖新功能；功能开关有到期日。

领域 F：移动 App

要点遵循平台规范；权限按需申请；密钥进系统安全存储；分阶段发布。
  • SHOULDMOB-01遵循平台规范：iOS 按 Apple Human Interface Guidelines，Android 按 Material Design；跨平台框架同样遵守各平台的导航、返回和手势约定。
  • SHOULDMOB-02架构采用 MVVM 或单向数据流；界面状态由单一来源驱动，可在没有界面的情况下测试。
  • SHOULDMOB-03M+需要离线使用时以本地数据为先，后台同步；同步冲突有明确规则（例如以服务端版本号判断并提示用户），不静默覆盖。
  • SHOULDMOB-04网络请求有超时、带退避的重试（只对幂等请求）和离线提示；弱网下界面不卡住。
  • SHOULDMOB-05节省电量和流量：批量后台任务交给系统调度器，大文件只在 Wi-Fi 或经用户同意时下载，不做高频轮询。
  • SHOULDMOB-06权限在用到时、结合上下文申请，只申请最少的权限；被拒绝时功能降级并说明。
  • MUSTMOB-07隐私：数据最少化；应用商店的隐私标签与实际行为一致；第三方 SDK 的数据收集纳入清单。隐私标签与行为不符会被下架。
  • MUSTMOB-08令牌与密钥存放在 Keychain（iOS）或 Keystore（Android）；不放在普通偏好设置或文件中。普通存储中的令牌容易被提取。
  • SHOULDMOB-09证书固定只在威胁模型证明需要时使用，并有轮换方案，避免证书更换导致应用失联。
  • MUSTMOB-10深度链接用 Universal Links / App Links 校验域名；链接参数按外部输入校验，不能直接触发写入。外部链接可能触发非预期的写入。
  • SHOULDMOB-11推送通知需用户授权；通知内容不含敏感数据；点击后导航到明确的页面。
  • SHOULDMOB-12无障碍：支持 VoiceOver 与 TalkBack 的标签和顺序，支持动态字体（Dynamic Type、系统字号），触控目标不小于 44 pt / 48 dp。
  • SHOULDMOB-14M+发布前对照应用商店审核规则自查；经内部测试渠道（TestFlight、内部测试轨道）验证后再分阶段发布，监视崩溃率，异常时暂停。
  • MUSTMOB-15崩溃报告需用户同意，并在隐私说明中列出收集的数据（DIAG-01）。未经同意上报崩溃数据违反隐私规则。
  • SHOULDMOB-16写明最低系统版本政策（例如支持最近若干个主版本）和设备测试矩阵（小屏、大屏、平板、低端机、最新系统）。

F.1 移动发布清单

  • 设备矩阵上的冒烟测试通过；离线、弱网、权限被拒绝时的行为正确。
  • VoiceOver/TalkBack 与最大字号下走一遍主要流程。
  • 隐私标签、权限说明文字与实际一致；崩溃报告需同意。
  • 内部测试渠道验证通过；分阶段发布的比例和暂停条件已设定。
