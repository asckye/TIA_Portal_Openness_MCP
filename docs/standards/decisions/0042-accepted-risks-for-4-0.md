# 0042 4.0 接受的风险：更新包不签名，密码作为工具参数传入

- 状态：已采纳
- 日期：2026-11-23
- 决策者：维护者（2026-11-23 按建议批准）
- 置信度：中
- 相关：[安全标准](../security.md) SEC-06、SEC-11、SEC-16 与第 6 节；[ADR 0038](0038-keyless-http-transport.md)；计划 S3；桌面规范 DSK-07、通用规范 MIG-05、SEC-19

## 背景

2026-11-22 的全面审查指出两项没有 ADR 的 MUST 例外：

1. 更新器只用同一发布中的 `.sha256` 核对 ZIP。控制 GitHub 账户或发布令牌的人可以同时替换包和摘要。维护者 2026-11-04 已接受此风险（S3），但只写在计划中。工程规范 2.1 起要求核对发布者签名，签名密钥不放在更新服务器上。
2. DPAPI 保管库移除后，PLC 保护、UMAC、Web 服务器、驱动安全、Teamcenter 和 UMC 的密码只能作为工具参数由 AI 客户端传入。本产品的审批卡、日志和审计会脱敏，但密码已经过模型服务商并留在客户端的对话记录中；经局域网 HTTP 时还以明文传输。

## 选项

1. 4.0 前实现更新签名和工作台专用的密码输入：消除两项风险；推迟 4.0。
2. 4.0 接受两项风险并写明，签名和密码输入在 4.1 决定和实施：4.0 按计划发布；风险由用户知情承担。

## 决定

采用选项 2。

- 更新包不签名是 4.0 接受的风险，仍用同一发布的 SHA-256；是否签名及签名方式在 4.1 决定。发布账户与令牌的保护由 S4 处理。
- 作为工具参数传入的密码会到达模型服务商和对话记录，这是 4.0 的已知风险，写进发布说明的已知限制。4.1 计划提供只在工作台输入、不经过 AI 的密码输入方式。

## 后果

- 正面：4.0 不因这两项推迟；风险在发布说明和偏差登记中可见。
- 负面与取舍：GitHub 账户被控制时可以发布恶意更新；用户须避免在 AI 对话中输入重要密码，或在使用后更换。
- 后续工作：4.1 的更新签名决定和工作台密码输入。
- 验证方式：rc.2 和 4.0 发布说明的已知限制；[标准说明](../README.md)的偏差登记。
