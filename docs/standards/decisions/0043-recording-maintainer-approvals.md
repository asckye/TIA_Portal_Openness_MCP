# 0043 主导代理只为维护者明确批准的事项登记批准记录

- 状态：已采纳
- 日期：2026-11-23
- 决策者：维护者
- 置信度：高
- 相关：[ADR 0016](0016-architecture-decision-records.md)；[ADR 0054](0054-no-check-loosening-without-approval.md)（不放宽检查，待补写编号 B36）；`build-tools/release/baselines/approved-check-changes.json`；[AGENTS.md](../../../AGENTS.md)

## 背景

检查、断言和阈值只有维护者批准后才能删除、跳过或放宽。`check-loosening` 要求每处改动在 `approved-check-changes.json` 中有批准记录，记录由主导代理以“Record maintainer approval”提交写入。维护者 2026-11-17 起要求按推荐执行、不再逐项询问（“按推荐来做”），2026-11-21 再次确认。批准记录因此可能由代理代写，需要说明代写的边界。

## 选项

1. 只要有常设指示，代理可以为任何检查改动写批准记录：最快；常设指示会被当作对未见过事项的批准。
2. 代理只为维护者明确批准过的事项写记录，并注明依据：每条记录可以追溯到维护者的一次批准。

## 决定

采用选项 2。

- 主导代理只为维护者明确批准的事项写批准记录：维护者对这些具体项说了“是”，或批准了事先列出这些项的任务说明或建议清单。
- 常设指示“按推荐来做”只覆盖已经写给维护者的推荐项，记录写明日期和依据，例如“维护者 2026-11-23 按建议批准”。没有写给维护者的检查改动，即使看似误报，也先问维护者。
- 实现代理不写批准记录；审查者确认改动与批准范围一致后提交。

## 后果

- 正面：每条批准记录都能对应维护者的一次决定和日期。
- 负面与取舍：未事先列出的检查改动要等维护者回复。
- 验证方式：`check-loosening` 对照批准记录；审查时核对 `reason` 中的日期和依据。
