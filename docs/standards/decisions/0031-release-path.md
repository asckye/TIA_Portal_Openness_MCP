# 0031 提前准备候选，确认后在五分钟内公开预发布

- 状态：已采纳
- 日期：2026-11-03（重建工具、准备与公开分离）；2026-11-04（整理顺序与发布后校验）
- 决策者：维护者
- 置信度：高
- 相关：[ADR 0019](0019-incremental-check-all.md)、[0024](0024-ci-does-not-block-merges.md)、[0025](0025-release-evidence-nightly-and-verified-build-units.md)、[0020](0020-prereleases-tested-by-users.md)；[开发计划](../../plan/plan.md)；[发布流程](../../manuals/release.md)；[验证](../../manuals/validation.md)

## 背景

旧构建、检查和发布链包含调度器、结果复用、构建收据、证据采纳及 nightly。多轮发布准备仍耗时过长。维护者于 2026-11-03 要求将构建、检查和发布工具作为新项目重建，不继续改装旧链；产品代码只按批次整理，不随之重写。

同日维护者明确：公开发布在五分钟内完成是硬性要求，不是优化目标；耗时构建、测试、打包和上传必须提前完成。2026-11-04 又决定先完成全部已安排的整理，再真正准备 beta.3，并将发布后工作流缩减为 ZIP 与 sidecar 校验。

## 选项

1. 在原链上继续优化并采纳旧运行结果：保留大量身份、收据和缓存耦合，仍难保证公开发布的时限。
2. 使用原生构建与测试工具提前准备并上传候选，确认后只做核对、推送、标签和公开：耗时工作可提前完成，公开过程能采用独立预算。

## 决定

采用选项 2。

1. 从头实现 `prepare`：普通 MSBuild / `dotnet build`、全部注册套件、保留的发布检查、ZIP 与 SHA-256、单份本地 `candidate.json`。不沿用旧调度器、结果缓存、收据或证据采纳链，不在 Git 中记录构建结果。
2. 提前将检查过的 ZIP 和 `.sha256` 上传到私有草稿；上传失败保留候选，`upload-draft` 可重复执行。被测试和上传的包必须是相同字节。
3. 维护者确认后执行 `publish-prepared`，从进程启动到公开采用 300 秒硬预算。发布阶段不构建、测试、打包或等待 CI；核对通过后推送候选提交、创建标签并公开草稿。重复执行同一命令恢复故障，读取既有远端状态而不假定失败响应代表没有执行。
4. 公开的版本为预发布，`make_latest=false`。正式版规则另行决定；当前命令只接受 beta/rc 版本。
5. 发布后 GitHub 工作流只核对公开 ZIP 与 `.sha256`；不再要求标签中的旧交付记录与包相符。摘要校验不等于真实性签名或真机验收。
6. 取消 nightly。合并门由 NEW-REL-2 的 `merge-check` 承担：普通构建、受影响的测试及生成/仓库检查，目标约 10 分钟。完整发布检查在 `prepare`，GitHub CI 不阻塞合并。
7. 移除已批准的性能门槛、HTTP 稳定性压测、静默阶段、套件输出对照和全部八版逐工具响应捕获；保留工具定义快照、功能测试、数量门槛、审批、写安全和故障恢复覆盖。真实行为按 ADR 0020 由发布后的 VM 回归与测试者验证。

本决定取代 ADR 0019 的结果复用/调度规则、ADR 0024 的旧合并命令及 nightly 安排，以及 ADR 0025 的发布证据采纳规则。ADR 0024 中 CI 不阻塞合并与发布的原则继续有效；旧记录中的背景与历史数据不改写。

## 后果

- 准备失败不会产生可发布候选；上传失败不要求重新构建。源代码变化后须重新准备，不能手工修改候选或包哈希。
- 公开阶段可独立审查和计时，但网络故障仍可能使下载确认失败；已有标签或公开状态由重跑同一命令核实，失败不得报告为成功。
- NEW-REL-B 接入完整检查与候选；NEW-REL-2 实现合并门；NEW-REL-3 删除旧工具和响应基线。所有整理完成后再真实运行 `prepare`，顺序见开发计划。
- REVIEW-1 在 beta.4 迁到新工具并带入漏洞扫描；此迁移缺口需在计划中可见，不宣称当前准备流程已经包含该扫描。S3 的包签名与 S7 的旧资产许可处理仍待维护者决定。
- 验证准备产物、完整套件门槛、发布的拒绝路径、草稿复用、五分钟预算和故障恢复；通过合成夹具测试工具，不借此授权连接 TIA、PLC 或 VM。
