# v3.3.0 — Unified desktop and compatible runtime refactor

3.3.0 is the first release after the internal refactor across phases 0–5, including the default-build changes from phase 4. It includes MCP runtimes for **V14 SP1, V15.1 and V16–V21** and one desktop workbench for configuration and engineering. Original V14/V15 are not supported.

MCP tool names, parameter names and types, response structures and error conventions remain compatible with 3.2.0, except for the **stricter PLC name resolution described below (G9)**. The experimental Studio session and engine VCI routes behind `TiaSharedAdapterPaths` remain disabled (`false`) and are outside this release. Phase 6 changes belong to 4.0.

## Changes

- **One desktop.** The root `TiaMcpConfigurator.exe` opens the WPF/.NET 10 workbench. Engineering and MCP & clients share one window and retain their page state. Menus are grouped by owner: Project and PLC run the workbench's own bridge operations (Ctrl+O open or connect, Ctrl+S save, Ctrl+B compile), MCP runs the service and client actions of the configuration page with the same availability as its buttons, View switches pages (Ctrl+1 / Ctrl+2), and Tools holds language and theme. The title bar shows the MCP service state on both pages and keeps version selection. Client configuration merging, backups and secret protection are preserved; native bridges and MCP engines remain separate backend processes.
- **Desktop fixes.** The options panel opens correctly, panels follow the light/dark theme, application dialogs use the workbench style, and the configuration menu entries that stayed Chinese in English mode are translated. The caption shows the current page, and Help exposes updates from either page. Summary, log and diff cards share one card style; Windows 10 shows the caption and list icons instead of empty boxes; closing the workbench with the HTTP service running no longer crashes.
- **Bundles work outside the repository.** Engines and Studio locate bundled guides, templates, companion scripts, sibling engines and bridge components from the installation layout. A complete extracted bundle needs no Git checkout. The V21 ecosystem catalog is embedded in both full engines, so its queries no longer depend on a loose JSON file; editing the reference copy does not change those queries. Existing resource overrides and compatibility probes remain in place. See [runtime layout](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/runtime-layout.md).
- **Bundled .NET 10 runtime.** The package ships Microsoft .NET 10.0.12 in `runtime/dotnet` (base runtime, ASP.NET Core and Windows Desktop), taken from Microsoft's official archives and checked against their published SHA-512. The V14 SP1–V19 foundation hosts move from .NET 8 to .NET 10, and every .NET executable in the package looks for this copy first, so the target computer needs no .NET 8, ASP.NET Core or .NET 10 Desktop Runtime installation.
- **Framework requirement for older workers.** The V14 SP1, V15.1 and V16 foundation workers now target **.NET Framework 4.8**, matching the later workers. .NET Framework is a Windows component and cannot be bundled; install 4.8 on Windows versions that do not include it (before Windows 10 1903).
- **Worker and Studio bridge protocol.** Both now use internal protocol 2, with an identity handshake and request/session correlation; their JSON payloads use System.Text.Json. This requires no MCP client protocol change. Failed requests are never automatically replayed. Handled Studio operation errors keep their original text and allow the session to continue; a broken channel requires explicit recovery after inspecting the actual TIA state.
- **One diagnostics journal per process.** Engine and in-process adapter diagnostics share a journal and call correlation IDs, making an operation traceable across that boundary. Separate worker processes keep their own journals. The default location remains `%LOCALAPPDATA%\TiaMcp\diagnostics`, with the existing `TIA_MCP_DIAGNOSTICS_DIRECTORY` override.
- **V15.1 project files.** The V15.1 foundation engine accepts the `.ap15_1` files TIA V15.1 actually writes. Since 3.2.0 it accepted only `.ap15`, so binding, opening or creating a V15.1 project failed; a V15 `.ap15` project is still not opened as V15.1.
- **Process and installation fixes.** Child-process input is written as UTF-8 without a BOM regardless of the Windows console code page, avoiding corrupted non-ASCII requests. Foundation health reports use the application release version instead of a hard-coded value. The desktop updater recognizes a worktree's `.git` file as a source checkout and disables installation updates there.

Internally, the large engine classes were split into domain tools/services and a session kernel, with shared logic, runtime channels and adapter contracts separated into libraries. Compatibility evidence includes unchanged tool/schema contracts, [raw response snapshots](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/manifest/history/contracts-v3/responses) for direct and `CallTool` paths where available, per-domain byte comparisons (68 domains, 3,748 checks per full-engine version for the response conversions), and native call inventories checking the structural moves. The [refactor plan](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/refactor-plan.md) records the evidence and its limits.

## PLC name resolution — behavior change (G9)

In the V20/V21 full engines, reads and writes now resolve a non-empty `softwarePath` only by an exact software name or a unique structural alias: CPU, owning station/device, or a group-qualified device/software path. Matching ignores case and surrounding whitespace. An incorrect name no longer selects the only PLC in the project, and substrings are no longer guessed. This prevents a stale name from silently targeting a different PLC after another client changes the bound project.

For example, assume one PLC named `PLC_Main`, on CPU `CPU_1` in station `Station_1`, under device group `Line_A`:

| `GetBlocks` argument | 3.3.0 result |
|---|---|
| `{"softwarePath":" plc_main "}` | Resolves `PLC_Main`. |
| `{"softwarePath":"CPU_1"}` or `{"softwarePath":"Line_A/Station_1/PLC_Main"}` | Resolves the uniquely matching PLC. |
| `{"softwarePath":"PLC_Old"}` or `{"softwarePath":"Main"}` | Returns NotFound with available PLC paths; 3.2 could select the sole PLC. |
| `{"softwarePath":""}` | Still selects the sole PLC; it cannot choose between multiple PLCs. |

If two PLCs share the station alias `Station_1`, that alias returns an ambiguity error listing the candidates. Use a unique software name or the appropriate qualified path. A group name alone is not a PLC alias. The same rules apply to reads such as `ExportPlcTagTable` and writes such as `ImportPlcTagTable`. Verified resolutions are cached, and changing the bound project clears the cache.

Before upgrading, replace placeholder, stale or partial PLC names in saved prompts and automation with actual names or unique paths from the selected project. Empty-name shorthand remains available where the tool accepts it and the project contains exactly one PLC.

## Validation and real-machine acceptance

Recorded offline evidence covers full-engine functional and protocol checks, eight exact-version SDK builds, Foundation/Studio channel fault tests, JSON golden samples, desktop/configuration tests and bundle relocation checks. The channel suite recorded 253 checks; Studio relocation compared 1,921 results; embedded ecosystem catalog checks passed 75 cases in each full engine. These are implementation-task results recorded in the [refactor plan](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/refactor-plan.md) and [layout evidence](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/runtime-layout.md), not a completed 3.3.0 real-machine acceptance run. The [release workflow](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/release-workflow.md) rebuilds and validates the final candidate and package.

The [3.3.0 minimal per-VM acceptance list](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/reference/real-machine-ledger.md#330-发布前最小验收按虚拟机) is the publication gate: Foundation MCP on V14 SP1–V19 (including the net48 change on the oldest three), Studio on V14 SP1/V16/V21, and G9 plus default-engine smoke checks on V20/V21. It uses the candidate bundle outside the repository and test-project copies. Every item passed on 2026-10-04/05 with the seventh candidate build; the per-VM results are in the [real-machine ledger](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/reference/real-machine-ledger.md#330-验收结果2026-10-0405). Acceptance found that V15.1 projects (`.ap15_1`) could not be bound, which is fixed in this release, and confirmed on a VM with only .NET Framework 4.8 that the bundled .NET 10 runtime needs no installation.

**Publication gate:** met; this package was published after every item of that list passed on its virtual machine.

Offline checks do not establish successful engineering operations or native crash safety. The existing native PLC cross-reference restrictions, Unified script-library rename incident and unverified Startdrive BICO read crash remain documented in [Openness limitations](../troubleshooting/openness-limitations.md).

## Download and upgrade

The complete package name is **`TIA_MCP_Delivery_v3.3.0_YYYYMMDD.zip`**, accompanied by a `.sha256` asset. GitHub's automatically generated source archives omit runtime binaries. See the [beginner guide (Chinese)](../getting-started/beginners.zh-CN.md) for installation and version selection.

Install the matching Siemens TIA Portal, Openness and licenses separately. Required runtimes are:

| Component | Required runtime |
|---|---|
| Unified desktop/configuration, V14 SP1–V19 foundation hosts | None: .NET 10 is bundled in `runtime/dotnet` |
| V20/V21 engines, native workers and Studio bridge | .NET Framework 4.8, including the V14 SP1/V15.1/V16 workers |

Python companion tools retain their separate environment setup.

Stop the MCP and workbench processes before replacing an installation, preserve your configuration and secret, and restart clients afterward. The configuration page retains its existing merge, backup and secret-protection behavior. No running service is updated automatically. Replace the complete bundle: the root `TiaMcpConfigurator.exe` launches `runtime/studio/TiaOpenness.exe`, and MCP entrypoints remain `runtime/v<release-key>/TiaMcpServer.exe` (keys: `14sp1`, `15.1`, `16`, `17`, `18`, `19`, `20`, `21`). Copying only an EXE is insufficient.

The package now includes dependencies such as `TiaMcp.Logic.dll`, `TiaMcp.Runtime.dll`, `TiaMcp.Adapters.Contracts.dll` and `TiaMcp.WorkerChannel.dll` in their component outputs; V20/V21 engine folders also carry their matching `TiaMcp.Adapter.20.dll` or `TiaMcp.Adapter.21.dll`. Studio's default native adapters remain under `runtime/studio/bridge/adapters/v<release-key>/TiaOpenness.Openness.dll`. These dependencies do not enable the experimental shared-adapter routes.

In the bundled source and documentation, the design checklist moved to [docs/development/design-qa.md](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/design-qa.md), dated diagnostic evidence moved to [manifest/history](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/manifest/history), and the launcher source and Glass assets moved under [TiaOpenness.Launcher](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/tools/tia-openness-studio/src/TiaOpenness.Launcher) and [TiaOpenness.Gui](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/tools/tia-openness-studio/src/TiaOpenness.Gui). The archive retains source, tests, examples, templates and licenses; Siemens PublicAPI assemblies, private projects, credentials and build logs are excluded.
