# v4.0.0-beta.4 — fourth 4.0 pre-release

This is the fourth 4.0 pre-release of Automation Engineering Workbench (formerly TIA Portal Openness MCP).
It is a **pre-release** on GitHub: it is never marked as the latest release, and is not offered by the
3.3 updater or the Workbench update check of a 3.3 installation. Download it by hand from the
[releases page](https://github.com/asckye/TIA_Portal_Openness_MCP/releases) to test it.

Unless a release is named below, the changes apply to all eight supported TIA Portal releases, V14 SP1, V15.1 and V16–V21.
The beta.4 changes have not run on a real TIA Portal. A separate real-machine regression session follows publication.

## Behavior changes you must know

- **27 more write tools preview by default.** A call without `dryRun:false`, the preview's `expectedPlanHash` and the exact
  bound `expectedProjectFile` only previews or refuses the write. Use the hash and project file from that tool's own preview.
  The full list is below. Actions that only read retain their direct behavior.
- **Plans include input file contents.** Changing an input file after preview makes the old plan stale and refuses apply.
  Preview again after a host restart. Directory plans currently include every file recursively, including files the import
  itself will not use.
- **Canonical parameter names.** Use `exportFile` for a file, `exportDirectory` for an output directory, `sourceDirectory` for
  an input directory and an array of exact segments for `devicePath`. Old names and the legacy device-path string work until
  5.0 and return `DEPRECATED_PARAMETER` warnings in `meta.warnings`. Do not send an old name and its replacement together.
  An omitted required export target uses a folder for the current session under the output root. Omitted report directories
  also move there. `GetSessionState.data.outputRoot` identifies the root.
- **Schemas use descriptions for alternatives.** No tool input schema has a root `oneOf`, `allOf` or `anyOf`. Mutually
  exclusive arguments and form-specific fields are described and checked at run time. Nested property schemas may still
  use combinators. Clients must handle a refused call even when its arguments pass their schema validation.
- **One tool-list model, short list by default.** V14 SP1–V19 clients now start with the `lite` list. V20/V21's short list
  expands. All eight use the `plc-foundation` profile name, shared instructions and catalog shape. `FindTools` discovers the
  rest, `CallTool` invokes them, and `--profile full` requests the full list. The Workbench operator sees the full list for
  the selected release even when the attached AI host uses `lite`. Known tools unavailable on that release report
  `UNSUPPORTED_CAPABILITY`, while unknown names report `TOOL_NOT_FOUND`.
- **File-write approval shows the actual target.** MCP file writes outside the output root require a Workbench approval card,
  including UNC targets. Every full normalized target is shown and bound to the decision. Git stage and commit always
  require approval. Turning off write approval requires typing the displayed localized confirmation word.
- **Workbench form prefill.** `PrefillWorkbenchForm` exposes a flat schema. `mode="set"` requires exactly the fields for its
  selected form, and `mode="clear"` requires an empty `fields` object. Prefills belong to the calling session and await human
  confirmation. A mismatched form and field set is refused at run time.
- **Session recovery.** A timed-out worker read returns `TIMEOUT` and drains before reuse. During recovery, cached
  `GetSessionState` and host-only tools remain available, while tools needing the worker remain gated. Write timeouts can
  still leave an unknown outcome requiring reset. Disconnect reports `requiresTiaRestart` from outstanding calls and the
  process lease. Use that result to decide whether TIA must restart. Save As, archive retrieval and isolated startup keep
  the current binding in sync.
- **Export handles are per session.** A session can no longer read, list or clear another session's exports. Restarting its
  worker drops its export handles. Run the producing tool again to obtain new ones.

## What is new compared with beta.3

### What testers will notice

- **Batch tools use one plan hash.** `RepairAndReimportPlcBlock`, `ImportPlcTagTablesFromDirectory`,
  `ExportPlcWatchTablesToDirectory` and `ExportTechnologyObjectsToDirectory` preview the selected items together and use one
  approval. Apply requires `confirm:true`, `dryRun:false`, the batch hash and the project file. Items run in order and stop
  at the first failure, with completed and unstarted items reported. The batch itself does not roll back earlier items.
- **Safer block moves.** `MovePlcBlockToGroup` exports and checks a recovery copy before deleting the source, then imports and
  verifies the destination's parent, name, number and language. If verification fails, it attempts to remove the destination
  and restore the original group. Failed cleanup or restoration keeps the recovery file and reports the remaining work.
  OB moves remain refused because that round trip has not been verified to preserve their event assignment.
- **Rollback for captured writes.** Multi-step engineering writes with captured recovery actions undo them in reverse order
  after failure. `restored` requires successful read-back verification. An uncertain or unverified restoration reports
  `unknown` and requires reset. Unified HMI button actions are sent in one worker request.
- **Native failure reasons.** Results retain the redacted native reason. Proven refusals and failures that read back unchanged
  no longer become `OUTCOME_UNKNOWN`. Uncertain dispatched writes still require reset.
- **Remote relay.** Remote MCP clients use a local stdio relay. Private and loopback destinations bypass proxies, other
  destinations follow the configured proxy and NO_PROXY rules, and new client configurations use the current user's
  DPAPI-protected access key. The HTTP listener validates Host and Origin on each request. The Workbench offers a proxy
  check and migration of old direct configurations.
- **Redesigned Workbench pages.** The shell, project, environment check, logs and diagnostics, MCP and clients, version control
  and AI calls pages share the new layout. Approvals use a waiting/processed list and detail view with the host's risk level,
  equal-weight write decisions, a default rejection for destructive operations and a countdown. With several running TIA
  processes, select the exact PID to attach.
- **VMFIX-5b tool fixes.** PLC loadable, fingerprint and monitor services are resolved through the PLC software and its device
  hierarchy. Unified tags bind through a verified PLC connection without writing read-only `PlcName`. Screen design, layout
  and background themes apply to existing screens without accidental rename requests. Missing connections report the native
  reason. On V21, technology-object creation still admits only the verified type/version pairs because other pairs caused a
  native crash. That V21 restriction remains pending real-machine evidence.
- **Other fixes.** Technology-object directory export creates its output directory before the native export and reports a
  creation failure as an ordinary refusal. Tag-table import name filters are case-insensitive. The Workbench reads block details page by page with `ListPlcBlocks`, and native invocation logs can be filtered by exact request and timestamp range.

### For developers

The wide `merge-check` is reported at about 12 minutes, compared with about 21 before FAST-GATE, against a target of about
10 minutes. Scheduling overlaps GUI and transport checks and reuses builds. HANG-GUARD replaces approved short waits with
120-second hang guards, and TREND-ALERT reports slowdowns above twice the recent median. Security analyzers and the block on
unapproved loosened checks run in the development gate, and full `prepare` performs a fresh dependency vulnerability scan.
These changes preserve the functional checks and their count gates.

## Known limitations

- **Real TIA verification is pending.** None of the beta.4 changes has run on a real TIA Portal. Publication is followed by a
  separate regression session on project copies, with its raw results retained for review. The generated checklist below
  remains unverified.
- **Argument and native-error detail is unfinished.** Argument errors do not yet consistently carry JSON pointers, and native
  failures do not yet carry `innererror`. DES-4 Parts 2 and 3 moved to beta.5.
- **Update signing is not done.** The maintainer accepted this risk on 2026-11-04. The updater checks a hash from the same
  GitHub release as the ZIP. Someone controlling the GitHub account could publish a malicious update.
- **LAN transport is plain HTTP.** The maintainer accepted this risk on 2026-11-04. Anyone on the same network can read the
  access key and PLC passwords. Use it only on a trusted network.
- **UNC access can precede approval.** Tool input and preview checks can contact a UNC server before an approval card and
  expose Windows credentials. S8 is planned before 4.0 to refuse network paths from AI calls, including loopback network
  paths. Workbench human actions retain their intended scope.
- **Eight-release unification is unfinished.** The tool-list presentation is shared, but call routes and policy switches
  still differ. UNIFY-1 remains a condition for 4.0. Capabilities still depend on the actual release's official API.
- **Some PLC group names are refused.** In tag, technology, watch-table and external-source trees, a group literally named
  `Program blocks` or `程序块` is refused with `INVALID_ARGUMENT`.
- **Directory previews are broader than the import.** The hash includes all nested files. An unrelated changed file makes the
  plan stale, and an unreadable file can refuse preview. A locked apply input may report a validation refusal instead of
  `PLAN_STALE`. Some host preflight checks omit `sourceDirectory` readability. The stale-plan message does not explain that
  a host restart can be the cause.
- **Some output hints need correction.** `ExportPlcBlockDocuments` chooses an existing default directory although its
  description requires a new one. Optional outputs such as `PatchPlcBlockDocument` may advertise an omitted-target default
  they do not provide. The `ExportPlcType` example uses a filename-shaped directory. Supply an explicit suitable target.
  Omitted report targets now use the session directory instead of the former reports directory.
- **Some validation and recovery messages remain imprecise.** `PreviewToolCall` can report READY for mismatched prefill fields
  that the real call refuses. HMI connection guidance can name a tool that cannot create the connection. A device name that contains `/` cannot be addressed through `devicePath`, because segments are joined with `/`. A lost TIA process before a network write starts
  can be reported as an exclusive-access refusal.

- **A refused scaffold step locks the session.** If one step of `BuildProjectScaffold` is refused, even a step that changed
  nothing, the tool reports the whole write as unknown and the session requires a reset. The step report is complete, so
  read it before you reset.
- **Some single-object exports are refused on some releases.** `semantics-unverified` previews refuse apply for a
  technology-object export on V14 SP1, V15.1 and V21, and for a watch-table export on V14 SP1. The official API has the
  export on all eight releases, so UNIFY-1 opens these.

## Install it next to 3.3

1. Select `v4.0.0-beta.4` on the releases page and download
   `TIA_MCP_Delivery_v4.0.0-beta.4_<date>.zip` and its `.sha256` file. Run
   `Get-FileHash -Algorithm SHA256 -LiteralPath '.\<downloaded-package>.zip'` and compare its hash with the sidecar.
   Extract only when they match. This checks the downloaded bytes. The accepted signing risk is described above.
2. Extract into a separate folder, such as `C:\TIA_MCP_4.0.0-beta.4`, keeping the 3.3 installation separate.
3. Start `TiaOpenness.exe`, run the environment check and create a separate MCP client entry for this folder.
   Follow the [configuration guide](../getting-started/configuration.md).
4. Use project copies, and connect only one host to a given TIA Portal process at a time.
5. To remove the pre-release, close the processes belonging to that installation and remove its folder.
