# v4.0.0-beta.2: second 4.0 pre-release draft

This is the draft for the next 4.0 pre-release. Download it by hand from its GitHub pre-release page when published;
it will not be marked as the latest release or offered to 3.3 installations. Native behavior remains unverified on a real TIA Portal.

## What is new compared with beta.1

- **Workbench text.** The P8-80e text review improves labels and guidance across the Workbench.
- **Sensitive-value digests.** The P8-83b fix keeps sensitive values redacted consistently in approval, plan and audit digests.
- **Release chain.** Packaging and release-record fixes support the host and PLC-worker delivery without the retired engine.
- **PLC audit fixes (P8-81d).** Imports refuse unsupported SimaticML versions instead of rewriting their headers and require
  explicit overwrite authorization. Type imports precede blocks, compile results retain native diagnostics, and V21-only
  FC/FB and related composers are withheld on V20 while release-aware UDT, tag-table and global DB builders remain available.
- **HMI audit fixes (P8-81e).** Project graphics tools are registered on all eight releases; Unified screen-item inspection is
  limited to V19–V21, and the classic tag-table/package builders are withheld on V20. HMI imports default to `overwrite=false`,
  missing folders refuse instead of falling back to the root, omitted script options preserve existing settings, and unverified
  Unified connection creation refuses with guidance.
- **Library, VCI, Safety and reflection fixes (P8-81f).** DCB library import is registered from V16. VCI uses the documented
  root-relative export directory and chooses supported formats consistently. Library and Safety writes validate prerequisites
  before changes; ambiguous reflection calls and guarded writes refuse with dedicated-tool guidance.
- **Security and optional-product fixes (P8-81g).** PUT/GET changes default to preview (`dryRun=true`); unverified security
  attributes refuse before writes. Password-policy failures retain unchanged-state evidence, credential callbacks respect their
  lifetime, and drive/SiVArc operations use release-specific admission and native feasibility checks.

## Install it next to 3.3

1. Download `TIA_MCP_Delivery_v4.0.0-beta.2_<date>.zip` and its `.sha256` from the GitHub pre-release and check the SHA-256.
2. Unpack it into a new folder, for example `C:\TIA_MCP_4.0.0-beta.2`. Do not unpack it over the 3.3 installation and do not run the
   3.3 updater on it. Each installation keeps its own data and logs when its folder is writable.
3. Start `TiaOpenness.exe` from the new folder and use the environment check. Point a separate MCP client entry at the new folder;
   keep the 3.3 entry for your normal work. See [configuration](../getting-started/configuration.md).
4. Use copies of your TIA projects. Do not connect the 3.3 and the 4.0 hosts to the same TIA Portal process at the same time.
5. To remove the pre-release, close its processes and delete its folder; the 3.3 installation is not changed.

## Report problems

Open an issue with the [pre-release report form](https://github.com/asckye/TIA_Portal_Openness_MCP/issues/new?template=prerelease_report.md)
and include:

- the package name, the TIA Portal version with its update, and the release key (`14sp1` to `21`);
- the item number from the "Not verified on a real TIA Portal" list below, if the report is about one of its items;
- the tool call with its arguments (remove passwords and keys) and the complete result envelope;
- what you expected and what TIA Portal shows, and whether the project was saved;
- the Workbench audit or diagnostics export for the request ID (the diagnostics folder is `data\diagnostics` in the installation
  folder, or `%LOCALAPPDATA%\TiaMcp\diagnostics` when that folder is not writable). Do not attach customer projects, credentials or
  unredacted logs.

Every item in the list below has a number. When you check one, give its item number and say whether it passed; a passed item is as
useful as a failed one.
