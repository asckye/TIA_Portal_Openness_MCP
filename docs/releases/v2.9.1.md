## 判断（2026-09-30 校正）

- 历史记录报告 **`EVENT_PROCESSTERMINATION_SELF` + 退出码 -1**。[Microsoft 的说明](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/registry-entries-for-silent-process-exit)区分自身退出与被其他进程终止；这个分类不说明应用为什么退出，不能仅凭它排除内存不足、内部异常或共享文件夹操作的间接影响。此前对此作出的排除判断撤回。
- **未编译的改动 + 查询返回旧引用 + 随后 TIA 退出** 是已记录的先后关系。交叉引用信息不一致是调查假设；尚无 TIA 日志、转储或逐个原生调用记录证明后台刷新访问了被删对象，也不能保证编译后不再崩溃。
- 表内两处带 `Z` 的时间表示相互矛盾，原始事件 XML 尚未在本次核对，不应据此确定 UTC 偏移。9 月 20 日的另一次退出也不能直接归为同一根因。
- 官方提供独立的“重建交叉引用信息”操作，不能将普通编译等同于这项重建。本轮官方资料、GitHub 修复与部署状态见 [2026-09-30 调查](../development/cross-reference-investigation-20260930.md)。本节校正不改变下面保留的 v2.9.1 历史实现和测试结果。

## 怎么查实（维护者可做）

1. **TIA 自己的日志**：在虚拟机上找 03:42:30–03:43:00 改动过的文件：`Get-ChildItem "C:\ProgramData\Siemens\Automation", "$env:LOCALAPPDATA\Siemens\Automation", "$env:APPDATA\Siemens\Automation" -Recurse -File -ErrorAction SilentlyContinue | Where-Object { $_.LastWriteTime -ge '2026-09-21 03:42:00' -and $_.LastWriteTime -le '2026-09-21 03:43:30' }`——TIA 的致命错误通常会在自己的 log / trace 里留“Fatal”“Exit”“CrossReference”字样。
2. **核对事件日志**：先用原始事件 XML 的 UTC 时间对齐窗口，再检查 `Application Error` 1000、`Windows Error Reporting` 1001、`.NET Runtime` 1026、`ProcessExitMonitor` 3000，以及系统日志 `Resource-Exhaustion-Detector` 2004。不预设有无；单个事件缺失不能排除相应原因。[取证脚本](../../scripts/diagnostics/Collect-TiaExitEvidence.cmd)只读取本机最近 24 小时的这些记录。
3. **受控复现（`项目1`，可丢）**：建 `MCP_XR_FB` + 其 IDB + 调它的 `MCP_XR_FC`，`CompileSoftware`；用 `GenerateBlocksFromExternalSource`（Override）重导一个不再调 IDB 的 FC 和一个结构不同的 IDB，**不编译**，然后 `GetCrossReferences MCP_XR_FB_IDB`（2.9.1 会拒绝——要复现得用 2.9.0 或在 TIA 里手工看交叉引用）；再做一遍中间加 `CompileSoftware`。TIA 退出与否分别记录。做之前先保存工程、确认虚拟机 TIA 可以随便重启。
