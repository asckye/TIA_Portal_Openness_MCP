# v4.0.0 — Draft

This is an unpublished draft; its CHANGELOG entry is added in the release commit, because the delivery check compares the newest CHANGELOG entry with the packaged version. Version 4.0 is a breaking change to MCP tool names, input schemas, result envelopes, and the installed product layout. It does not provide 3.x tool aliases or an input conversion layer.

## Changes

- Tool names are normalized by operation and domain, and equivalent guide and recipe lookups use **GetToolUsage**. This makes names more consistent and removes duplicate discovery entry points. The generated [release-key migration tables](../releases/v4.0.0-tool-migration.md) compare each archived 3.x catalog with its V4 baseline and list every old name with its destination, including unchanged names. They also mark merged, withdrawn and added tools and parameter changes, including JSON-string inputs replaced by typed objects or arrays.
- Inputs use the types in each tool's V4 schema, so clients can validate and send object structure without JSON-string encoding. V4-only safety parameters are not advertised while their behavior policy remains **current**.
- Results use one schema-version-4 envelope for direct calls, **CallTool**, batches, and CLI output so status, errors, and partial or unknown outcomes have one shape. **structuredContent** and the text representation contain the same envelope; **CallTool** does not wrap a successful target result in another JSON string. See [response and error rules](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/response-and-errors.md).
- All eight releases use the same MCP host. Each release starts **TiaMcp.FoundationHost.exe --release-key &lt;key&gt;** from its own runtime folder, and the host starts a per-release Openness worker: the PLC worker on V14 SP1–V19 and the V20/V21 engine in worker mode on V20/V21. Tools common to all eight releases share one implementation, input schema and usage; a session is bound with **ConnectPortal** and then **AttachOpenProject** on every release. Tools that exist only on V20/V21 keep their V4 names and input schemas. In the V20/V21 worker, shared and V20/V21-only operations use one TIA connection on one MTA owner thread; V14 SP1–V19 workers keep their STA thread.
- Every MCP session has its own worker. Over stdio that is one worker; over HTTP each live session has one, so plan client concurrency by worker memory and TIA instances. A session's disconnect, fault, restart, staging and export handles do not affect other sessions, and ending the session ends its worker. The host binds every worker to a Windows job object, so workers also end when the host is terminated; a TIA Portal instance a worker started keeps running. The HTTP host serves **/mcp/ready** (same Bearer authentication as MCP calls) and reports **fileVersion** in **/mcp/health** on every release.
- Every release leases the selected TIA process to one MCP owner. Attaching to an instance reserved by another live MCP session, or one whose previous owner was interrupted during a native call or left an unknown outcome, is refused with the lease reason as precondition text; an owner that ended while idle is taken over (see the lease rules below). Tools that need a connected TIA process are refused with **PRECONDITION_FAILED** naming **ConnectPortal** when no process is connected, and the session stays usable.
- After a write with an unknown outcome, the session refuses further native calls with **SESSION_RESET_REQUIRED** (`previous-outcome-unknown`) before approval and before Openness. Only results that crossed a native call lock the session. Recovery is the same on every release: inspect TIA, then call **DisconnectPortal**. An idle worker detaches without saving or closing (on V20/V21 it also releases the lease); a busy, timed-out or lost worker is terminated and the reply says TIA must be restarted. Then start a new MCP session and call **ConnectPortal** and **AttachOpenProject** again; never replay the failed request.
- The V20/V21 worker channel has one timeout policy: 120 s by default, 300 s for the first attach of a worker generation, and 30 minutes for compile, download/upload, import/export, archive and library updates. **--worker-timeout-config** or **TIA_MCP_WORKER_TIMEOUTS** override these budgets. Cancellation before dispatch returns **CANCELLED**; after dispatch the host waits for the real result. Requests over the 1 MiB frame are refused before dispatch, oversized replies are kept as export handles, and progress reaches the caller's progress token. Worker exit, hang, malformed frames or TIA process loss fault the worker generation with an unknown outcome; recover with **DisconnectPortal** or an explicit **RestartOpennessWorker**, then bind again. **RestartOpennessWorker** detaches an idle worker cleanly before starting the new generation; a faulted worker keeps its lease and reports **requiresTiaRestart**.
- V20/V21 advertise a 73-tool lite profile by default: the 67 shared Foundation tools also advertised on V19 before the phase 8 port below, plus **FindTools**, **CallTool**, **ListToolCategories**, **PreviewToolCall**, **GetOpennessWorkerStatus** and **RestartOpennessWorker**. **--profile full** or **TIA_MCP_PROFILE=full** advertises the full catalog; **FindTools** and **CallTool** reach it from the lite profile.
- **ConnectProject** (3.x **ConnectToProject**) is withdrawn on V20/V21 as a duplicate of **ConnectPortal** followed by **AttachOpenProject**. The other V20/V21 lifecycle tools (**ConnectIsolatedPortal**, **SaveProjectCopy**, **RetrieveProjectArchive**, **ManageMultiuserSession** and **BuildProjectScaffold**) keep their V4 records and publish their portal, project and lease into the same shared session, so the Foundation and engine sides cannot hold different bindings. The project lifecycle tools on every release are **ConnectPortal**, **AttachOpenProject**, **OpenProject**, **CreateProject**, **SaveProject**, **CloseProject**, **DisconnectPortal**, **GetSessionState**, **ListPortalProcessProjects** and **GetPortalConnectionReadiness**.
- Writes are checked before they reach the Workbench. With approval enabled, a write first runs its own preview with the same arguments; a refusal is returned without an approval request, a preview that reports no effect returns without approval, and the approved call is checked again before it runs. Previews (**dryRun: true** or **mode: preview**) never wait for approval.
- Refusals before an operation are typed and leave the session usable: argument and precondition errors are **INVALID_ARGUMENT** or **PRECONDITION_FAILED** with the parameter name, precondition messages written by this project are passed through on every release, missing caller files are **INVALID_ARGUMENT**, and caller input files that cannot be read are refused before the operation. Project paths are only checked for existence, so opening a project file that TIA holds open no longer reports an unknown outcome. **INVALID_ARGUMENT**, **PRECONDITION_FAILED**, **SESSION_RESET_REQUIRED** and **CONFIRMATION_REQUIRED** results carry a **RECOVERY_GUIDANCE** warning with the **GetToolUsage** lookup and, when one fits, example arguments for the connected release.
- Import, project and directory paths are passed to Openness as normalized full paths, so either slash works. A single XML import with **overwrite: false** refuses an object that already exists before the native call. Creating a PLC tag or user constant refuses a symbol that already exists in any tag table of that PLC and names the table. V20/V21 import and export tools check the file format, an existing parent directory and a new target before the native call; an export exception that wrote nothing is **NATIVE_OPERATION_FAILED** with the native message instead of an unknown outcome.
- On V20/V21, a tool that only writes files and whose native call reports an explicit error or failure state (for example alarm-text, CAx, document and unit exports and folder downloads) returns **NATIVE_OPERATION_FAILED** without locking the session; imports, uploads and downloads that may have changed the project still return an unknown outcome. Both carry the native state, the log path, the native messages, and whether the target file exists and its size.
- **SaveProjectCopy** (V20/V21) is TIA Save As: the open project and the MCP binding switch to the new location, unsaved changes are saved into the new copy, and the original project file keeps its last saved state. It is classified **SESSION** like **SaveProject** and **CloseProject**, and its result reports **previousProjectFile** and **newProjectFile**.
- Two TIA Portal crashes found in the V20 VM rounds are guarded. SiVArc block tools accept only FB and FC blocks. On V20/V21, CFC chart protection and CFC exports are refused before any CFC call because the API offers no safe chart inventory; CFC imports remain available.
- Native calls are journaled and flushed before they start, and **GetNativeInvocationLog** reads the journals of every session by time, so the last native call before a TIA crash can be found from a new session. **ManagePlcGitRepository** refuses a missing repository path with a typed error.
- A compilation that returns errors is a completed failure with the new **COMPILE_ERRORS** code: the error and warning counts and up to ten leaf error messages with object paths are in the error details, and the full diagnostics stay in **data**.
- **StageImportFiles**, **ListStagedImportFiles** and **CleanupStagedImportFiles** let a client on another machine send SCL, SimaticML, tag-table and UDT text to the TIA machine. Files are written under <code>&lt;bundle-root&gt;/staging/&lt;session&gt;/&lt;batch&gt;/</code> (4 MiB per file, 128 files and 32 MiB per session); the approval request shows the location and each file's name, kind, size and SHA-256. Batches record their MCP session; another session can clean a batch after its owner session or host has ended.
- **ImportPlcBlocksFromDirectory** and **ImportPlcProgramFromDirectory** accept **overwrite: true**. The preview lists each object as created or replaced in the plan hash; every replaced object is exported before the first import, and a failure stops the batch and restores known replacements in dependency order. Single XML imports make a best-effort backup and report **BACKUP_SKIPPED** when they cannot.
- Hardware catalog tools refuse an unbound session and a catalog row that does not exist before any native write, and **CreateHardwareDevice** checks the device name and the reviewed plan hash before it creates, so a repeated apply is refused.
- Openness work runs on one exclusive lane per session; tools that do not use TIA run concurrently and do not wait behind a running TIA call.
- Every release's MCP host also starts when the matching TIA Portal or its Openness files are missing or the user is outside the Siemens TIA Openness group. **InitializeEnvironment** and the Workbench environment check report the cause and repair steps, and TIA-dependent calls are refused with `RESOURCE_UNAVAILABLE` before native dispatch.
- The hardware addressing family (**GetDeviceAddressing**, **GetDeviceIpAddress**, **GetDeviceItemIoAddresses**, **SetDeviceAddress** and **SetDeviceItemIoAddress**) runs through the shared Foundation adapters on all eight releases. It is new on V14 SP1–V19, where its behavior state is **current** with L5 **NOT RUN** (family **F19** in the behavior capabilities). The V20/V21 contracts and responses of these tools are unchanged; there they remain part of the full profile.
- The workbench includes MCP write approvals, a hash-chain audit log with **tia audit verify**, a live call panel, an environment check and diagnostic bundle, single-block ladder rendering, and a whole-program book. Its views are rebuilt on one component set in light and dark themes and in Chinese and English; long call, approval and audit lists are virtualized and the audit page shows a bounded window. Generated ladder pages and the program book use the same visual style.
- **GetToolUsage** examples include the calls confirmed in VM test rounds, such as session binding with the exact project file, PLC aliases versus exact software paths, export directory rules and the export–import round trip.
- Product executables and resource lookup use one bundle-root contract so a complete installation can run outside a source checkout; data and logs follow that installation root when it is writable.

All eight releases reserve the selected TIA process with a session lease. Requests persist BUSY before native dispatch, IDLE after a known result, and UNCERTAIN after an unknown result. A live owner refuses a competing attachment. A dead owner's RELEASED or IDLE lease can be taken over; ConnectPortal reports `data.previousOwnerEndedIdle=true` for an idle takeover. An in-flight request or shutdown timeout permits worker termination. No project is saved or closed. AttachOpenProject and other portal-dependent calls without a connection return PRECONDITION_FAILED with ConnectPortal guidance, without requiring a session reset.

## Result envelope and errors

Every result has **schemaVersion**, **ok**, **data**, **error**, and **meta**. **data** contains the tool's result or is **null**; **error** is **null** or an error object. **meta** identifies the release, tool and request, and reports **outcome**, **execution**, **completeness**, behavior policy, paging and warnings.

The outcome values are **succeeded**, **rejected-before-operation**, **read-failed**, **failed**, **partial**, and **unknown**. The CLI exits with 0 for success, 2 for refusal before an operation, 3 for a read or confirmed operation failure, 4 for partial results, and 5 for an unknown write outcome. CLI syntax errors exit 64; process-level failures before a tool context exists exit 70.

The V4 error-code set is **INVALID_ARGUMENT**, **LIMIT_EXCEEDED**, **UNSUPPORTED_CAPABILITY**, **TOOL_NOT_FOUND**, **PROJECT_NOT_BOUND**, **NOT_FOUND**, **TARGET_AMBIGUOUS**, **IDENTITY_MISMATCH**, **ALREADY_EXISTS**, **CONFIRMATION_REQUIRED**, **PLAN_STALE**, **PRECONDITION_FAILED**, **OFFLINE_REQUIRED**, **AUTHENTICATION_REQUIRED**, **ACCESS_DENIED**, **SESSION_RESET_REQUIRED**, **RESOURCE_UNAVAILABLE**, **IO_FAILED**, **NATIVE_OPERATION_FAILED**, **COMPILE_ERRORS**, **CANCELLED**, **TIMEOUT**, **NOT_EXECUTED**, **PARTIAL_FAILURE**, **OUTCOME_UNKNOWN**, and **INTERNAL_ERROR**. The details each code carries and the outcome rules are defined in section 3 of the [4.0 specification](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/phase6-review.md); **COMPILE_ERRORS** carries **errorCount**, **warningCount** and the leaf **errors**.

The warning codes in **meta.warnings** are **INCOMPLETE_DATA**, **NATIVE_WARNING**, **CANDIDATE_ONLY**, **UNVERIFIED_BEHAVIOR**, **CLEANUP_FAILED**, **NATIVE_CAPABILITY_LIMIT**, **DIAGNOSTIC_WRITE_FAILED**, **APPROVAL_DISABLED**, **RECOVERY_GUIDANCE**, **BACKUP_SKIPPED**, **APPROVAL_PRECHECK_REFUSED**, and **STAGING_FOLDER_RETAINED**. A warning never turns a failure into a success.

| Entry | Bundle-relative path and role |
|---|---|
| **TiaOpenness.exe** | Root workbench launcher; starts **runtime/studio/TiaOpenness.exe**. |

The engine's former MCP host mode, including its **--isolate-openness** and **--no-isolate-openness** switches, is not a product entry point and is removed before the 4.0 release; on every release Openness already runs in the separate worker process.

The matching TIA Portal installation, Openness components, and licenses are installed separately. The Foundation hosts and the workbench use the bundled .NET 10 runtime; the per-release workers, including the V20/V21 engines, and native Openness components require .NET Framework 4.8.

The Foundation hosts, the engine workers and the CLI accept **--bundle-root &lt;absolute-path&gt;** or **TIA_MCP_BUNDLE_ROOT**. The CLI option takes precedence. If an explicitly selected root is invalid, startup reports **RESOURCE_UNAVAILABLE** and does not search another root. See [runtime layout](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/runtime-layout.md).

When writable, software data is stored under <code>&lt;bundle-root&gt;/data</code>. The main process logs are under <code>data/logs/&lt;releaseKey&gt;</code> and workbench logs under <code>data/logs/studio</code>; native diagnostics and call-panel records are under <code>data/diagnostics</code>, the audit chain is under <code>data/logs/audit</code>, and the backups of overwrite imports are under <code>data/recovery</code>. Import staging is under <code>&lt;bundle-root&gt;/staging</code>, not under **data** or **%LOCALAPPDATA%**. An explicit **TIA_MCP_DATA_DIRECTORY** selects another absolute data root and fails if it is not writable. If the bundle data directory is unavailable, the existing per-purpose fallbacks include **%LOCALAPPDATA%\TiaMcp\diagnostics** for diagnostics, **%LOCALAPPDATA%\TiaMcp\logs\audit** for the audit chain, **%TEMP%\TiaMcp\logs\<releaseKey>** for process logs, **%TEMP%\TiaMcp\logs\studio** for workbench logs, **%LOCALAPPDATA%\TiaPortalMcp** for configuration, and **%LOCALAPPDATA%\TiaOpennessStudio** for UI preferences. Configuration and UI preference files are copied from their former user directories only when the corresponding bundle file is absent; old files are left in place. Logs and diagnostics are not migrated.

The companion Python default is **%LOCALAPPDATA%\TiaMcp\ecosystem-python\Scripts\python.exe**. **TIA_MCP_PLC_TOOLS_PYTHON** overrides it. The bundle does not create or reuse a Python environment beside the installation.

The workbench can migrate existing MCP client launch commands and arguments to the selected release's 4.0 host. It asks before writing, creates a timestamped backup beside each existing configuration file, and preserves server URLs, authentication fields, and unrelated entries. If the selected host is missing, it refuses to change that client's configuration. Restart the affected clients after migration.

## Upgrade from 3.x

Upgrading from 3.x to 4.0 is a fresh install. Download the complete 4.0 ZIP and unpack it into a new folder; do not unpack it over the 3.x folder. Keep the old folder until the 4.0 workbench and clients are confirmed working. The 3.3 PowerShell updater checks its required legacy package paths before creating a backup or replacing files. Those paths are absent from the 4.0 package, so it stops with `package is incomplete` without replacing or deleting any installed file; the ZIP it downloaded stays in the installation's `.update\` folder and its extracted copy in `%TEMP%\tia-mcp-update-<process id>`, both safe to delete.

The 4.0 MCP entry points and tool names changed. Recreate each AI client's configuration from the new workbench and refresh the client's tool cache and schemas; do not reuse the 3.x launch commands. From 4.0 onward, use the bundled C# updater for subsequent releases.

| 3.3 data | 4.0 location | What to copy |
|---|---|---|
| Connection settings: `%LOCALAPPDATA%\TiaPortalMcp\` (`http-v<release>.json`, `client.json`) | Writable bundle `data\config\` | On first use, 4.0 copies these existing files when the corresponding target is absent. Keep the originals as a backup. These files are not the AI client's MCP launch configuration. |
| Workbench preferences: `%LOCALAPPDATA%\TiaOpennessStudio\ui.settings` | `data\ui\ui.settings` | 4.0 copies it on first use only when the target is absent; keep the original. |
| Approval state | 3.3 has no Workbench MCP approval settings file; 4.0 stores it in `data\config\approval.settings` | There is no 3.3 state to migrate. New 4.0 installs enable approvals by default. For a later 4.0 reinstall, copy this file while the applications are closed to retain the approval switch and timeout. |
| Process and workbench logs: `%LOCALAPPDATA%\TiaMcp\logs\<releaseKey>\` and `studio\` | `data\logs\<releaseKey>\` and `data\logs\studio\` | Logs are not migrated automatically. Keep them in place, or copy the relevant subdirectories after closing both installations; avoid overwriting existing files. |
| Audit data | 3.3 has no 4.0 approval audit hash chain; 4.0 stores it in `data\logs\audit\` | There is no 3.3 chain to migrate. When moving an existing 4.0 installation, copy the entire audit directory with all applications closed if the chain must be retained; do not copy only part of it. |

If the bundle data directory is not writable, 4.0 uses the per-purpose user-directory fallbacks described above. The updater preserves the `data` and `staging` directories during later 4.0 updates.

## Workbench write controls and diagnostics

MCP write approvals are enabled by default. With approvals enabled, MCP writes are refused while the workbench is closed; open the workbench to review a pending request, or turn approvals off in the MCP menu. Read-only MCP calls and previews do not wait for approval. **WRITE** and **ONLINE-WRITE** calls wait for approval, and so do **StageImportFiles**, **CleanupStagedImportFiles**, **SaveProject**, **SaveProjectCopy** (save-as, V20/V21) and **CloseProject**, although the tool catalog classifies these as **FILE** or **SESSION**. Other session calls such as connect, attach, open, and disconnect remain ungated. A write that its own preview refuses is returned with **APPROVAL_PRECHECK_REFUSED** and no approval request. Turning approvals off is visible in response metadata and does not remove a tool's own confirmation or plan checks.

The audit log records write requests, approvals, refusals, and outcomes; the request, decision and start/end rows of one call share the response's **requestId**. **tia audit verify** checks the audit chain. The call panel shows current calls and pending approvals. The environment page checks the local setup and can export a diagnostic bundle. Ladder rendering produces an SVG for an individual block; the program book collects rendered blocks and available check results into a self-contained HTML file.

## D1 safety-policy state

The V4 baselines report **state=current** and **l5=NOT RUN** for every D1 behavior family on all eight release keys. Where an operation is applicable, the existing 3.x behavior is included. The **UNVERIFIED_BEHAVIOR** warning remains visible. Safe-v4 candidates are present but are not selected in the shipped policy.

The families are device creation (**P6-DEVICE**), import (**P6-IMPORT**), export (**P6-EXPORT**), connect/open (**P6-SESSION**), save/close (**P6-CLOSE**), PLC paths and external sources (**P6-SOURCE**), compile (**P6-COMPILE**), and native fallback (**P6-FALLBACK**). Passing L5 for a family on a specific release can switch that accepted release/family entry to **safe-v4**; unaccepted entries remain **current**. The applicability and deferred work are recorded in the [real-machine ledger](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/reference/real-machine-ledger.md). L5 acceptance for D1 does not complete the separate product, G3/G9, or J gates.

## For MCP clients

Close the old MCP host before replacing the installation, then start a new MCP session and explicitly connect to the selected TIA process. A normal idle shutdown or an idle worker kill does not require restarting TIA. Restart that TIA instance only after an interrupted native call or an unknown outcome; a legacy ACTIVE lease cannot prove the old owner was idle and remains refused. Do not delete lease files to bypass the guard.

After upgrading, refresh the client's tool cache and read the selected release's current tool schemas. 4.0 does not register 3.x aliases; old names and JSON-string argument encodings must be replaced using the [generated migration tables](../releases/v4.0.0-tool-migration.md). Bind a session with **ConnectPortal** and **AttachOpenProject** on every release; on V20/V21, replace **ConnectProject** with that sequence.

Use **GetToolUsage** for examples for the selected release. The [tool-call examples](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/calls.json) contain per-tool arguments, and [sequences](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/sequences.json) contain ordered calls. Runnable source examples include [SCL](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/languages/FC_Add.scl), [Unified HMI JavaScript](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/languages/unified-tag-read.js), [Classic HMI VBScript](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/languages/classic-tag-read.vbs), and the [language catalog](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/languages/catalog.json).
