# v4.0.0 — Automation Engineering Workbench 4.0

## 中文

这是自动化工程工作台（适用于 TIA Portal，原 TIA Portal Openness MCP）4.0 的正式版，发布日期 2026-11-26。它在 GitHub 上设为最新版（Latest）。3.3 的自动更新器不会提供本版：从 3.3 升级请手动下载，与 3.3 并排安装，见“从 3.3 升级”。
[GitHub 发布页](https://github.com/asckye/automation-engineering-workbench/releases)

4.0 支持全部八个 TIA Portal 版本：V14 SP1、V15.1 和 V16–V21。除非写明版本，下列内容适用于全部八个版本。4.0 的 MCP 接口与 3.3 不兼容：工具名、参数和结果格式都改变了，不提供 3.x 的别名。

### 4.0 带来了什么

#### 八个版本，一套实现

- 八个版本都由同一个 MCP 宿主 `TiaMcp.FoundationHost.exe --release-key <版本键>` 提供服务，每个 MCP 会话有自己的 PLC worker 进程。V20/V21 不再使用旧引擎程序。八个版本共用工具实现、输入、用法、就绪规则和官方 API 能力表，只在工具集合和各版官方 API 的差异上不同。
- V14 SP1–V19 获得了 3.3 只在 V20/V21 上提供的大部分工具，只要该版本的 API 支持：硬件与网络、CAx/AML、PLC 组、变量和常量、实例 DB、验证导入、外部源、交叉引用、监控表、工艺对象、软件单元、库、编译设置、发现与批处理等。版本缺少 API 的动作在调用 TIA 之前返回 `UNSUPPORTED_CAPABILITY`。
- 默认公布精简的 lite 工具列表；`FindTools` 和 `CallTool` 可以调用其余工具，`--profile full` 公布完整目录。各版本的工具数：

#### 新的 MCP 接口

- 工具按操作和领域统一命名。[逐版迁移表](v4.0.0-tool-migration.md)列出每个 3.x 工具名的去向，以及合并、撤下、新增的工具和参数类型的变化。
- 参数按各工具的 schema 传入对象和数组，不再用 JSON 字符串。导出和导入参数统一为 `exportFile`、`exportDirectory`、`sourceDirectory` 和数组形式的 `devicePath`；旧别名在 5.0 之前仍可用，并给出 `DEPRECATED_PARAMETER` 警告。
- 直接调用、`CallTool` 和批处理的结果都用同一个 `schemaVersion` 4 信封，见“结果与错误”。
- `GetToolUsage` 按所连版本返回用法、示例参数和调用顺序，取代 3.x 的指南和配方查询。参数或前提错误附带 `RECOVERY_GUIDANCE`，指出本版用法和合适的示例。

#### 写入更安全

- 写入先预览后执行。许多写入工具默认只预览；执行时传入 `dryRun:false`、预览返回的计划哈希和绑定的工程文件，计划变化后须重新预览。
- 工作台人工审批默认开启：写入在工作台批准后才执行，工作台没有打开时写入被拒绝。审批前先用相同参数预览，预览拒绝的写入不生成审批请求；只读调用和预览不等待审批。
- 审计日志按哈希链记录请求、决定和结果，可用 `tia audit verify` 校验。审批卡、日志和审计对密码等凭据脱敏。
- 下载时 TIA 的对话框只按显式参数应答，例如 `allowSafetyProgramDownload`、`allowHardwareDifferences`。设备证书默认不信任（`trustDeviceCertificate=false`），通信不安全时须设 `allowNonTlsLogin: true` 才发送密码。
- 设备创建严格使用所请求的类型、版本和名称，不改用相邻固件或其他 CPU；没有精确匹配时在创建前拒绝并列出候选。
- 输入文件不接受 UNC 路径和设备路径，以免访问网络共享时泄露 Windows 凭据；读取用户提供的 XML 时禁止 DTD。

#### 会话与结果

- 先 `ConnectPortal`，再 `AttachOpenProject` 绑定工程。一个 TIA 进程同一时间只租给一个 MCP 会话；空闲的会话可以用 `takeOver` 移交。
- 结果未知只影响那一次调用，会话不会被锁定，也不必重启 TIA。`GetSessionState` 列出写入结果尚未确认的请求，保存工程时给出 `UNSETTLED_CALLS` 提示；能用读回证明的未知写入会自动结算。请先核对目标，不要自动重放。
- 长时间的调用返回 `in-progress`，之后用 `GetCallResult(requestId)` 取最终结果。worker 故障或超时后，可用 `RestartOpennessWorker` 或断开再连接恢复。TIA 弹出的对话框会记录在结果和工作台中。
- 能确定的失败返回类型化错误和去敏的西门子原因，不再一律报结果未知。编译出错返回 `COMPILE_ERRORS`，带错误数和前十条错误。

#### 工程功能

- PLC：导入后读回核对的验证导入；带备份和失败恢复的目录覆盖导入；外部源生成；`StageImportFiles` 让另一台电脑上的客户端把 SCL、SimaticML、变量表和 UDT 文本送到 TIA 所在电脑；离线的 `AnalyzePlcCrossReferences` 和原生交叉引用；软件单元（V16 起）；`ListPlcBlocks` 分页；块文档的编辑和比较。
- 版本控制工作区（V16–V21）：连接、状态和同步。连接不覆盖内容不同的已有文件；状态列出断开的映射和没有映射的工作区文件。
- SIMATIC SD 文档（V20/V21）：导出和导入，覆盖导入前核对能否保留块的属性和编号。
- HMI：Unified 对象使用绝对路径 `/组/子组/名称`，面板接口可读写；V20/V21 提供 Classic HMI 包。
- 硬件：硬件目录、精确创建、寻址工具族（八个版本），GSD 设备（V18 起）。
- 标准包和机器描述可离线使用；工作台控制工具（`ShowWorkbenchPage` 等）让客户端在工作台中显示页面、块和调用，或预填待确认的表单。

#### 工作台

- 按最终设计重做：项目、协作、MCP、客户端、检查、审计、日志和设置页面，浅色、深色和高对比度主题，中文和英文，`Ctrl+K` 命令面板。
- 环境检查给出原因和修复步骤（TIA 安装、`Siemens TIA Openness` 用户组、Openness 防火墙允许列表），`doctor --fix` 可修复用户组。诊断包遮蔽 Windows 用户名和用户目录，默认不含工程内容。
- 调用面板显示当前调用和待批请求；梯形图可输出单块 SVG，程序册把渲染的块和检查结果汇成一个 HTML 文件。
- 工作台可把现有 AI 客户端的配置迁移到 4.0 宿主，写入前确认并在原文件旁备份。随包的 C# 更新器取代 3.3 的 PowerShell 更新脚本。

#### 产品与安装

- 产品更名为自动化工程工作台（Automation Engineering Workbench）。可执行文件 `TiaOpenness.exe`、`TiaMcp.*`、Claude Code 插件 ID `tia-portal-openness-mcp` 和 MCP 服务名 `tia-portal` 保持不变，GitHub 会把旧仓库链接重定向到新地址。
- 交付包不含西门子程序集，Openness 从本机的 TIA 安装加载。工作台和宿主使用随包的 .NET 10 运行时，PLC worker 需要 .NET Framework 4.8。
- 安装目录可写时，配置、日志、审计和恢复备份都在 `<包根>\data` 中，导入暂存在 `<包根>\staging`。
- 局域网 HTTP 默认关闭，不使用访问密钥，也不加密；`--http-api-key` 会被拒绝。4.0 预发布版中的凭据保管库已撤下，以 `vault:` 开头的值被拒绝。

### 结果与错误

每个结果都包含 `schemaVersion`、`ok`、`data`、`error` 和 `meta`。`meta.outcome` 为 `succeeded`、`rejected-before-operation`、`read-failed`、`failed`、`partial` 或 `unknown`。命令行成功返回 0，操作前拒绝返回 2，读取或已确认的操作失败返回 3，部分结果返回 4，写入结果未知返回 5；语法错误返回 64，建立工具上下文前的进程故障返回 70。

错误码包括 `INVALID_ARGUMENT`、`LIMIT_EXCEEDED`、`UNSUPPORTED_CAPABILITY`、`TOOL_NOT_FOUND`、`PROJECT_NOT_BOUND`、`NOT_FOUND`、`TARGET_AMBIGUOUS`、`IDENTITY_MISMATCH`、`ALREADY_EXISTS`、`CONFIRMATION_REQUIRED`、`PLAN_STALE`、`PRECONDITION_FAILED`、`OFFLINE_REQUIRED`、`AUTHENTICATION_REQUIRED`、`ACCESS_DENIED`、`RESOURCE_UNAVAILABLE`、`IO_FAILED`、`NATIVE_OPERATION_FAILED`、`COMPILE_ERRORS`、`CANCELLED`、`TIMEOUT`、`NOT_EXECUTED`、`PARTIAL_FAILURE`、`OUTCOME_UNKNOWN` 和 `INTERNAL_ERROR`。警告不会把失败变成成功。各错误的详情见[设计规范](https://github.com/asckye/automation-engineering-workbench/blob/master/docs/standards/design.md)，处理方法见[调用失败时如何处理](../troubleshooting/errors.md)。

### 自 rc.8 以来的变化

本版修复 rc.8 真机复验发现的 LOW 问题，不再发布 rc.9。工具名称、参数名和参数类型没有变化；连接工作区的结果多了一个 `reused` 计数，部分消息文字改变。

- **设备创建的预览不再写出调用者没有传的 `family`。** `CreateDevice` 和 `CreateHardwareCatalogDevice` 的预览和结果只在调用者传入 `family` 时列出它，HMI 面板不再显示 `S7-1500`。查找目录时使用的系列没有改变。
- **同步汇总按原因给出建议（V16–V21）。** 对象因块不一致而未验证时，汇总点名这些块，建议先编译再同步；“备份后删除过期的工作区文件再同步”只用于比较导出内容不同或无法证明内容的对象。rc.8 对不一致的块也给出删除文件的建议，那会删掉正确的文件。
- **`PatchPlcBlockDocument` 的 `changes=[]` 给出正确的错误。** 返回 `INVALID_ARGUMENT`，写明 `changes` 至少需要一项。所有低于 `minItems` 的数组参数都写出参数名和所需数量；不是数组的值仍报类型错误。
- **连接工作区报告复用的已有文件（V16–V21）。** 复用的对象在结果中写作 `mapped | reused existing file`，计入新的 `reused` 计数，不再算作导出（`exportsIssued`）。成功的对象中有复用时，部分失败的消息写作 “Some objects were mapped to the workspace.”。
- **证书模板的提示包括 V21。** 提示改为该限制已知出现在 S7-1500 固件 V2.9 和 TIA V17 及更高版本上。
- **状态列出导入断开的映射和没有映射的文件（V16–V21）。** 覆盖导入或 SD 覆盖导入断开了映射时，`GetVersionControlStatus` 和同步一样逐个点名断开的映射，并列出工作区中没有映射引用的 XML 文件（消息最多列 20 个，`evidence.unmappedFiles` 给出完整清单，最多 200 个）。重新连接后的重复映射，每一行显示各自的状态，不再都写成断开的那条的状态。

完整变化见[更新日志](../../CHANGELOG.md)。

### 已知限制

- **局域网 HTTP 不认证且是明文。** MCP 连接不使用密码或访问密钥，能访问 HTTP 端点的设备都能调用工具，能监听链路的人能读到工程数据和 PLC 密码。HTTP 默认关闭；只在可信局域网或虚拟机的仅主机网络中启用。
- **作为工具参数传入的密码会离开本机。** 密码由 AI 客户端组成，会到达模型服务商并留在客户端的对话记录中。本产品只在自己的审批卡、日志和审计中脱敏。不要在 AI 对话中输入重要密码，或在使用后更换。
- **更新包没有签名。** 更新器用同一发布中的 SHA-256 核对 ZIP，不能防御 GitHub 账户被控制。
- **更新不是整目录切换。** 更新器核对更新包后逐个替换文件；更新中断时，安装可能只替换了一部分。遇到这种情况，请从发布页下载完整包，解压到新文件夹。
- **关闭审批后，删除也不再确认。** 关闭普通写入审批后，只有向真实设备的在线写入和放弃更改的 `CloseProject` 仍须由人确认。
- **名称像凭据的值在审批卡上被遮蔽。** 审批卡按参数名脱敏，名称像凭据的用户数据（例如变量 `Door_Key`、`TokenCount`）的写入值也显示为圆点。
- **没有连接过真实 PLC。** 在线、下载、强制和仿真执行都未经真机验证。
- **本版的修复没有在虚拟机上重跑。** 见“真机验证”。
- **连接期间另一进程创建的文件仍可能被覆盖。** 连接在原生写入前检查目标文件；如果另一进程在 TIA 写入期间创建同名文件，TIA 仍可能覆盖它。连接完成之前，只让 TIA 写入该工作区。
- **断开的映射不能用工具删除。** 覆盖导入后重新连接，旧映射仍留在工作区；状态会点名它，但没有删除它的工具。
- **在 TIA 之外改动或删除工作区文件后的状态尚未在真机上验证。** 原地添加变量后的状态已验证。
- **SIMATIC SD 不是无损格式。** 即使通过核对，报警、监控、SiVArc 和成员属性仍可能丢失。`verifyDocumentReadback` 只比较 `.s7dcl` 和 `.s7res` 文本（`sdDocumentsMatch`）。V21 的 SD 导出不带块编号，作为新块导入时由 TIA 分配编号，只有通用警告。
- **V20 上启动 OB 的 SD 导出需要 V20 Update 4 和 SimaticSdEnabler。** 否则 TIA 拒绝导出，结果为确定的失败并带西门子原文。
- **监控表的条目读写需要 V17 及更高版本。** V14 SP1–V16 上的监控表工具返回部分结果并说明原因，不尝试连接 PLC。
- **结果判定尚未统一。** 各工具共用的宿主默认判定规则移到 4.1。普通情况仍可能报结果未知，也可能在没有证据时报确定失败。
- **一些失败的写入仍报结果未知。** 包括删除块、类型和变量表，从源生成块（TIA 明确说明的生成失败除外），以及 `ManagePlcGitRepository` 的暂存和提交。名称或版本没有变化，不足以证明没有副作用。
- **导入遇到未能识别的异常时报结果未知。** 例如报警类、报警文本列表和 OPC UA 接口的文件格式错误。
- **嵌套 UDT 旧值的核对有条件。** 只有标准导出可用时才能判为一致。
- **被拒导入的证据有边界。** 证据只覆盖目标块和目标组的块名，不包括其他对象、UDT 和库。
- **验证导入有未覆盖的情况。** UDT 展开内部的成员属性和注释不参与比较，新文档省略的块属性和成员设置从原块恢复。UDT 数组的展开不做归一化，未展开 UDT 实例的标志没有恢复。
- **工作区导出的判定有限制。** 快照遇到重解析点、超过 10,000 项或无法读取时报结果未知，快照之后的延迟写入和时间戳精度内的等长改写可能看不到。没有对象导出成功、但已保留映射或写入了文件时报 `PARTIAL_FAILURE`，实际失败数见 `data.evidence.failed`。
- **带级别标签的诊断可能被整体遮蔽。** `[Error]` 等标签后的文字若含有像凭据的内容或 JSON 片段，整段显示为圆点，即使没有秘密。
- **S7-1500 固件 V2.9 的证书模板在 TIA V17 及更高版本上不可用。** 这是 TIA 的已知限制，rc.8 复验在 V17–V21 上再次记录。
- **`ExportDeviceAml` 不能导出部分 HMI 设备。** 这是 TIA 的限制：V19–V21 上 TIA 报 TypeIdentifier 错误并留下部分文件，V15.1–V18 上 TIA 的导出返回失败。V17 导入 HMI AML 报 “wrong type”，原因尚未查明。
- **`CreateDevice` 仍拒绝创建 TP700 面板（V18–V20）。** 拒绝给出原因。在 V18 和 V19 上，`CreateHardwareCatalogDevice` 的关键字方式可用。
- **OPC UA 的 ReferenceNamespace 不能新建。** `ImportOpcUaInterface` 选择 `ReferenceNamespace` 新建时总是被拒绝。
- **V14 SP1、V15.1 和 V16 不能带安全程序密码编译。** 这三个版本的 Openness 没有对应接口，带密码的编译在审批前返回 `UNSUPPORTED_CAPABILITY`；请在 TIA 中编译安全程序。
- **V21 OPC UA 报警类型更新可能让 TIA 退出。** 在带界面的 TIA V21 上用 `ManageUnifiedOpcUaAlarmType` 修改 nodeId 时，TIA 进程退出，结果为 `OUTCOME_UNKNOWN`。原因尚未查明，探查移到 4.1；请先保存工程，或在 TIA 中手动修改。
- **V21 交叉引用只在无界面 TIA 上验证过。** 带界面实例的检查移到 4.1。
- **V19–V21 拒绝新建 Unified 脚本模块。** 请在 TIA 中创建，再预览并执行 `SetUnifiedGlobalScript` 的 `action=update`。
- **V21 LAD 生成有限制。** 以触点开头的扇出分支被拒绝；梯级中的上升沿、下降沿触点返回 `edge-contact-unverified`。
- **批处理、文档、交叉引用和目录工具不接受短 PLC 名。** 请传入完整的软件路径。
- **只读监视计划不接受变量表中的全局变量。** `PlanOnlineReadOnlyMonitoring` 拒绝这类变量并说明原因。
- **大的用法条目只有一个拆页。** `GetToolUsage` 只把 `BuildAndImportPlcArtifact` 的完整输入定义移到后续页面。
- **多数示例没有在真机上运行过。** 真机标记只覆盖部分 V18–V21 示例。
- **工作台尚未在真机上逐页手动检查。** 它经过了自动化界面测试和离线截图检查。
- **工作台配置页的检测可能让界面短暂停顿。** 检测 AI 客户端和 TIA 安装仍在界面线程上进行。
- **“关于”页的图标在高对比度下仍是彩色的。** 窄窗口中的调用详情以 520 像素宽的抽屉打开。
- **仍未解决的 LOW 问题。** `GetHardwareFeatures` 把一些功能列为提供，读取时却报不存在；`ProbeHardwareHmiConnectionWhitelistedServices` 报接口候选不可用；`GetSoftwareTree` 把 PID 的系统 UDT 列在用户类型下；`FindTools` 首页很大时分页完整性自相矛盾（V15.1）；TIA 拒绝 `CreateDevice` 后，`execution` 仍写 `not-started`；`PatchPlcBlockDocument` 的部分错误不填 `details.parameter`。V16–V19 同步时连接在最终比较中断开，提示会写"重新编译"而不是中断；工作区根路径含 Windows 不允许的字符时，`GetVersionControlStatus` 整体失败，而不是报告"无法检查"。这两项计划在 4.0.1 修复。
- **V14 SP1–V19 的 worker 用 STA。** V20/V21 使用 MTA。

3.3 用户会遇到的行为变化：

- **工具名、参数和结果都变了。** 按[迁移表](v4.0.0-tool-migration.md)替换旧工具名和 JSON 字符串参数，按 V4 信封读取结果：先看 `ok`，再看 `meta.outcome`，失败时看 `error.code` 和 `error.details`。
- **写入需要人工审批。** 审批默认开启，写入在工作台批准后执行；工作台没有打开时写入被拒绝。可以在工作台关闭审批，在线写入真实设备和放弃更改的 `CloseProject` 仍须由人确认。
- **写入先预览。** 许多写入工具默认只返回计划；执行时传入 `dryRun:false` 和预览给出的计划哈希。
- **会话要先绑定。** 先 `ConnectPortal` 再 `AttachOpenProject`；V20/V21 的 `ConnectProject` 已撤下。同一个 TIA 进程同一时间只属于一个 MCP 会话。
- **HTTP 没有访问密钥。** 删除启动命令中的 `--http-api-key`，或在工作台重新生成客户端配置。只在可信网络中启用 HTTP。
- **参数更严格。** `expectedProject` 是工程名称，像路径的值被拒绝，需要文件身份的工具用 `expectedProjectFile`（绝对路径）。路径一律为绝对路径。`ListPlcBlocks` 分页返回，用 `meta.paging.nextCursor` 继续读取。输入文件不能用 UNC 路径或设备路径。
- **在线和下载更保守。** `trustDeviceCertificate` 默认为 `false`；下载中的对话框要用 `allow*` 参数明确允许；`DownloadPlc` 之前先 `DisconnectOnlinePlc`。
- **命令行只保留部分命令。** `doctor`、`audit verify`、`schema`、`version`、`config`、`install-plc-tools` 和 `help` 保留；`gen`、`patch`、`describe`、`compile`、`export`、`import`、`prewarm` 改用 MCP 工具。
- **数据位置变了。** 安装目录可写时，数据在 `<包根>\data`。第一次使用时，只有目标不存在才从 3.3 的用户目录复制连接设置（`%LOCALAPPDATA%\TiaPortalMcp\`）和工作台偏好（`%LOCALAPPDATA%\TiaOpennessStudio\ui.settings`），旧文件保留；日志不自动迁移。4.0 的后续更新保留 `data` 和 `staging`。

### What 4.0 brings

#### Eight releases, one implementation

An action the release's API lacks returns `UNSUPPORTED_CAPABILITY` before any call into TIA.

#### A new MCP interface

- Tool names follow one scheme by operation and domain. The [per-release migration tables](v4.0.0-tool-migration.md) list where every 3.x tool name went, and which tools were merged, withdrawn or added, and how argument types changed.
- Arguments are objects and arrays as each tool's schema defines them, not JSON strings. Export and import arguments are `exportFile`, `exportDirectory`, `sourceDirectory` and an array `devicePath`; the old aliases keep working until 5.0 with a `DEPRECATED_PARAMETER` warning.
- Direct calls, `CallTool` and batches return one `schemaVersion` 4 envelope; see "Result envelope and errors".
- `GetToolUsage` returns usage, example arguments and call order for the connected release, replacing the 3.x guide and recipe lookups. Argument and precondition errors carry `RECOVERY_GUIDANCE` that points to the release's usage and a fitting example.

#### Safer writes

- Writes are previewed before they run. Many write tools only preview by default; to apply, pass `dryRun:false`, the plan hash from the preview and the bound project file. A changed plan needs a new preview.
- Workbench approval is on by default: a write runs only after a person approves it in the Workbench, and writes are refused while the Workbench is closed. A write first runs its own preview with the same arguments, and a write that its preview refuses creates no approval request. Reads and previews never wait for approval.
- The audit log records requests, decisions and outcomes in a hash chain that `tia audit verify` checks. Approval cards, logs and the audit redact passwords and other credentials.
- TIA download prompts are answered only through explicit arguments such as `allowSafetyProgramDownload` and `allowHardwareDifferences`. Device certificates aren't trusted by default (`trustDeviceCertificate=false`), and a password is sent over a connection that isn't secure only with `allowNonTlsLogin: true`.
- Device creation uses exactly the requested type, version and name, without stepping to another firmware or CPU; without an exact match it's refused before anything is created, with the catalog candidates listed.
- Input files can't be UNC or device paths, so that looking up a network share can't leak Windows credentials. User-supplied XML is read with DTDs prohibited.

#### Sessions and outcomes

- Bind a project with `ConnectPortal` and then `AttachOpenProject`. A TIA process is leased to one MCP session at a time; an idle session can hand it over with `takeOver`.
- An unknown outcome affects only that call. The session isn't locked, and TIA doesn't need a restart. `GetSessionState` lists the requests whose write outcome isn't confirmed, and saving the project warns with `UNSETTLED_CALLS`; unknown writes that a read-back can prove are settled automatically. Check the target before repeating a call, and never replay it automatically.
- A long call returns `in-progress`; read the final result later with `GetCallResult(requestId)`. After a worker fault or timeout, recover with `RestartOpennessWorker` or by disconnecting and connecting again. Dialogs that TIA opens are recorded in the result and in the Workbench.
- Failures that can be decided return typed errors with the sanitized Siemens reason instead of an unknown outcome. Compile errors return `COMPILE_ERRORS` with the counts and the first ten errors.

#### Engineering features

- PLC: verified import that reads the result back; directory overwrite imports with backups and recovery on failure; generation from external sources; `StageImportFiles` to send SCL, SimaticML, tag-table and UDT text from a client on another machine; offline `AnalyzePlcCrossReferences` and native cross-references; software units (V16 and later); paged `ListPlcBlocks`; editing and comparing block documents.
- Version-control workspaces (V16–V21): connect, status and synchronize. Connect never overwrites an existing file with other content, and status names disconnected mappings and workspace files without a mapping.
- SIMATIC SD documents (V20/V21): export and import, with an override check before the write that the block's attributes and number can be kept.
- HMI: absolute Unified object paths `/Group/Sub/Name` and faceplate interfaces; Classic HMI packages on V20/V21.
- Hardware: the hardware catalog, exact creation, the addressing tool family on all eight releases, and GSD devices (V18 and later).
- Standard packages and machine descriptions work offline. Workbench control tools such as `ShowWorkbenchPage` let a client show pages, blocks and calls in the Workbench, or prefill a form for the user to confirm.

#### Workbench

- Rebuilt to the final design: Project, Collaboration, MCP, Clients, Checks, Audit, Logs and Settings pages, light, dark and high-contrast themes, Chinese and English, and a `Ctrl+K` command palette.
- The environment check gives causes and repair steps (TIA installation, the `Siemens TIA Openness` user group, the Openness firewall allow list), and `doctor --fix` repairs the group membership. Diagnostic bundles mask Windows user names and profile paths and leave out project content by default.
- The call panel shows current calls and pending approvals. Ladder rendering produces an SVG for one block, and the program book collects rendered blocks and check results into one HTML file.
- The Workbench can move existing AI client configurations to the 4.0 host; it asks first and keeps a backup next to each file. The bundled C# updater replaces the 3.3 PowerShell updater.

#### Product and installation

- The product is renamed Automation Engineering Workbench. The executables `TiaOpenness.exe` and `TiaMcp.*`, the Claude Code plugin ID `tia-portal-openness-mcp` and the MCP server name `tia-portal` keep their names, and GitHub redirects old repository links.
- The package contains no Siemens assemblies; Openness loads from the local TIA installation. The Workbench and the host use the bundled .NET 10 runtime, and the PLC workers need .NET Framework 4.8.
- When the installation folder is writable, configuration, logs, the audit and recovery backups live under `<bundle-root>\data`, and import staging under `<bundle-root>\staging`.
- LAN HTTP is off by default, uses no access key and isn't encrypted; the host refuses `--http-api-key`. The secret vault of the 4.0 pre-releases is gone, and values that start with `vault:` are refused.

### Result envelope and errors

Every result has `schemaVersion`, `ok`, `data`, `error` and `meta`. `meta.outcome` is `succeeded`, `rejected-before-operation`, `read-failed`, `failed`, `partial` or `unknown`. The CLI exits with 0 for success, 2 for a refusal before an operation, 3 for a read or confirmed operation failure, 4 for partial results and 5 for an unknown write outcome; syntax errors exit 64, and process failures before a tool context exists exit 70.

The error codes are `INVALID_ARGUMENT`, `LIMIT_EXCEEDED`, `UNSUPPORTED_CAPABILITY`, `TOOL_NOT_FOUND`, `PROJECT_NOT_BOUND`, `NOT_FOUND`, `TARGET_AMBIGUOUS`, `IDENTITY_MISMATCH`, `ALREADY_EXISTS`, `CONFIRMATION_REQUIRED`, `PLAN_STALE`, `PRECONDITION_FAILED`, `OFFLINE_REQUIRED`, `AUTHENTICATION_REQUIRED`, `ACCESS_DENIED`, `RESOURCE_UNAVAILABLE`, `IO_FAILED`, `NATIVE_OPERATION_FAILED`, `COMPILE_ERRORS`, `CANCELLED`, `TIMEOUT`, `NOT_EXECUTED`, `PARTIAL_FAILURE`, `OUTCOME_UNKNOWN` and `INTERNAL_ERROR`. A warning never turns a failure into a success. The [design standard](https://github.com/asckye/automation-engineering-workbench/blob/master/docs/standards/design.md) defines the details of each code, and [what to do when a call fails](../troubleshooting/errors.md) explains how to handle them.

### Changes since rc.8

This release fixes the LOW findings of the rc.8 real-machine retest; there is no rc.9. Tool names, argument names and argument types haven't changed; connect results gain a `reused` count, and some message texts changed.

- **Device creation previews no longer show a `family` the caller didn't pass.** `CreateDevice` and `CreateHardwareCatalogDevice` previews and results list `family` only when the caller passed it, so HMI panels no longer show `S7-1500`. The family used for the catalog lookup hasn't changed.
- **The synchronization summary gives advice per reason (V16–V21).** When objects aren't verified because a block is inconsistent, the summary names those blocks and says to compile them and synchronize again. The advice to back up and remove a stale workspace file is kept only for objects whose comparison export differs or can't prove the content. In rc.8 it also appeared for inconsistent blocks, where following it would delete a correct file.
- **`PatchPlcBlockDocument` with `changes=[]` reports the right error.** It returns `INVALID_ARGUMENT` saying that `changes` needs at least one change. Every array argument below its `minItems` names the argument and the required count; a value that isn't an array still reports the type.
- **Connect reports reused files (V16–V21).** A reused object reads `mapped | reused existing file` in the result and counts in a new `reused` count, not as an export (`exportsIssued`). When reuses are among the successes, a partial failure says "Some objects were mapped to the workspace."
- **The certificate-template hint includes V21.** It now says the limit is known on S7-1500 firmware V2.9 with TIA V17 and later.
- **Status names mappings that an import disconnected, and files without a mapping (V16–V21).** When an overwrite or SD override import disconnects mappings, `GetVersionControlStatus` names each one as synchronization does, and lists workspace XML files that no mapping references (the message names up to 20; `evidence.unmappedFiles` holds the list, up to 200). After a reconnect, each line of a duplicate mapping shows that mapping's own state instead of repeating the disconnected one.

See the [changelog](../../CHANGELOG.md) for every change.

### Known limitations

- **LAN HTTP has no authentication and isn't encrypted.** MCP connections use no password or access key, so any device that can reach the HTTP endpoint can call tools, and anyone who can listen on the link can read project data and PLC passwords. HTTP is off by default; turn it on only in a trusted LAN or a host-only network of a virtual machine.
- **A password passed as a tool argument leaves this computer.** The AI client composes it, so it reaches the model provider and stays in the client's conversation history. This product masks it only in its own approval cards, logs and audit. Don't type important passwords into an AI conversation, or change them after use.
- **Update packages aren't signed.** The updater checks the ZIP with the SHA-256 from the same release, which doesn't protect against a compromised GitHub account.
- **An update doesn't switch the whole folder.** The updater checks the package and then replaces files one by one; an interrupted update can leave a partly replaced installation. In that case, download the full package from the releases page and extract it to a new folder.
- **With approvals off, deletions aren't confirmed either.** When ordinary write approvals are off, only online writes to real devices and `CloseProject` that discards changes still need a person to confirm.
- **Values whose names look like credentials are masked on approval cards.** Approval cards mask by argument name, so the written values of user data with such names (for example the tags `Door_Key` or `TokenCount`) are shown as dots too.
- **No real PLC has been connected.** Online, download, force and simulation runs haven't been verified on a real machine.
- **The fixes in this release haven't run again on a virtual machine.** See "Real-machine verification".
- **A file that another process creates during the connect can still be overwritten.** Connect checks the target file before the native write. If another process creates a file with the same name while TIA writes, TIA can still overwrite it. Until the connect finishes, let only TIA write to the workspace.
- **No tool deletes a disconnected mapping.** After an overwrite import and a reconnect, the old mapping stays in the workspace; the status names it, but no tool deletes it.
- **The status after workspace files are changed or deleted outside TIA hasn't been verified on a real machine.** The status after a tag is added in place has been verified.
- **SIMATIC SD isn't a lossless format.** Even when the check passes, alarms, supervision, SiVArc and member attributes can still be lost. `verifyDocumentReadback` compares only the `.s7dcl` and `.s7res` text (`sdDocumentsMatch`). SD exports on V21 carry no block number, so a block imported as new gets its number from TIA, with only a generic warning.
- **SD export of a startup OB on V20 needs V20 Update 4 and SimaticSdEnabler.** Without them, TIA refuses the export; the result is a definite failure with the Siemens text.
- **Reading and writing watch-table entries needs V17 or later.** On V14 SP1–V16, the watch-table tools return a partial result that says why and don't try to connect to the PLC.
- **Outcome rules aren't uniform yet.** The default host rules that all tools share moved to 4.1. Ordinary cases can still report an unknown outcome, or a definite failure without evidence.
- **Some failed writes still report an unknown outcome.** These include deleting blocks, types and tag tables, generating blocks from source (except a generation failure that TIA states explicitly), and staging and committing with `ManagePlcGitRepository`. An unchanged name or version doesn't prove that there was no side effect.
- **Imports that meet an unrecognized exception report an unknown outcome.** Examples are format errors in files for alarm classes, alarm text lists and OPC UA interfaces.
- **The check for old values in nested UDTs has a condition.** It can report a match only when the standard export is available.
- **The evidence for a refused import has limits.** It covers only the target block and the block names of the target group, not other objects, UDTs or libraries.
- **Verified import doesn't cover every case.** Member attributes and comments inside UDT expansions aren't compared, and block attributes and member settings that a new document omits are restored from the original block. Expansions of UDT arrays aren't normalized, and the flags of unexpanded UDT instances aren't restored.
- **Workspace export decisions have limits.** A snapshot reports an unknown outcome when it meets a reparse point, more than 10,000 entries, or an unreadable entry. A delayed write after the snapshot, or a same-length rewrite within the timestamp precision, can go unseen. When no object was exported but a mapping was kept or a file was written, the result is `PARTIAL_FAILURE`, and the real number of failures is in `data.evidence.failed`.
- **Labelled diagnostics can be masked completely.** When the text after a label such as `[Error]` contains something that looks like a credential or a JSON fragment, the whole text is shown as dots, even when it contains no secret.
- **Certificate templates aren't available for S7-1500 CPUs with firmware V2.9 on TIA V17 and later.** This is a known TIA limitation, recorded again on V17–V21 in the rc.8 retest.
- **`ExportDeviceAml` can't export some HMI devices.** This is a TIA limitation: on V19–V21, TIA reports a TypeIdentifier error and leaves a partial file; on V15.1–V18, the TIA export returns failure. On V17, an HMI AML import reports "wrong type"; the cause isn't known yet.
- **`CreateDevice` still refuses to create a TP700 panel (V18–V20).** The refusal gives the reason. On V18 and V19, the keyword route of `CreateHardwareCatalogDevice` works.
- **An OPC UA ReferenceNamespace can't be created.** `ImportOpcUaInterface` always refuses to create a `ReferenceNamespace`.
- **V14 SP1, V15.1 and V16 can't compile with a safety program password.** Openness for these three releases has no interface for it, and a compile with a password returns `UNSUPPORTED_CAPABILITY` before approval; compile the safety program in TIA.
- **Updating an OPC UA alarm type on V21 can make TIA exit.** Changing a nodeId with `ManageUnifiedOpcUaAlarmType` on TIA V21 with a user interface makes the TIA process exit, and the result is `OUTCOME_UNKNOWN`. The cause isn't known yet, and the probe moved to 4.1; save the project first, or make the change in TIA by hand.
- **V21 cross-references have been verified only on TIA without a user interface.** The check with a user interface moved to 4.1.
- **V19–V21 refuse to create Unified script modules.** Create the module in TIA, then preview and apply `SetUnifiedGlobalScript` with `action=update`.
- **V21 LAD generation is limited.** A fan-out branch that starts with a contact is refused, and rising or falling edge contacts in rung requests return `edge-contact-unverified`.
- **Batch, document, cross-reference and catalog tools don't accept a short PLC name.** Pass the full software path.
- **Read-only monitoring plans don't accept global tags from tag tables.** `PlanOnlineReadOnlyMonitoring` refuses such tags and says why.
- **Only one large usage entry is split into pages.** `GetToolUsage` moves only the full input definition of `BuildAndImportPlcArtifact` to later pages.
- **Most examples haven't run on a real machine.** Real-machine marks cover only some V18–V21 examples.
- **The Workbench hasn't been checked page by page on a real machine.** It has passed automated UI tests and offline screenshot checks.
- **Checks on the Workbench configuration page can pause the UI briefly.** Detection of AI clients and TIA installations still runs on the UI thread.
- **The About icon stays in color in high contrast.** In a narrow window, call details open in a 520-pixel drawer.
- **Open LOW findings.** `GetHardwareFeatures` lists some features as provided and then reports them as missing on read; `ProbeHardwareHmiConnectionWhitelistedServices` reports the interface candidate as unavailable; `GetSoftwareTree` lists the PID system UDTs under user types; `FindTools` contradicts itself about paging completeness when the first page is very large (V15.1); after TIA refuses `CreateDevice`, `execution` still says `not-started`; some errors of `PatchPlcBlockDocument` don't set `details.parameter`. On V16–V19, when the connection drops during the final comparison of a synchronization, the advice says to recompile instead of naming the interruption; a workspace root path with characters Windows doesn't allow makes `GetVersionControlStatus` fail instead of reporting that the check wasn't possible. Both are planned for 4.0.1.
- **V14 SP1–V19 workers use STA.** V20/V21 use MTA.

### Upgrade from 3.x

GitHub marks 4.0.0 as Latest, but the 3.3 automatic updater doesn't offer it (decision of 2026-11-21). The 3.3 Workbench update check may show the 4.0.0 version number; the 3.3 updater doesn't recognize the package name of the final release and stops before downloading. Install by hand:

1. Save the project in TIA and finish any write in progress in 3.3.
2. Select `v4.0.0` on the releases page and download `TIA_MCP_v4.0.0_<date>.zip` and its `.sha256` file. Compare the sidecar with `Get-FileHash -Algorithm SHA256 -LiteralPath '.\<downloaded-package>.zip'` before extracting. Don't use the `Source code` archives that GitHub generates.
3. Extract to a new, writable folder, never over the 3.3 folder, and keep 3.3 until 4.0 works for you.
4. Start `TiaOpenness.exe`, run the environment check, then write the configuration of each AI client again from the Workbench, restart the client and refresh its tool cache and schemas. On the first connect, TIA asks for Openness access for the new worker program; allow it.
5. Try it on project copies first. Connect only one version to a TIA process at a time.

The [3.3 to 4.0 migration guide (Chinese)](../guides/migrate-3.3-to-4.0.md) walks through the side-by-side installation, client and plugin configuration, approvals, tool renames and rolling back to 3.3. The [configuration guide](../getting-started/configuration.md) covers client configuration.

The bundled updater in an rc installation can update directly to this release. The updaters of beta.1 through beta.6 recognize only the old package name; download by hand as above.

Behavior changes that a 3.3 user meets:

- **Tool names, arguments and results changed.** Replace old tool names and JSON-string arguments by using the [migration tables](v4.0.0-tool-migration.md), and read results as V4 envelopes: check `ok`, then `meta.outcome`, and on failure `error.code` and `error.details`.
- **Writes need a person's approval.** Approval is on by default, writes run after approval in the Workbench, and writes are refused while the Workbench is closed. You can turn approval off in the Workbench; online writes to real devices and `CloseProject` that discards changes still need a person.
- **Writes preview first.** Many write tools return only a plan by default; to apply, pass `dryRun:false` and the plan hash from the preview.
- **Sessions must be bound.** Call `ConnectPortal` and then `AttachOpenProject`; `ConnectProject` on V20/V21 is withdrawn. A TIA process belongs to one MCP session at a time.
- **HTTP has no access key.** Remove `--http-api-key` from launch commands, or write the client configuration again from the Workbench. Turn HTTP on only in a trusted network.
- **Arguments are stricter.** `expectedProject` is the project name and a path-like value is refused; tools that need the file identity use `expectedProjectFile` (an absolute path). Paths are absolute. `ListPlcBlocks` returns pages; continue with `meta.paging.nextCursor`. Input files can't be UNC or device paths.
- **Online and download are more cautious.** `trustDeviceCertificate` defaults to `false`; download prompts must be allowed with the `allow*` arguments; call `DisconnectOnlinePlc` before `DownloadPlc`.
- **The command line keeps only some commands.** `doctor`, `audit verify`, `schema`, `version`, `config`, `install-plc-tools` and `help` remain; use MCP tools instead of `gen`, `patch`, `describe`, `compile`, `export`, `import` and `prewarm`.
- **Data moved.** When the installation folder is writable, data lives under `<bundle-root>\data`. On first use, 4.0 copies the 3.3 connection settings (`%LOCALAPPDATA%\TiaPortalMcp\`) and Workbench preferences (`%LOCALAPPDATA%\TiaOpennessStudio\ui.settings`) only when the target is missing, and leaves the old files in place; logs aren't migrated. Later 4.0 updates keep `data` and `staging`.
