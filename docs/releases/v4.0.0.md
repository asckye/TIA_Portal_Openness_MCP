# v4.0.0: Draft

This is an unpublished draft; its CHANGELOG entry is added in the release commit, because the delivery check compares the newest CHANGELOG entry with the packaged version. Version 4.0 is a breaking change to MCP tool names, input schemas, result envelopes, and the installed product layout. It does not provide 3.x tool aliases or an input conversion layer.

## Changes

- Tool names are normalized by operation and domain, and equivalent guide and recipe lookups use `GetToolUsage`. This makes names more consistent and removes duplicate discovery entry points. The generated [release-key migration tables](../releases/v4.0.0-tool-migration.md) compare each archived 3.x catalog with its V4 baseline and list every old name with its destination, including unchanged names. They also mark merged, withdrawn and added tools and parameter changes, including JSON-string inputs replaced by typed objects or arrays.
- Inputs use the types in each tool's V4 schema, so clients can validate and send object structure without JSON-string encoding. V4-only safety parameters are not advertised while their behavior policy remains `current`.
- Results use one schema-version-4 envelope for direct calls, `CallTool` and batches so status, errors, and partial or unknown outcomes have one shape. `structuredContent` and the text representation contain the same envelope; `CallTool` does not wrap a successful target result in another JSON string. See [response and error rules](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/design-spec/v4-protocol.md).
- All eight releases use the same MCP host and the same kind of Openness worker. Each release starts `TiaMcp.FoundationHost.exe --release-key <key>` from its own runtime folder, and the host starts that release's PLC worker, `runtime/v<key>/worker/TiaMcp.PlcWorker.<key>.exe`. Tools common to all eight releases share one implementation, input schema and usage; a session is bound with `ConnectPortal` and then `AttachOpenProject` on every release. Tools that exist only on V20/V21 keep their V4 names and input schemas. On V20/V21 the worker runs shared and V20/V21-only operations on one TIA connection and one MTA owner thread; on V14 SP1–V19 it keeps its STA owner thread.
- V20 and V21 no longer ship the engine executables `TiaMcp.Engine.V20.exe` and `TiaMcp.Engine.V21.exe`, their worker files or `tool-catalog.json`; the PLC worker runs their tools as on the other six releases. Without TIA Portal, the packaged V20/V21 hosts return the same answers as the engine did. The host refuses the retired `--engine-worker`, `--engine-catalog` and other `--engine-*` options with exit code 64. The package's build record is `manifest/multi-version-build.json`; `manifest/release-build.json` is no longer delivered.
- The command line runs on `TiaMcp.FoundationHost.exe` for all eight releases and keeps `doctor`, `audit verify`, `schema`, `version`, `config`, `install-plc-tools` and `help`. The engine commands `gen`, `patch`, `describe`, `compile`, `export`, `import` and `prewarm` are retired; use the MCP tools and the project generation framework instead.
- Every MCP session has its own worker. Over stdio that is one worker; over HTTP each live session has one, so plan client concurrency by worker memory and TIA instances. A session's disconnect, fault, restart, staging and export handles do not affect other sessions, and ending the session ends its worker. The host binds every worker to a Windows job object, so workers also end when the host is terminated; a TIA Portal instance a worker started keeps running. A worker that exits on its own while the host ends it counts as stopped, so `DisconnectPortal` and session end no longer report "Unable to verify or stop the owned worker" for it. The HTTP host serves `/mcp/ready` (same Bearer authentication as MCP calls) and reports `fileVersion` in `/mcp/health` on every release.
- Every release leases the selected TIA process to one MCP owner. Attaching to an instance reserved by another live MCP session, or one whose previous owner was interrupted during a native call or left an unknown outcome, is refused with the lease reason as precondition text; an owner that ended while idle is taken over (see the lease rules below). Tools that need a connected TIA process are refused with `PRECONDITION_FAILED` naming `ConnectPortal` when no process is connected, and the session stays usable.
- After a write with an unknown outcome, the session refuses further native calls with `SESSION_RESET_REQUIRED` (`previous-outcome-unknown`) before approval and before Openness. Only results that crossed a native call lock the session. Recovery is the same on every release: inspect TIA, then call `DisconnectPortal`. An idle worker detaches without saving or closing (on V20/V21 it also releases the lease); a busy, timed-out or lost worker is terminated and the reply says TIA must be restarted. Then start a new MCP session and call `ConnectPortal` and `AttachOpenProject` again; never replay the failed request.
- All eight releases (V14 SP1–V21) share one worker channel timeout policy: 120 seconds by default, 300 seconds for the first attach of a worker generation, and 30 minutes for compile, download/upload, import/export, archive and library updates. `--worker-timeout-config` or `TIA_MCP_WORKER_TIMEOUTS` override these budgets; `--worker-timeout-seconds` sets the default budget. Previews and reads use the default; `DisconnectPortal` retains its bounded shutdown wait. Cancellation before dispatch returns `CANCELLED`; after dispatch the host waits for the real result. Requests over the 1 MiB frame are refused before dispatch, oversized replies are kept as export handles, and progress reaches the caller's progress token. Worker exit, hang, malformed frames or TIA process loss fault the worker generation with an unknown outcome; recover with `DisconnectPortal` or an explicit `RestartOpennessWorker`, then bind again. `RestartOpennessWorker` detaches an idle worker cleanly before starting the new generation; a faulted worker keeps its lease and reports `requiresTiaRestart`.
- V20/V21 default to the generated lite profile. `--profile full` or `TIA_MCP_PROFILE=full` advertises the full catalog; `FindTools` and `CallTool` reach it from lite. The generated table below gives current counts.
- `ConnectProject` (3.x `ConnectToProject`) is withdrawn on V20/V21 as a duplicate of `ConnectPortal` followed by `AttachOpenProject`. The other V20/V21 lifecycle tools (`ConnectIsolatedPortal`, `SaveProjectCopy`, `RetrieveProjectArchive`, `ManageMultiuserSession` and `BuildProjectScaffold`) keep their V4 records and publish their portal, project and lease into the same shared session, so a session holds only one binding. The project lifecycle tools on every release are `ConnectPortal`, `AttachOpenProject`, `OpenProject`, `CreateProject`, `SaveProject`, `CloseProject`, `DisconnectPortal`, `GetSessionState`, `ListPortalProcessProjects` and `GetPortalConnectionReadiness`.
- Writes are checked before they reach the Workbench. With approval enabled, a write first runs its own preview with the same arguments; a refusal is returned without an approval request, a preview that reports no effect returns without approval, and the approved call is checked again before it runs. The approval timeout starts after that preview, so a slow preview does not shorten the time to decide. Previews (`dryRun: true` or `mode: preview`) never wait for approval.
- Refusals before an operation are typed and leave the session usable: argument and precondition errors are `INVALID_ARGUMENT` or `PRECONDITION_FAILED` with the parameter name, precondition messages written by this project are passed through on every release, missing caller files are `INVALID_ARGUMENT`, and caller input files that cannot be read are refused before the operation. Project paths are only checked for existence, so opening a project file that TIA holds open no longer reports an unknown outcome. `INVALID_ARGUMENT`, `PRECONDITION_FAILED`, `SESSION_RESET_REQUIRED` and `CONFIRMATION_REQUIRED` results carry a `RECOVERY_GUIDANCE` warning with the `GetToolUsage` lookup and, when one fits, example arguments for the connected release.
- Import, project and directory paths are passed to Openness as normalized full paths, so either slash works. A single XML import with `overwrite: false` refuses an object that already exists before the native call. Creating a PLC tag or user constant refuses a symbol that already exists in any tag table of that PLC and names the table. V20/V21 import and export tools check the file format, an existing parent directory and a new target before the native call; an export exception that wrote nothing is `NATIVE_OPERATION_FAILED` with the native message instead of an unknown outcome.
- On V20/V21, a tool that only writes files and whose native call reports an explicit error or failure state (for example alarm-text, CAx, document and unit exports and folder downloads) returns `NATIVE_OPERATION_FAILED` without locking the session; imports, uploads and downloads that may have changed the project still return an unknown outcome. Both carry the native state, the log path, the native messages, and whether the target file exists and its size.
- `SaveProjectCopy` (V20/V21) is TIA Save As: the open project and the MCP binding switch to the new location, unsaved changes are saved into the new copy, and the original project file keeps its last saved state. It is classified `SESSION` like `SaveProject` and `CloseProject`, and its result reports `previousProjectFile` and `newProjectFile`.
- Two TIA Portal crashes found in the V20 VM rounds are guarded. SiVArc block tools accept only FB and FC blocks. On V20/V21, CFC chart protection and CFC exports are refused before any CFC call because the API offers no safe chart inventory; CFC imports remain available.
- Native calls are journaled and flushed before they start, and `GetNativeInvocationLog` reads the journals of every session by time, so the last native call before a TIA crash can be found from a new session. `ManagePlcGitRepository` refuses a missing repository path with a typed error.
- A compilation that returns errors is a completed failure with the new `COMPILE_ERRORS` code: the error and warning counts and up to ten leaf error messages with object paths are in the error details, and the full diagnostics stay in `data`.
- `StageImportFiles`, `ListStagedImportFiles` and `CleanupStagedImportFiles` let a client on another machine send SCL, SimaticML, tag-table and UDT text to the TIA machine. Files are written under `<bundle-root>/staging/<session>/<batch>/` (4 MiB per file, 128 files and 32 MiB per session); the approval request shows the location and each file's name, kind, size and SHA-256. Batches record their MCP session; another session can clean a batch after its owner session or host has ended. `ListStagedImportFiles` lists the newest 200 batches; when more exist, it returns them with an `INCOMPLETE_DATA` warning instead of failing.
- `ImportPlcBlocksFromDirectory` and `ImportPlcProgramFromDirectory` accept `overwrite: true`. The preview lists each object as created or replaced in the plan hash; every replaced object is exported before the first import, and a failure stops the batch and restores known replacements in dependency order. Single XML imports make a best-effort backup and report `BACKUP_SKIPPED` when they cannot.
- Hardware catalog tools refuse an unbound session and a catalog row that does not exist before any native write, and `CreateHardwareDevice` checks the device name and the reviewed plan hash before it creates, so a repeated apply is refused.
- Device creation uses exactly the requested type identifier, version and name, with no firmware stepping, alternative CPU or rename retry. A request without an exact match is refused before anything is created and lists the hardware-catalog candidates where the release has a hardware catalog. `CreateGsdDevice` is registered on V18–V21 only, and multicast transfer areas can be changed on V19 and later. Attribute writes check the attribute's access mode and read the value back, subnets are looked up by name before one is created, and a duplicate IO system name is refused. Every device walk finds the devices in the "Ungrouped devices" folder; VCI workspaces put them under a fixed `UngroupedDevices` folder and refuse a root device group with that name. `tia schema` describes `plcMlfb` as required and lists `plcVersion`, `hmiMlfb` and `hmiVersion`.
- TIA download prompts are answered only when the request allows them: the F-program download, hardware differences, cancelling test functions, an expanded download and loading identification data need `allowSafetyProgramDownload`, `allowHardwareDifferences`, `allowActiveTestCancel`, `allowExpandedDownload` and `allowIdentificationDataLoad`. The approval request shows the planned answers; a refused prompt stops the download, and the result names the prompt and the parameter that allows it (`meta.promptsRefused`). `DownloadPlc` requires an offline PLC, so call `DisconnectOnlinePlc` first. Data block reinitialization stops the PLC only when `stopBeforeDownload` is `true` (the default). `downloadScope: softwareOnlyChanges` is available on V17 and later.
- Device certificates are not trusted by default: `trustDeviceCertificate` defaults to `false` on the online, download and upload tools, and on V21 `meta.tlsVerification.certificates` lists the device certificates. A password is not sent over a connection that reports non-secure communication unless `allowNonTlsLogin: true`. Previews of `UploadStationFromPlc` and `UploadDeviceParameters` no longer scan the network, create addresses or apply a route; that happens only after approval.
- `OpenProject` and `RetrieveProjectArchive` accept `umacUserName`, `umacPassword` and `umacUserType` for UMAC-protected projects on V15.1–V21. The password never appears in logs, journals, the approval request, audit records or results. When TIA refuses a protected project because credentials are missing, the result is `PRECONDITION_FAILED` and names the missing parameters. Documented Openness refusals (access denied, missing products, missing license, multiuser refusal) return `PRECONDITION_FAILED` with `details.condition` and leave the session usable; a failed multiuser commit stays an unknown outcome. `OpenProject` and `CreateProject` are refused while another project or local session is open. TIA confirmation dialogs are refused by default and reported by `GetPortalInfo`. `DisconnectPortal` is refused while a project is still open in a TIA Portal the worker started, and `ShowObjectInEditor` needs a TIA Portal with a user interface.
- The Workbench environment page checks, without changing anything, whether the shipped workers are on the Openness firewall AllowList and shows the administrator's steps when they are not.
- Openness work runs on one exclusive lane per session; tools that do not use TIA run concurrently and do not wait behind a running TIA call.
- Every release's MCP host also starts when the matching TIA Portal or its Openness files are missing or the user is outside the Siemens TIA Openness group. `InitializeEnvironment` and the Workbench environment check report the cause and repair steps, and TIA-dependent calls are refused with `RESOURCE_UNAVAILABLE` before native dispatch.
- On the PlcWorker path the host checks every worker reply against the exact shape its tool reads; a reply of any other shape is malformed and stops the session. `doctor --fix` adds the user to the Openness user group on every release, reports "sign out and sign in again" when the membership takes effect at the next logon, and `doctor --json` gives the same result in machine-readable form for the Workbench.
- The hardware addressing family (`GetDeviceAddressing`, `GetDeviceIpAddress`, `GetDeviceItemIoAddresses`, `SetDeviceAddress` and `SetDeviceItemIoAddress`) runs through the shared Foundation adapters on all eight releases. It is new on V14 SP1–V19, where its behavior state is `current` with L5 `NOT RUN` (family `F19` in the behavior capabilities). The V20/V21 contracts and responses of these tools are unchanged; there they remain part of the full profile.
- More V20/V21 tool families run through the same shared adapters and are added to V14 SP1–V19 where the release's API allows: the host tools, discovery bridge and batch tools (`CallTool`, `FindTools`, `PreviewToolCall`, `ApplyToolBatch` and the offline analysis, documentation and template tools), hardware devices, modules, networks and CAx/AML exchange, PLC groups, deletion, protection, tag and constant definitions, instance DBs, verified import, external sources, cross references and device/HMI compile, watch tables, cause tracing, technology objects and motion, software units, checksums and fingerprints, and project languages and texts, compilation settings, transactions, object identifiers and Openness reflection, and global and project libraries. An action a release's API lacks is refused with `UNSUPPORTED_CAPABILITY` before any native call; formats evidenced only for V20/V21 (Classic HMI packages, SIMATIC SD documents) are not offered on older releases. Behavior on the newly enabled releases is `current` with L5 `NOT RUN`, and the V20/V21 contracts and responses of the moved tools are unchanged.
- Batch admission follows one reviewed classification on all eight releases. `RunReadOnlyToolBatch` accepts 47 read tools that a review found read-only, bounded and free of native side effects, for example `GetProjectTree`, `ListPlcBlocks`, `ListDevices`, the HMI listings and `GetOnlineState`. On V20/V21 it now accepts 13 of these that 3.3 refused. `GetUnifiedCrossReferences` and `GetExportContent` leave the read batch. Slow searches and reflection reads stay single-call only, and offline, write and file tools stay outside the read batch. `PreviewToolBatch` admits only the write tools whose classification allows a preview batch.
- Through `CallTool` and `PreviewToolCall`, a missing or invalid argument names the target tool's field and points `GetToolUsage` at the target tool.
- Eight Workbench control tools on every release (`ShowWorkbenchPage`, `ShowWorkbenchBlock`, `ShowWorkbenchCall`, `ShowWorkbenchLadder`, `ShowWorkbenchAtlas`, `GetWorkbenchState`, `GetWorkbenchSelection`, `PrefillWorkbenchForm`) let a client show pages, blocks, calls and renderings in the running Workbench and prefill a form for the user to confirm. They connect only to the Workbench of the same user and bundle, never start it, never approve or execute anything, and are refused inside batches; without a running Workbench they return `RESOURCE_UNAVAILABLE`.
- Standard packages: `ListStandardPackages`, `DescribeStandardPackage`, `ValidateStandardPackage`, `ManageStandardPackage` (import, export, copy, fork and remove user packages) and `ManageMachineDescription` (machine descriptions as JSON or CSV) work offline on every release. Packages shipped in `templates/standards` are read-only; user packages live in the data folder. File writes preview by default and need the usual approval.
- The workbench includes MCP write approvals, a hash-chain audit log with `tia audit verify`, a live call panel, an environment check and diagnostic bundle, single-block ladder rendering, and a whole-program book. Its views are rebuilt on one component set in light and dark themes and in Chinese and English; long call, approval and audit lists are virtualized and the audit page shows a bounded window. Generated ladder pages and the program book use the same visual style.
- `GetToolUsage` examples include the calls confirmed in VM test rounds, such as session binding with the exact project file, PLC aliases versus exact software paths, export directory rules and the export–import round trip.
- Product executables and resource lookup use one bundle-root contract so a complete installation can run outside a source checkout; data and logs follow that installation root when it is writable.

V14 SP1–V19 list a moved tool only when at least one of its actions can run on that release; actions the release lacks are refused before any native call.


All eight releases reserve the selected TIA process with a session lease. Requests persist BUSY before native dispatch, IDLE after a known result, and UNCERTAIN after an unknown result. A live owner refuses a competing attachment. A dead owner's RELEASED or IDLE lease can be taken over; ConnectPortal reports `data.previousOwnerEndedIdle=true` for an idle takeover. ## Result envelope and errors

Every result has `schemaVersion`, `ok`, `data`, `error`, and `meta`. `data` contains the tool's result or is `null`; `error` is `null` or an error object. `meta` identifies the release, tool and request, and reports `outcome`, `execution`, `completeness`, behavior policy, paging and warnings.

The outcome values are `succeeded`, `rejected-before-operation`, `read-failed`, `failed`, `partial`, and `unknown`. The CLI exits with 0 for success, 2 for refusal before an operation, 3 for a read or confirmed operation failure, 4 for partial results, and 5 for an unknown write outcome. CLI syntax errors exit 64; process-level failures before a tool context exists exit 70.

The V4 error-code set is `INVALID_ARGUMENT`, `LIMIT_EXCEEDED`, `UNSUPPORTED_CAPABILITY`, `TOOL_NOT_FOUND`, `PROJECT_NOT_BOUND`, `NOT_FOUND`, `TARGET_AMBIGUOUS`, `IDENTITY_MISMATCH`, `ALREADY_EXISTS`, `CONFIRMATION_REQUIRED`, `PLAN_STALE`, `PRECONDITION_FAILED`, `OFFLINE_REQUIRED`, `AUTHENTICATION_REQUIRED`, `ACCESS_DENIED`, `SESSION_RESET_REQUIRED`, `RESOURCE_UNAVAILABLE`, `IO_FAILED`, `NATIVE_OPERATION_FAILED`, `COMPILE_ERRORS`, `CANCELLED`, `TIMEOUT`, `NOT_EXECUTED`, `PARTIAL_FAILURE`, `OUTCOME_UNKNOWN`, and `INTERNAL_ERROR`. The details each code carries and the outcome rules are defined in the [4.0 specification](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/design-spec/v4-protocol.md); `COMPILE_ERRORS` carries `errorCount`, `warningCount` and the leaf `errors`.


The warning codes in `meta.warnings` are `INCOMPLETE_DATA`, `NATIVE_WARNING`, `CANDIDATE_ONLY`, `UNVERIFIED_BEHAVIOR`, `CLEANUP_FAILED`, `NATIVE_CAPABILITY_LIMIT`, `DIAGNOSTIC_WRITE_FAILED`, `APPROVAL_DISABLED`, `RECOVERY_GUIDANCE`, `BACKUP_SKIPPED`, `APPROVAL_PRECHECK_REFUSED`, and `STAGING_FOLDER_RETAINED`. A warning never turns a failure into a success.

## Product and bundle layout

| Entry | Bundle-relative path and role |
|---|---|
| `TiaOpenness.exe` | Root workbench launcher; starts `runtime/studio/TiaOpenness.exe`. |
| `TiaMcp.FoundationHost.exe` | `runtime/v<release-key>/` for all eight release keys `14sp1`, `15.1`, `16`, `17`, `18`, `19`, `20`, and `21`; the MCP server entry, started with `--release-key <key>`. |
| `TiaMcp.PlcWorker.<release-key>.exe` | `runtime/v<release-key>/worker/` for all eight release keys; the PLC worker the host starts for each MCP session. |

The package contains no engine executables: client configurations and the command line use `TiaMcp.FoundationHost.exe` for every release. The engine's former stdio/HTTP MCP host and isolation supervisor, including its `--isolate-openness` and `--no-isolate-openness` switches, have been removed; on every release Openness runs in the separate worker process.

The matching TIA Portal installation, Openness components, and licenses are installed separately. The Foundation hosts and the workbench use the bundled .NET 10 runtime; the per-release PLC workers and native Openness components require .NET Framework 4.8.

The Foundation hosts, including their command-line commands, accept `--bundle-root <absolute-path>` or `TIA_MCP_BUNDLE_ROOT`. The command-line option takes precedence. If an explicitly selected root is invalid, startup reports `RESOURCE_UNAVAILABLE` and does not search another root. See [runtime layout](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/runtime-layout.md).

When writable, software data is stored under `<bundle-root>/data`. The main process logs are under `data/logs/<releaseKey>` and workbench logs under `data/logs/studio`; native diagnostics and call-panel records are under `data/diagnostics`, the audit chain is under `data/logs/audit`, and the backups of overwrite imports are under `data/recovery`. Import staging is under `<bundle-root>/staging`, not under `data` or `%LOCALAPPDATA%`. An explicit `TIA_MCP_DATA_DIRECTORY` selects another absolute data root and fails if it is not writable. If the bundle data directory is unavailable, the existing per-purpose fallbacks include `%LOCALAPPDATA%\TiaMcp\diagnostics` for diagnostics, `%LOCALAPPDATA%\TiaMcp\logs\audit` for the audit chain, `%TEMP%\TiaMcp\logs\<releaseKey>` for process logs, `%TEMP%\TiaMcp\logs\studio` for workbench logs, `%LOCALAPPDATA%\TiaPortalMcp` for configuration, and `%LOCALAPPDATA%\TiaOpennessStudio` for UI preferences. Configuration and UI preference files are copied from their former user directories only when the corresponding bundle file is absent; old files are left in place. Logs and diagnostics are not migrated.

The companion Python default is `%LOCALAPPDATA%\TiaMcp\ecosystem-python\Scripts\python.exe`. `TIA_MCP_PLC_TOOLS_PYTHON` overrides it. The bundle does not create or reuse a Python environment beside the installation.

The workbench can migrate existing MCP client launch commands and arguments to the selected release's 4.0 host. It asks before writing, creates a timestamped backup beside each existing configuration file, and preserves server URLs, authentication fields, and unrelated entries. If the selected host is missing, it refuses to change that client's configuration. Restart the affected clients after migration.

## Upgrade from 3.x

Upgrading from 3.x to 4.0 is a fresh install. Download the complete 4.0 ZIP and unpack it into a new folder; do not unpack it over the 3.x folder. Keep the old folder until the 4.0 workbench and clients are confirmed working. The 3.3 PowerShell updater checks its required legacy package paths before creating a backup or replacing files. Those paths are absent from the 4.0 package, so it stops with `package is incomplete` without replacing or deleting any installed file; the ZIP it downloaded stays in the installation's `.update\` folder and its extracted copy in `%TEMP%\tia-mcp-update-<process id>`, both safe to delete.

The 4.0 MCP entry points and tool names changed. Recreate each AI client's configuration from the new workbench and refresh the client's tool cache and schemas; do not reuse the 3.x launch commands. From 4.0 onward, use the bundled C# updater for subsequent releases.

| 3.3 data | 4.0 location | What to copy |
|---|---|---|
| Connection settings: `%LOCALAPPDATA%\TiaPortalMcp\` (`http-v<release>.json`, `client.json`) | Writable bundle `data\config\` | On first use, 4.0 copies these existing files when the corresponding target is absent. Keep the originals as a backup. These files are not the AI client's MCP launch configuration. |
| Workbench preferences: `%LOCALAPPDATA%\TiaOpennessStudio\ui.settings` | `data\ui\ui.settings` | 4.0 copies it on first use only when the target is absent; keep the original. |
| Approval state | 3.3 has no Workbench MCP approval settings file; 4.0 stores it in `data\config\approval.settings` | There is no 3.3 state to migrate. New 4.0 installs enable approvals by default. For a later 4.0 reinstall, copy this file while the applications are closed to retain the approval switch and timeout. |
| Process and workbench logs: `%LOCALAPPDATA%\TiaMcp\logs\<releaseKey>\` and `studio\` | `data\logs\<releaseKey>\` and `data\logs\studio\` | Logs are not migrated automatically. Keep them in place, or copy the relevant subdirectories after closing both installations; avoid overwriting existing files. |
| Audit data | 3.3 has no 4.0 approval audit hash chain; 4.0 stores it in `data\logs\audit\` | There is no 3.3 chain to migrate. When moving an existing 4.0 installation, copy the entire audit directory with all applications closed if the chain must be retained; do not copy only part of it. |

If the bundle data directory is not writable, 4.0 uses the per-purpose user-directory fallbacks described above. The updater preserves the `data` and `staging` directories during later 4.0 updates.

## Workbench write controls and diagnostics

MCP write approvals are enabled by default. With approvals enabled, MCP writes are refused while the workbench is closed; open the workbench to review a pending request, or turn approvals off in the MCP menu. Read-only MCP calls and previews do not wait for approval. `WRITE` and `ONLINE-WRITE` calls wait for approval, and so do `StageImportFiles`, `CleanupStagedImportFiles`, `SaveProject`, `SaveProjectCopy` (save-as, V20/V21) and `CloseProject`, although the tool catalog classifies these as `FILE` or `SESSION`. Other session calls such as connect, attach, open, and disconnect remain ungated. A write that its own preview refuses is returned with `APPROVAL_PRECHECK_REFUSED` and no approval request. Turning approvals off is visible in response metadata and does not remove a tool's own confirmation or plan checks.

The audit log records write requests, approvals, refusals, and outcomes; the request, decision and start/end rows of one call share the response's `requestId`. `tia audit verify` checks the audit chain. The call panel shows current calls and pending approvals. The environment page checks the local setup and can export a diagnostic bundle. Ladder rendering produces an SVG for an individual block; the program book collects rendered blocks and available check results into a self-contained HTML file.

## D1 safety-policy state

The V4 baselines report `state=current` and `l5=NOT RUN` for every D1 behavior family on all eight release keys. Where an operation is applicable, the existing 3.x behavior is included. The `UNVERIFIED_BEHAVIOR` warning remains visible. Safe-v4 candidates are present but are not selected in the shipped policy.

The families are device creation (`P6-DEVICE`), import (`P6-IMPORT`), export (`P6-EXPORT`), connect/open (`P6-SESSION`), save/close (`P6-CLOSE`), PLC paths and external sources (`P6-SOURCE`), compile (`P6-COMPILE`), and native fallback (`P6-FALLBACK`). Passing L5 for a family on a specific release can switch that accepted release/family entry to `safe-v4`; unaccepted entries remain `current`. The applicability and deferred work are recorded in the [real-machine ledger](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/reference/real-machine-ledger.md). L5 acceptance for D1 does not complete the separate product, G3/G9, or J gates.

## For MCP clients

Close the old MCP host before replacing the installation, then start a new MCP session and explicitly connect to the selected TIA process. A normal idle shutdown or an idle worker kill does not require restarting TIA. Restart that TIA instance only after an interrupted native call or an unknown outcome; a legacy ACTIVE lease cannot prove the old owner was idle and remains refused. Do not delete lease files to bypass the guard.

After upgrading, refresh the client's tool cache and read the selected release's current tool schemas. 4.0 does not register 3.x aliases; old names and JSON-string argument encodings must be replaced using the [generated migration tables](../releases/v4.0.0-tool-migration.md). Bind a session with `ConnectPortal` and `AttachOpenProject` on every release; on V20/V21, replace `ConnectProject` with that sequence.

Use `GetToolUsage` for examples for the selected release. The [tool-call examples](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/calls.json) contain per-tool arguments, and [sequences](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/sequences.json) contain ordered calls. Runnable source examples include [SCL](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/languages/FC_Add.scl), [Unified HMI JavaScript](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/languages/unified-tag-read.js), [Classic HMI VBScript](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/languages/classic-tag-read.vbs), and the [language catalog](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/languages/catalog.json).
