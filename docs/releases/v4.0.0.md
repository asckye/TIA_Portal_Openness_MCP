# v4.0.0 — Draft

This is an unpublished draft; its CHANGELOG entry is added in the release commit, because the delivery check compares the newest CHANGELOG entry with the packaged version. Version 4.0 is a breaking change to MCP tool names, input schemas, result envelopes, and the installed product layout. It does not provide 3.x tool aliases or an input conversion layer.

## Changes

- Tool names are normalized by operation and domain, and equivalent guide and recipe lookups use **GetToolUsage**. This makes names more consistent and removes duplicate discovery entry points. The generated [release-key migration tables](v4.0.0-tool-migration.md) compare each archived 3.x catalog with its V4 baseline and list every old name with its destination, including unchanged names. They also mark merged and added tools and parameter changes, including JSON-string inputs replaced by typed objects or arrays.
- Inputs use the types in each tool's V4 schema, so clients can validate and send object structure without JSON-string encoding. V4-only safety parameters are not advertised while their behavior policy remains **current**.
- Results use one schema-version-4 envelope for direct calls, **CallTool**, batches, and CLI output so status, errors, and partial or unknown outcomes have one shape. **structuredContent** and the text representation contain the same envelope; **CallTool** does not wrap a successful target result in another JSON string. See [response and error rules](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/response-and-errors.md).
- The workbench includes MCP write approvals, a hash-chain audit log with **tia audit verify**, a live call panel, an environment check and diagnostic bundle, single-block ladder rendering, and a whole-program book.
- Product executables and resource lookup use one bundle-root contract so a complete installation can run outside a source checkout; data and logs follow that installation root when it is writable.

## Result envelope and errors

Every result has **schemaVersion**, **ok**, **data**, **error**, and **meta**. **data** contains the tool's result or is **null**; **error** is **null** or an error object. **meta** identifies the release, tool and request, and reports **outcome**, **execution**, **completeness**, behavior policy, paging and warnings.

The outcome values are **succeeded**, **rejected-before-operation**, **read-failed**, **failed**, **partial**, and **unknown**. The CLI exits with 0 for success, 2 for refusal before an operation, 3 for a read or confirmed operation failure, 4 for partial results, and 5 for an unknown write outcome. CLI syntax errors exit 64; process-level failures before a tool context exists exit 70.

The V4 error-code set is **INVALID_ARGUMENT**, **LIMIT_EXCEEDED**, **UNSUPPORTED_CAPABILITY**, **TOOL_NOT_FOUND**, **PROJECT_NOT_BOUND**, **NOT_FOUND**, **TARGET_AMBIGUOUS**, **IDENTITY_MISMATCH**, **ALREADY_EXISTS**, **CONFIRMATION_REQUIRED**, **PLAN_STALE**, **PRECONDITION_FAILED**, **OFFLINE_REQUIRED**, **AUTHENTICATION_REQUIRED**, **ACCESS_DENIED**, **SESSION_RESET_REQUIRED**, **RESOURCE_UNAVAILABLE**, **IO_FAILED**, **NATIVE_OPERATION_FAILED**, **CANCELLED**, **TIMEOUT**, **NOT_EXECUTED**, **PARTIAL_FAILURE**, **OUTCOME_UNKNOWN**, and **INTERNAL_ERROR**. The details allowed for each code and the outcome rules are in [response-and-errors.md](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/response-and-errors.md).

## Product and bundle layout

| Entry | Bundle-relative path and role |
|---|---|
| **TiaOpenness.exe** | Root workbench launcher; starts **runtime/studio/TiaOpenness.exe**. |
| **TiaMcp.FoundationHost.exe** | Under <code>runtime/v&lt;release-key&gt;/</code> for release keys **14sp1**, **15.1**, **16**, **17**, **18**, and **19**. |
| **TiaMcp.Engine.V20.exe** | **runtime/v20/**; full V20 engine. |
| **TiaMcp.Engine.V21.exe** | **runtime/v21/**; full V21 engine. |

The matching TIA Portal installation, Openness components, and licenses are installed separately. Foundation hosts and the workbench use the bundled .NET 10 runtime; the V20/V21 engines and native Openness components require .NET Framework 4.8.

Engine, Foundation host, and CLI entry points accept **--bundle-root &lt;absolute-path&gt;** or **TIA_MCP_BUNDLE_ROOT**. The CLI option takes precedence. If an explicitly selected root is invalid, startup reports **RESOURCE_UNAVAILABLE** and does not search another root. See [runtime layout](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/runtime-layout.md).

When writable, software data is stored under <code>&lt;bundle-root&gt;/data</code>. The main process logs are under <code>data/logs/&lt;releaseKey&gt;</code> and workbench logs under <code>data/logs/studio</code>; native diagnostics and call-panel records are under <code>data/diagnostics</code>, and the audit chain is under <code>data/logs/audit</code>. An explicit **TIA_MCP_DATA_DIRECTORY** selects another absolute data root and fails if it is not writable. If the bundle data directory is unavailable, the existing per-purpose fallbacks include **%LOCALAPPDATA%\TiaMcp\diagnostics** for diagnostics, **%LOCALAPPDATA%\TiaMcp\logs\audit** for the audit chain, **%TEMP%\TiaMcp\logs\<releaseKey>** for process logs, **%TEMP%\TiaMcp\logs\studio** for workbench logs, **%LOCALAPPDATA%\TiaPortalMcp** for configuration, and **%LOCALAPPDATA%\TiaOpennessStudio** for UI preferences. Configuration and UI preference files are copied from their former user directories only when the corresponding bundle file is absent; old files are left in place. Logs and diagnostics are not migrated.

The companion Python default is **%LOCALAPPDATA%\TiaMcp\ecosystem-python\Scripts\python.exe**. **TIA_MCP_PLC_TOOLS_PYTHON** overrides it. The bundle does not create or reuse a Python environment beside the installation.

The workbench can migrate existing MCP client launch commands and arguments to the selected 4.0 engine. It asks before writing, creates a timestamped backup beside each existing configuration file, and preserves server URLs, authentication fields, and unrelated entries. If the selected engine is missing, it refuses to change that client's configuration. Restart the affected clients after migration.

## Upgrade from 3.x

Upgrading from 3.x to 4.0 is a fresh install. Download the complete 4.0 ZIP and unpack it into a new folder; do not unpack it over the 3.x folder. Keep the old folder until the 4.0 workbench and clients are confirmed working. The 3.3 PowerShell updater checks its required legacy package paths before creating a backup or replacing files. Those paths are absent from the 4.0 package, so it stops with `package is incomplete` without replacing or deleting any installed file; the ZIP it downloaded stays in the installation's `.update\` folder and its extracted copy in `%TEMP%	ia-mcp-update-<process id>`, both safe to delete.

The 4.0 engine executable names and MCP tool names changed. Recreate each AI client's configuration from the new workbench and refresh the client's tool cache and schemas; do not reuse the 3.x launch commands. From 4.0 onward, use the bundled C# updater for subsequent releases.

| 3.3 data | 4.0 location | What to copy |
|---|---|---|
| Connection settings: `%LOCALAPPDATA%\TiaPortalMcp\` (`http-v<release>.json`, `client.json`) | Writable bundle `data\config\` | On first use, 4.0 copies these existing files when the corresponding target is absent. Keep the originals as a backup. These files are not the AI client's MCP launch configuration. |
| Workbench preferences: `%LOCALAPPDATA%\TiaOpennessStudio\ui.settings` | `data\ui\ui.settings` | 4.0 copies it on first use only when the target is absent; keep the original. |
| Approval state | 3.3 has no Workbench MCP approval settings file; 4.0 stores it in `data\config\approval.settings` | There is no 3.3 state to migrate. New 4.0 installs enable approvals by default. For a later 4.0 reinstall, copy this file while the applications are closed to retain the approval switch and timeout. |
| Process and workbench logs: `%LOCALAPPDATA%\TiaMcp\logs\<releaseKey>\` and `studio\` | `data\logs\<releaseKey>\` and `data\logs\studio\` | Logs are not migrated automatically. Keep them in place, or copy the relevant subdirectories after closing both installations; avoid overwriting existing files. |
| Audit data | 3.3 has no 4.0 approval audit hash chain; 4.0 stores it in `data\logs\audit\` | There is no 3.3 chain to migrate. When moving an existing 4.0 installation, copy the entire audit directory with all applications closed if the chain must be retained; do not copy only part of it. |

If the bundle data directory is not writable, 4.0 uses the per-purpose user-directory fallbacks described above. The updater preserves the `data` directory during later 4.0 updates.

## Workbench write controls and diagnostics

MCP write approvals are enabled by default. With approvals enabled, MCP writes are refused while the workbench is closed; open the workbench to review a pending request, or turn approvals off in the MCP menu. Read-only MCP calls do not wait for approval. `SaveProject`, `SaveProjectCopy` (save-as), and `CloseProject` also require approval even though the tool catalog classifies them as `SESSION`; other session calls such as connect, attach, open, and disconnect remain ungated. Turning approvals off is visible in response metadata and does not remove a tool's own confirmation or plan checks.

The audit log records write requests, approvals, refusals, and outcomes. **tia audit verify** checks the audit chain. The call panel shows current calls and pending approvals. The environment page checks the local setup and can export a diagnostic bundle. Ladder rendering produces an SVG for an individual block; the program book collects rendered blocks and available check results into a self-contained HTML file.

## D1 safety-policy state

The V4 baselines report **state=current** and **l5=NOT RUN** for every D1 behavior family on all eight release keys. Where an operation is applicable, the existing 3.x behavior is included. The **UNVERIFIED_BEHAVIOR** warning remains visible. Safe-v4 candidates are present but are not selected in the shipped policy.

The families are device creation (**P6-DEVICE**), import (**P6-IMPORT**), export (**P6-EXPORT**), connect/open (**P6-SESSION**), save/close (**P6-CLOSE**), PLC paths and external sources (**P6-SOURCE**), compile (**P6-COMPILE**), and native fallback (**P6-FALLBACK**). Passing L5 for a family on a specific release can switch that accepted release/family entry to **safe-v4**; unaccepted entries remain **current**. The applicability and deferred work are recorded in the [real-machine ledger](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/reference/real-machine-ledger.md). L5 acceptance for D1 does not complete the separate product, G3/G9, or J gates.

## For MCP clients

After upgrading, refresh the client's tool cache and read the selected release's current tool schemas. 4.0 does not register 3.x aliases; old names and JSON-string argument encodings must be replaced using the [generated migration tables](v4.0.0-tool-migration.md).

Use **GetToolUsage** for examples for the selected release. The [tool-call examples](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/calls.json) contain per-tool arguments, and [sequences](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/sequences.json) contain ordered calls. Runnable source examples include [SCL](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/languages/FC_Add.scl), [Unified HMI JavaScript](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/languages/unified-tag-read.js), [Classic HMI VBScript](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/languages/classic-tag-read.vbs), and the [language catalog](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/reference/tool-examples/languages/catalog.json).
