All eight releases provide discovery, bridge, preview and batch tools. `FindTools` and `CallTool` reach the selected release's registered catalog; version gates, target approvals and project identity checks remain enforced. V14 SP1–V19 publish their full catalog; V20/V21 default to lite and accept `--profile full`.

On V14 SP1–V19 a ported tool is registered only when at least one implemented action can run on that release’s API (maintainer decision, 2026-10-09). Tools with no usable action are absent from discovery, usage, bridges and passive diagnostics. Partial tools retain `UNSUPPORTED_CAPABILITY` before any native call. PLC protection, system groups and instance DB creation start at V15.1; program updates and native cross-references start at V18. Network domains start at V16, transfer areas at V15.1, system diagnostics exchange at V17, and catalog device creation and certificate service objects at V18. Communication connections remain V21 only. Older overloads and per-attribute writes keep the other migrated tools usable.

Newly enabled tools remain `current / NOT RUN` until release-specific native acceptance. Offline output is a candidate; registration does not establish import compatibility. Inspect `GetToolUsage` and the selected tool schema for supported actions and formats.

## Release differences

- V14 SP1 has no ordinary watch-table listing; it is available from V15.1.
- Hardware device, module, network, library, PLC and HMI families use the Foundation adapters where the selected release's API supports their actions.
- V20/V21 advertise the wider PLC, HMI, hardware, library, online, and optional
  engineering families. The [Openness coverage review](openness-coverage.md)
  tracks per-release implementation gaps and API evidence.
- Whole-tool and action availability follows the official API for each release. The [generated release catalog](version-tool-catalog.md) lists the current names and release keys. Counts describe registration, not native acceptance.

## Workbench control

All eight releases expose `ShowWorkbenchPage`, `ShowWorkbenchBlock`,
`ShowWorkbenchCall`, `ShowWorkbenchLadder`, `ShowWorkbenchAtlas`,
`GetWorkbenchState`, `GetWorkbenchSelection`, and `PrefillWorkbenchForm`.
The six display/prefill tools use operation `UI`; state and selection use `READ`.
They belong to the `Workbench` domain and are available without TIA, including
V20/V21 full and lite profiles. UI tools cannot run in batches. A running local
Workbench is required; the host never launches it. Prefill awaits a person's
confirmation, and only Settings can change the UI control switch.

The Engineering page attaches to an MCP session through the operator channel and uses the same tools, approvals and audit records. `session.source` identifies the attached MCP session; the caller attribution distinguishes a person from AI. Preserve exact project/software/block identities when locating targets. See the [control channel](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/runtime-layout.md#工作台控制通道p8-20) and [examples](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/official-tool-usage.md).

## 工作台 engineering

The Engineering page uses the selected FoundationHost session and its version-specific worker. Select the release before binding; read project and software identities from that session. V14 SP1/V15.1 have no VCI; later releases use their supported VCI APIs.

## Build and package

The release package contains all eight MCP runtimes, 工作台, and its eight adapters. `dotnet run --project build-tools/release -- release` builds the public package after multi-version validation; `Package-MultiVersion.py` creates a local development archive. SDK and PublicAPI directories are local build inputs and are not included in the repository or public package. See the [release workflow](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/release-workflow.md) and [validation guide](https://github.com/asckye/TIA_Portal_Openness_MCP/blob/master/docs/development/validation.md).

`version-tool-catalog.md` is generated by `generate-catalogs` from registered source catalogs. `generate-tool-counts -Check` verifies the embedded count tables. Runtime `tools/list` remains authoritative.
