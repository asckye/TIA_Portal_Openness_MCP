# Unified version framework

[Current handoff](handoff.md) · [Tool matrix](../reference/version-tools.md) · [Validation](validation.md)

## Exact release identity

The shared catalog uses `14sp1`, `15.1`, `16`, `17`, `18`, `19`, `20`, `21`.
Original V14/V15 are excluded; service/minor keys are not numeric major-version aliases.
All eight MCP/worker and Studio adapter targets have compiled against their matching
PublicAPI inputs. Current build evidence is in
[the multi-version record](../../manifest/multi-version-build.json) and
[the full-engine record](../../manifest/release-build.json). New native acceptance is
**NOT RUN**; older candidate notes saying references or Windows compilation were
unavailable do not describe the current build.

One process uses one exact API identity. The resolver checks selected directories
and assembly identities, including V21's split assemblies. Selecting a release
does not translate XML, upgrade a project, or make its unavailable tools runnable.

## Runtime profiles and shared code

| Profile | Runtime contract |
|---|---|
| V14 SP1–V19 MCP | .NET 8 foundation host plus exact typed .NET Framework worker; advertises its supported subset |
| V20/V21 MCP | Full .NET Framework engines, full/lite catalogs and discovery bridge |
| Studio, all eight releases | Desktop and bridge call the selected Openness adapter directly; no Studio MCP transport |

All eight foundation workers and their adapters target .NET Framework 4.8.
V14 SP1, V15.1 and V16 retain their exact original Siemens API identities;
their net48 workers require the release-time checks in the
[real-machine ledger](../reference/real-machine-ledger.md).
The foundation worker serializes native calls on its owning STA; the full engine
has its own threading and optional worker-isolation contract. Do not merge these
by replacing one tool's name or threading primitive.

The catalog, environment facts, process arguments, diagnostics, dependency planning
and tool-example data can be shared without Siemens references. Native algorithms
that require different API types stay in typed release adapters. Studio shares
appropriate independent code while preserving its ViewModels and commands.

Tool names are not API contracts: foundation parameter names, preview/confirmation
inputs, response envelopes and errors differ from the full engine. Retrieve the
selected host's schema and `GetToolUsage`. The [version matrix](../reference/version-tools.md)
owns current counts and per-version exclusions; the
[functional matrix](../../reference/version-feature-matrix.json) owns workflow gaps.

## Compiler feature table

[TiaFeatures.props](../../tools/openness-shared/TiaFeatures.props) is the single table
of compiler features and their exact release ranges. It lives beside `TiaPublicApi.props`
in the existing shared build-input directory, which the release source inventories already
include. No implicit repository-wide import is used.

The input is `TiaReleaseKey`: adapters retain their existing `AdapterReleaseKey` mapping,
Studio maps `StudioReleaseKey`, and engines map `TiaBuildVersion` (V20/V21).
`TiaFeatureProfile` selects the existing consumer: `Adapter` enables `PLC_*`, `Studio`
enables `STUDIO_*`, and `Engine` enables `TIA_V20` only for V20. These profiles are needed
to preserve each project's define set. PlcWorker and ApiCompileChecks already use
`TiaReleaseKey` but have no release feature defines; they do not import the table.
The SDK still owns `TRACE`, `RELEASE` and
framework symbols. The `V$(TiaVersion)` text in ToolUsageData is a reference code example,
not a repository compiler setting.

Intentional test defines remain explicit, including HardwareCatalogTests, DeviceAddTests,
SpecialExportShapeTests, NativeTests.V20 and the offline-v20 suite argument.
No `AdapterCapabilities` are generated by this table.

[Check-TiaFeatures.py](../../scripts/checks/Check-TiaFeatures.py), run by the
`validate-bundle` workflow after the .NET SDK is installed, evaluates MSBuild `DefineConstants` in Release configuration
and compares sets against the committed
[expectations](../../scripts/checks/tia-feature-expectations.json). It covers all eight
adapter and Studio projects, both engines, all eight PlcWorker and ApiCompileChecks
release selections and intentional test defines.
The check uses actual imports without restoring, compiling, or loading Siemens APIs;
keeping it in Python lets the repository gate detect build-property drift without Siemens
PublicAPI files (the .NET SDK with MSBuild `-getProperty` support is required).
Future changes require an explicit review of the expectation diff:

```powershell
python scripts/checks/Check-TiaFeatures.py
python scripts/checks/Check-TiaFeatures.py --capture bin-build/tia-feature-candidate.json
```

`--capture` only writes the named candidate; it never updates the committed expectations
automatically. Use `--output <path>` to retain a checked evaluation as before/after evidence.

## Version admission

The full engine's `ToolVersionPolicy` applies at discovery, bridge/preflight and
outer MCP dispatch, before worker forwarding or native calls. V20 excludes eleven
whole V21-only tools; mixed-action families retain supported operations and reject
unavailable selectors. Known unavailable names remain distinguishable from unknown
names. Product options, licenses and object-specific support are separate checks.

Foundation filters its registered catalog to its own implemented release routes.
Its passive `Bootstrap`/`RunCapabilitySelfTest` inspect configuration, registry
shape and operation mappings; they do not probe native readiness or call a worker.
Cached `GetState` is not proof of a live native connection.

VCI is unavailable in V14 SP1/V15.1; V16–V19 use the legacy workspace mapping API,
and V20/V21 use the modern mapped-object API. SDK signatures alone do not certify
the complete export/import round trip.

## Foundation session and engineering contracts

Foundation attachment requires an explicit currently enumerated process ID.
Project binding uses the exact project name and absolute path. Ordinary Open/Create
and explicit Save are implemented; Close requires an owned, unmodified project
and does not silently save. Explicit Disconnect is terminal and acknowledges
non-owning attachment release; it does not save, close, kill or automatically reconnect.

Native sessions require the existing explicit launch switch. Mutations use their
declared `dryRun`, `confirm`, `expectedProjectFile`, and where present fresh
`expectedPlanHash` contracts. A preview reports intentions, not completed work.
Ordinary project operations do not imply LocalSession, server lock/commit, archive
upgrade, protected-project authentication or secondary-project write support.

Exchange routes select explicit PLC software and groups. Import paths and original
bytes are preserved; version headers are not rewritten. Batch order and returned
per-item results are explicit. A partial/uncertain result does not mean rollback.
Source examples and actual schemas carry each tool's current input bounds, overwrite
semantics and output requirements, replacing separate candidate-contract pages.

Compilation now examines top-level, ungrouped and nested project devices. It requires
positive Offline observations for the selected PLC and all observable providers.
Devices without a provider appear in `offlineStateNotExposedByDevices`; they are not
asserted Offline. Siemens' all-device offline prerequisite still applies. Results
preserve error/warning counts and nested diagnostics. Engineering Offline is not CPU STOP.

External-source import/generation now have typed routes across the foundation
profiles, including ASCII source handling and explicit subsequent compile/readback.
V14 SP1 generation returns void: inventory observations do not become a fabricated
native generated-object list. Source import, generation, compile and Save remain
separate operations.

## Format and import boundaries

- UDT/GlobalDB declaration builders select exact release formats and are checked
  against the matching interface XSD fragments. Whole-document/native validation
  remains separate. Other shared builders still emit V21 candidates as documented.
- V14 SP1 SCL XML can contain interface-only information and cannot be presented
  as complete program restoration. File extensions or XML version edits are not conversions.
- SIMATIC SD language support depends on release/update: V20 DB/UDT/LAD and V21
  SCL/FBD/mixed additions have distinct contracts. Older LAD exports before V20
  Update 4 need regeneration. Check the exact selected tool and official example.
- Full-engine document imports require a directory and extensionless base filename.
  Inspect native status, messages and actual imported blocks. Batches stop after
  failure and preserve completed/attempted/not-attempted evidence.
- Full-engine block-directory import maps overwrite=false to native None. Mixed
  program import rejects duplicate classified identities; its types-first lexical
  schedule is not complete dependency resolution. Use the explicit planner where applicable.
- HMI and technology import paths no longer retry after native entry by rewriting
  input or selecting another overload. Failure may already have changed the project.
  None of these wrappers provides a general transactional rollback guarantee.
- Library document import and relocation retain their existing scope restrictions;
  an OB cannot be moved through an import path that changes its type/number.

## Remaining binding-snapshot integration

`BindingSnapshotContract`, `BindingSnapshotProcessSource` and
`BindingSnapshotAdapter` provide tested observation primitives. Current foundation
worker lifecycle dispatch does not call the transition hooks. Existing attachment
therefore remains PID-only; Siemens `AcquisitionTime` is a diagnostic snapshot time,
not OS process creation time. Full-engine binding checks do not confer their stronger
identity on the foundation profile.

Future integration must bracket actual attach/bind/unbind with Begin/Complete
transitions on the owning thread, capture the process-start anchor before attach,
increment epochs for every lifecycle transition (including same-path rebinding),
and fault on an unknown or interrupted outcome. Unknown/weak observations cannot
be converted to an unbound success. Terminal disposal ends the session and cannot
be represented as a recoverable detach. DTO conversion belongs in the matching
worker and must use observed state, never request-supplied identity.

## Evidence and maintenance

The retained [historical migration ledger](legacy-plc-migration-status.json),
[manual-read evidence](legacy-plc-manual-checklist.json) and `*-api-evidence.json`
preserve exact source/API observations. Historical status strings apply to their
recorded revision; current build and advertised scope come from the generated
manifests and version matrix. The 62-name ledger is not an exhaustive API inventory.

New capabilities update typed routes, admission, unified examples and meaningful
functional checks together. Use `dotnet run` for console test projects; `dotnet test`
does not execute their assertions. [Validation](validation.md) documents the current gates.
