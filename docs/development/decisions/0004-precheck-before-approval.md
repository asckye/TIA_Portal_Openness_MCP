# 0004 写请求先预检再审批，批准后复核再执行

- 状态：已采纳
- 日期：2026-10-06
- 决策者：维护者
- 置信度：高
- 相关：[重构计划](../refactor-plan.md) P6-60、P6-65；[4.0 发布说明草稿](../../releases/v4.0.0.md)“Changes”；[架构概览](../design-spec/architecture.md) 第 5.2 节；[V4 工具协议规范](../design-spec/v4-protocol.md) 第 9.4 节与第 10.2 节；[ADR 0003](0003-workbench-approval-for-mcp-writes.md)

回溯记录（写于 2026-10-11）。日期取 P6-60 的登记日期。

## 背景

审批上线后，明显不合法的写请求（路径不存在、对象已存在、缺 `expectedProjectFile` 等）也会排队等待人批准，批准后才失败；不会产生变化的写请求同样打扰用户。批准与执行之间，工程状态也可能变化。

## 选项

1. 先审批，执行时再检查：实现简单；用户会批准注定失败的请求。
2. 审批前用与预览相同的检查预检，批准后在 Openness 通道内复核：用户只看到可执行的请求；每次写入多一次只读预览。

## 决定

采用选项 2。写请求先用同样的参数在只读预览中运行：

- 预检拒绝时直接返回，不请求审批；
- 预览显示没有变化时返回预览结果，不请求审批；
- 批准后在 Openness 通道内复核会话锁、参数摘要与绑定身份，再执行（后来又加入生成写栅栏和批次身份的复核）。

只有越过原生调用的结果未知才锁定会话。两类宿主执行同一份规则（P6-65）。

## 后果

- 正面：审批卡只出现可执行的写请求；批准与执行之间的变化能被复核发现。
- 负面与取舍：每次写入多一次原生读取。预检拒绝被标为 `rejected-before-operation` 并附 `APPROVAL_PRECHECK_REFUSED`，这些标记目前在序列化后直接改写 JSON，绕过信封校验（API-28，4.0 前修正）。
- 验证方式：宿主行为一致性测试（两类宿主同一组场景）；响应快照中的预检拒绝。
