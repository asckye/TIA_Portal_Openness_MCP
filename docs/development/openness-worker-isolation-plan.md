## 依据与现状

Siemens [线程与并发](../../reference/siemens-openness/skills/threading-and-concurrency/SKILL.md)要求显式串行访问与合适的线程模型；[崩溃诊断](../../reference/siemens-openness/skills/crash-diagnosis/SKILL.md)要求在可能阻塞的 API 前后保留证据。第三方 [Czarnak 架构](https://github.com/Czarnak/tia-portal-mcp/blob/main/docs/ARCHITECTURE.md)将 MCP host 与 net48 worker 分进程，是值得参考的故障隔离边界。独立 worker 可以保住 MCP host；它无法修复或屏蔽 TIA 服务端自身崩溃。

静态 SemaphoreSlim 和 worker 队列协调各自服务；新增会话租约使同 Windows 用户的两个新版本 MCP 不能同时附加同一 TIA PID/启动时间。工具串行门不能取消已经进入 Openness 的同步调用。新 supervisor 统一处理传输/期限故障；已有异常分类器还不能覆盖所有被工具内部吞掉的原生故障。

## 完整目标关卡（尚未全部达成）

1. **先固定协议和身份。** host 保留 HTTP/STDIO、认证、工具清单和分页协议；worker 保留匹配版本的 net48 Openness。私有管道只传普通 DTO，绝不跨边界暴露 Siemens 代理对象。启动握手核对协议版本、API 主版本、引擎构建哈希与能力。工程绑定必须包含版本、PID、进程启动时间、规范化工程完整路径及会话代次；按名称模糊匹配不能作为写入身份。
2. **一个 worker 一条串行 MTA 执行队列。** 限制积压；请求在开始原生执行前取消可返回 cancelled，开始后不能谎报“已取消”。同一 TIA 实例跨 MCP 进程的协调需明确 mutex/lease 命名、访问权限和异常持有者退出语义，不能只复制现有静态锁。
3. **故障即使绑定失效。** 超时、worker 退出、管道断裂或响应序列错乱均从 Ready 进入 Faulted，使所有旧工程/对象句柄和预览令牌失效。写请求返回结果未知，不自动重放、不自动 Save、不附加其他工程。允许重建干净 worker，但恢复工程绑定须重新核对精确身份和所有权。
4. **日志在断点前落盘。** host 与 worker 共享调用相关 ID；记录队列时间、开始原生调用的时点、工具/步骤、可用的对象类型与路径、绑定代次。日志失败不能默默伪造已经记录的事实。收集 Windows 事件/转储路径线索须单独设计；不要自动开启全系统转储或上传工程内容。
5. **先故障注入，再接真实工程。** 不依赖 TIA 的假 worker 覆盖卡住、崩溃、部分 JSON、错误 ID、晚到响应、启动版本不匹配、重复写请求及 host 重启；证明 host 仍能响应独立诊断且不重放写入。之后才在获准的测试环境跑新框架，再逐族加入 MCP 的预览/写入/回读/编译断言。
6. **最后切换生产路径。** 保留对现有 V20/V21 注册工具的兼容验证；会话、事务、对象地址、库编辑、流式导出、异步工具和资源分页必须有迁移规则。整个迁移需要独立版本评审，不能仅套一个超时 Task 就宣布完成隔离。

## 必須保留的边界

- 不连接或修改 AutomaticDipCoatingMachine；测试工程需明确授权或由测试程序新建并持有。
- 原生 PLC 交叉引用保持默认拒绝。无法用故障注入、API 形状检查或第三方经验推断它的实际崩溃根因。
- 所有状态报告区分：实现、编译通过、离线故障注入通过、真实 TIA 验收通过。四者不能互相替代。
- 当前没有支持从零创建 Unified FaceplateType 或修改其内部控件/局部脚本的完整官方 API 证据；进程隔离不会补出缺失的 API。
