## 为什么不写进真机验收台账

真机验收台账是“已验收结果”和正式版本真机门槛的权威记录，而且有两部分由工具读取：

- `generate-prerelease-notes` 把 `未发布改动的验收边界`、`V20/V21 host + worker acceptance (P6-54)`、`4.0 安全策略验收计划（P6-R2）`、`4.0 发布前仍需的真实机器步骤` 四节的表格行编号，写进预发布说明的 “Not verified on a real TIA Portal” 清单；发布工具测试逐字节核对已发布的 beta 说明与这份生成结果，往这些表格加行会让已发布说明的核对失败。
- `generate-catalogs` 从台账生成逐版行为能力块，正则统计 `current | NOT RUN` 行。

测试者报告未经复核，内容包括缺陷、崩溃、提问和“通过”结论，混入台账会改变生成清单，也会模糊“已验收”的含义。因此报告先记在本页；复核后证据满足台账[“新记录应包含什么”](../reference/real-machine-ledger.md#新记录应包含什么)的通过结果，再由维护者写入台账对应位置并注明本页编号。

## 处理流程

1. 收到 Issue（问题报告、真机验证结果或预发布问题）后，在下表加一行，编号 `FB-NNN` 顺延，状态为“待复核”。
2. 核对包名和 SHA-256、TIA 版本和 Update、发布键、工具参数、完整结果信封和证据；缺少必要信息时状态改为“待补充”，在 Issue 中列出缺项。
3. 定性：缺陷进入任务清单（写明任务编号）；真机通过结果标为“通过”；与已有行相同标为“重复”并指向原编号。
4. 修复合并后写明提交和首个包含修复的版本，状态改为“已修复，待复测”；测试者复测通过后改为“已关闭”。
5. 通过结果满足台账要求时写入真机验收台账（不改动生成块和上述四节的表格，除非同时为下一个预发布重新生成说明），本行“去向”写台账位置。
6. 在 Issue 中回复结论后关闭。

## 状态取值

| 状态 | 含义 |
|---|---|
| 待复核 | 已登记，尚未核对 |
| 待补充 | 等测试者提供缺少的信息 |
| 已确认 | 复核确认是缺陷，已建任务 |
| 已修复，待复测 | 修复已合并，等真机复测 |
| 通过 | 真机结果符合预期 |
| 不适用 | 该版本没有对应能力，或不是本项目的问题 |
| 重复 | 与已有行相同 |
| 已关闭 | 处理完成 |
