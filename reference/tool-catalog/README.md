# Reviewed tool catalog inputs

`dotnet run --project build-tools/release -- generate-catalogs` owns the profile resource, version tool catalog, package counts, feature behavior table and ledger capability block. Run it and `generate-tool-usage` before building or capturing host responses. All generator `-Check` options compare raw bytes, including line endings and BOMs.

- `engine-source.json`: reviewed registrations and signatures frozen from commit `f2049d94296656198cb8c2c5c9d8544215602c92` for Q1. Each registration records its method, source path and owner, domain, full signature and parameter types, default expressions, evaluated defaults and descriptions. Paths are provenance only. The 48 frozen behavior entries record the former Engine and Shared candidate attributes; ledger P6 rows still own acceptance. The implementations were archived at tag `archive/safev4-candidates` and deleted on 2026-11-02 (ADR 0002); families that pass L5 are rebuilt on current code, P8-04l3 is cancelled and P8-31e6 is deferred. `foundationSourceNames` records the former Foundation names whose guidance substitutions now run in the usage generator, using `v3-v4-renames.json` targets. This data is maintained by review; normal generation never extracts it from `src/Engine`.
- `EngineSourceExamples.json` and `EngineSourceSequences.json`: frozen comparison evidence, formerly under the retired Engine test project's fixtures; frozen rows are not served to clients. Live examples use the complete maintained parameter set from `reference/tool-examples`. Usage generation validates parameter hints against `engine-source.json`; `FullEngineRejections.json` remains historical test evidence and is no longer a generated output.
- `new-v4-tools.json`: reviewed additions with owner, operation and the ordered eight release keys. Historical names cannot occur here. Known owner/operation decisions are checked in C#, and host-only additions must match GenerationTool registrations and ToolMetadata classifications.
- `v3-v4-renames.json`: frozen historical names from the eight 3.x archives. Exactly one target per archived name; the only approved merge is the three guide entries into GetToolUsage. New additions live in the separate file.
- `parameter-shapes.json`: reviewed typed parameter families and exact overrides. The generator checks frozen signatures, legacy parameter removal, declared types, envelope returns and Foundation adapter conversions.
- `lite-groups.json`: the reviewed workflow selection used to validate the original engine lite proposal. Shared Foundation contracts then determine the published lite roster.
- `behavior-examples.json`: frozen release-specific examples for the archived behavior entry/family pairs. The data stays byte-equal for existing catalog outputs; it does not select a candidate implementation. L5 acceptance comes only from exact release-scoped ledger decisions.
- `operation-review.json`: frozen operation exceptions, Foundation additions, withdrawn entries and source-name rebasing. The checker reads classification rules from ToolTaxonomy and explicit rows from ToolMetadata.
- `usage-topic-rules.json`: official topic and snippet mappings; project-defined and uncovered wrappers retain the no-direct-example rule.
- `phase6-groups.json`: frozen archive task memberships used by the remaining Python snapshot transition checks. Batch 4 will migrate this consumer; it never executes a generator.

DES-PORT A updates the ten reviewed compatibility, batch and move signatures and evaluated defaults in `engine-source.json`; CreateDevice remains available on all eight releases.

Port batches update PortedFamilies' per-tool release table, add reviewed data rows where needed, regenerate catalogs and usage, build, then capture. The old-release registration rule remains: a tool is listed only when at least one action is available. Unparsed family rows and unknown overrides fail closed.

`audit-version-tools -PublicApiRoot <SDK-root> [-InputsRoot <bin-build>] [-Output <candidate-directory>]` verifies the two owned catalog files and writes API audit evidence and candidate lists. `audit-tool-usage [-InputsRoot <bin-build>]` is the only writer of `manifest/tool-usage-coverage.json`; `-Records <json>` also accepts the eight distinct, source-hash-checked STDIO receipts from the remaining Python capturers. Capture those receipts under `bin-build`, then run this audit. They cannot run in build-free preflight: they require the same SDK XML, compiled inventories and eight release usage reports produced by the build/capture stages.

`generate-release-migration` reads the frozen rename data and eight current contract baselines. Its output is frozen after the 4.0 release. `docs/archive/development/phase6-review.md` is an archive; its marker blocks are not generated or checked.

DES-PORT-B synchronizes the 27 write-preview declarations with the served `dryRun`, `expectedPlanHash`, and `expectedProjectFile` parameters.
